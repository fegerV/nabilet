- `resources/js/lib/payments.ts` — `newIdempotencyKey()` (`pay_<uuid>`);
  ключ стабилен в пределах одного «намерения оплатить» и сбрасывается после

### R-02 + R-05 + R-09 — `PaymentService::initiatePayment()` переписан на ТРИ ФАЗЫ
Раньше: всё в одном `DB::transaction()`, SELECT без блокировки, вызов провайдера внутри.
Теперь:
- **Фаза 1** — только БД: `Order::whereKey($id)->lockForUpdate()->firstOrFail()`,
  затем `reusablePayment()` (по ключу → по активному платежу), затем `assertOrderIsPayable()`.
- **Фаза 2** — сеть ВНЕ транзакции.
- **Фаза 3** — снова `lockForUpdate()`, снова `reusablePayment()`, снова `assertOrderIsPayable()`.

Ключевые решения:
- **Порядок проверок в фазе 1 важен:** идемпотентный повтор (`reusablePayment`) стоит ВЫШЕ
  проверки оплачиваемости. Иначе клиент, нажавший «Оплатить» второй раз по уже оплаченному
  заказу, получал бы 409 `ORDER_NOT_PAYABLE` вместо своего платежа (200) — то есть не узнал бы,
  что деньги уже списаны.
- **Заказ в фазе 3 читается СВЕЖИМ** (`lockForUpdate()`), а не берётся из фазы 2. Снимок до
  сетевого вызова хранит старый `status`, и проверка по нему пропускает ровно ту гонку,
  от которой защищает фаза 3. Тест `test_the_order_status_is_rechecked_before_writing_the_payment`
  ловит именно это.
- **`assertOrderIsPayable()` разрешает `pending|awaiting_payment|payment_failed`.** `payment_failed`
  разрешён намеренно: клиент с отклонённой картой должен платить снова (`OrderStateMachine`
  держит `failed` нетерминальным).
- `reusablePayment()` — новый приватный метод, возвращает `array|null`; `ConflictError
  IDEMPOTENCY_CONFLICT` на чужой заказ переехал туда.

### SEO P-06 — `events:sync-status` (НОВАЯ КОМАНДА)
`app/Modules/Events/Console/SyncEventStatusCommand.php`, расписание `hourly()->withoutOverlapping(30)`.
`published → completed`, когда ЕСТЬ сеансы и ВСЕ закончились.
- Условие по сеансу: `COALESCE(sessions.ends_at, DATE_ADD(sessions.starts_at, INTERVAL N HOUR)) >= now()`
  → `whereDoesntHave('sessions', ...)`. `N` = `nabilet.events.session_default_duration_hours` (env
  `EVENT_SESSION_DEFAULT_DURATION_HOURS`, default 3).
- **Почему не `COALESCE(ends_at, starts_at)`:** `ends_at` nullable, и идущий трёхчасовой концерт
  объявлялся бы состоявшимся в момент начала. Окно вынесено в конфиг как явное допущение.
- Окно подставляется в SQL целым числом, а не параметром: `INTERVAL ? HOUR` разбирается не всеми
  версиями MySQL, а значение уже приведено к int.
- `EventService::complete()` теперь проверяет переход по `EventStateMachine` и бросает
  `ConflictError EVENT_TRANSITION_NOT_ALLOWED`. Без этого вызов на черновике записал бы `completed`,
  а `completed` входит в `EventStatus::publiclyVisible()` → черновик мгновенно стал бы публичным.

## Партия 4 (P-12): серверные посадочные страницы `/venue/{slug}`, `/city/{slug}`

**Проблема.** Каталог — hash-SPA с ОДНИМ индексируемым адресом (`/`). Фильтры
(`city`, `category`, `date_from`, `price_*`) объявлены в `ListEventsRequest`, но
`EventController::index()` читает только `organization_id|category_id|status|
is_featured` — то есть фильтры по городу/категории НЕ РАБОТАЮТ даже в API.
Длинный хвост запросов («афиша Сургута», «что идёт в филармонии») не имел
адресуемой страницы вообще.

**Что сделано (MVP по плану аудита: сначала площадки и города).**

Новые файлы:
- `app/Core/Support/RuText.php` — чистый хелпер: `plural()` (та же формула, что
  `plural()` в `resources/js/lib/format.ts`) и `date()/dateTime()` через
  `\DateTimeImmutable` (Carbon нельзя — каталог грузится без `vendor/`).
- `app/Modules/Seo/Services/CatalogService.php` — модель чтения каталога.
- `app/Modules/Seo/Services/LandingPageService.php` — заголовки/описания/тексты.
- `app/Modules/Seo/Services/LandingPageRenderer.php` — самодостаточный HTML.
- `app/Modules/Seo/Http/Controllers/LandingController.php`.
- `app/Modules/Seo/routes/web.php` → подключается из `routes/web.php` ВЫШЕ
  `Route::fallback()`.
- `tests/Support/CatalogFixtures.php`, `tests/Feature/Seo/LandingPageTest.php`,
  `tests/Feature/Seo/LandingSitemapTest.php`.

Правки: `LandingPage` (Domain) переработан — вместо поля `canonical` хранит
`baseUrl` + `canonical()`/`pageUrl()`/`static pageUrlFor()`; `StructuredDataService`
получил `generateItemList()`; `SitemapService` — `sitemap-venues.xml`,

`SitemapController` — `venues()`, `cities()` и общий `xml()`; `public/robots.txt`
дополнен.

**Ключевые решения.**
- Посадочные страницы отдаются СВОИМ HTML, а не оболочкой `dist/index.html`:
  адреса `/venue/…` в SPA не существует, и после монтирования Vue пользователь
  увидел бы каталог под адресом площадки. Стили встроены, внешних ресурсов нет →
  работают без `dist/` (в отличие от страницы события, которая даёт 503).
- Пустая коллекция и `?page` за последней страницей → 404 брендированной
  страницей (`NotFoundPage`), а НЕ пустой 200 и НЕ редирект.
- Порядок: сначала предстоящие (ближайшее вверх), затем прошедшие (недавнее
  вверх). Задаётся ТРЕМЯ ключами SQL, потому что группы требуют противоположных
  направлений, а список страничный.
- Город разрешается по slug из `Str::slug(venues.city)`; НЕСКОЛЬКО написаний
  («Санкт-Петербург» / «Санкт Петербург») сливаются в один адрес.
- Публичность = `EventStatus::publiclyVisible()`, БЕЗ требования `published_at`
  (мягче карты сайта) — навигационная страница не должна терять событие из-за
  незаполненного поля.

**Ловушки этой партии (стоили времени).**
- **`COALESCE(MIN(будущий), MAX(любой)) IS NULL` — НЕ разделяет группы.** У
  события с одним прошедшим сеансом COALESCE тоже возвращает дату, поэтому
  признак «будущего сеанса нет» не срабатывал, и ВСЁ сортировалось по одной
  дате: прошедшие концерты оказывались выше предстоящих. Разделять можно только
  по НАЛИЧИЮ будущего сеанса (`MIN(...) IS NULL`), а не по значению даты.
  Поймано тестом `test_upcoming_events_come_before_past_ones`.
- **`Str::slug()` транслитерирует НЕ интуитивно:** `Тюмень → tiumen` (не
  `tyumen`), `Брянск → briansk`, `Тверь → tver`. Адрес города — публичный
  контракт, поэтому в тестах он написан ЯВНО, а не через `Str::slug()`: падение
  такого теста = сигнал, что публичные адреса поехали (библиотека
  `voku/portable-ascii`). Смягчение при необходимости — таблица городов + редиректы.
- **`venues.slug` глобально уникален (P-03)** → две площадки с одним адресом в
  БД не создать, а фикстура создаёт новую площадку на каждое событие. Поэтому ВСЕ
  сценарии «список из N событий» (пагинация, порядок) идут через `/city/…`.
- **`CatalogFixtures` обязан САМ подключать `SellableSeatFixtures`** (`use` внутри
  трейта): иначе класс с `use CatalogFixtures;` падает «Call to undefined method
  seedSellableSeat()» — ошибка, невидимая при чтении теста.
- **`LandingPage::pageUrl()` — метод ЭКЗЕМПЛЯРА**, а не только статический
  `pageUrlFor()`: рендерер пагинации вызывает `$page->pageUrl(...)`, и его
  отсутствие дало 500 на любой странице с `lastPage > 1`. Тесты на одной странице
  этого не видят — нужен тест с пагинацией.
- **`Content-Type` карты = `text/xml; charset=utf-8`** (Symfony дописывает
  charset), а не `text/xml`.
- **`PreventIndexingOfServicePages`** — allow-by-omission в GLOBAL stack, и его
  докблок сам предупреждал про будущий `/venue/{slug}`. `/city/*` и `/venue/*` в
  список НЕ добавлены (иначе вся работа обнуляется незаметно: 200 есть, в индексе
  нет). Закреплено `test_a_landing_page_is_indexable` (`assertHeaderMissing('X-Robots-Tag')`).
- Провайдеры модулей не бутятся → маршруты модуля только через `routes/web.php`
  (web) и `routes/api.php` (api). `verify-route-ownership` сканирует ТОЛЬКО
  `routes/api.php`, поэтому `app/Modules/*/routes/web.php` для него невидим.

**Проверено.** Полный PHPUnit: **515 тестов / 1725 assertions, всё зелёное** (было
481/1612). Все девять гейтов exit 0 (`purity` 117 файлов / 0 нарушений, `openapi`
100 операций). `robots.txt` синхронизирован в `dist/`.

`/{city}/{category}` (фильтр), `sitemap-categories`; `Place`/`Organization` JSON-LD

### PHP-суита не герметична: секрет подписи брался из `.env` разработчика

### Ловушка PHPUnit `<env force="true">`

экспортированная переменная занимает `$_ENV`, и `env()` возвращает `''`.
Воспроизводить надо **подменой `.env`** на копию `.env.example` (+ `APP_KEY`).

## Партия 9 — суита страницы события перестала зависеть от сборки (коммит `e2586910`)

Пуш `a3318af0..e2586910`. Закрыт последний красный job CI — `PHP test suite`.

### Ключ к разбору: код возврата PHPUnit различает класс поломки

Run 292 (`01137b82`) — `exit 2` (ошибки: `QR_SECRET_NOT_CONFIGURED`), run 293
(`a3318af0`) — **`exit 1`**. То есть правка `TICKET_QR_SECRET` в `phpunit.xml`
сработала, а падало уже другое: `1` = упавшие утверждения, код отработал и вернул
не то. Без этого различия легко решить, что «та же ошибка осталась».

Аннотация (`check-runs/{id}/annotations`) даёт только «Process completed with exit
code 1» — номер строки в ней **врёт** (указывала на шаг job'а `frontend`). Шаг
определяется через `actions/runs/{id}/jobs` → `steps[].conclusion`.

### Причина: страница события обслуживается артефактом сборки

`EventPageController::spaShellPath()` → `config('nabilet.storefront.shell_path',
base_path('dist/index.html'))`. `dist/` — артефакт Vite: в git его нет (`.gitignore:
/dist`), и job `phpunit` его НЕ собирает (сборкой занят `frontend`, другой раннер).
На чистом клоне контроллер отвечает 503 `STORE_FRONT_NOT_BUILT`, и все тесты,
открывающие страницу события, падают. Локально проходило, потому что `dist/`
остался от прежней сборки: **результат зависел от состояния рабочего каталога**, а
не от кода — тот же класс, что `TICKET_QR_SECRET`.

Воспроизведение ровно CI-шного состояния: `mv dist dist.hidden` → **49 падений,
все «Expected 200 but received 503»**, в 6 файлах: `EventServerContentTest` (19),
`EventStatusSeoTest` (14), `EventBreadcrumbSeoTest` (13), `EventSeoPageTest` (5),
`EventRobotsTest` (4), `EventSlugUniquenessTest` (1).

### Починка

`tests/TestCase::setUp()` ставит `nabilet.storefront.shell_path` =
`tests/Fixtures/storefront-shell.html`. Все Feature-тесты наследуют `Tests\TestCase`
(проверено: ни один не минует `parent::setUp()` в этих 6 файлах). Тесты ветки 503
переопределяют путь сами.

Вопрос «цела ли настоящая сборка» переехал туда, где сборка есть: job `frontend`
после `npm run build` грепает `dist/index.html` на четыре точки контракта
(`<title>`, `<meta name="description"`, `</head>`, `<div id="app"></div>`).

`routes/web.php` (`/`) отвечал на тот же вопрос «собрана ли витрина» **жёстким**
`__DIR__ . '/../dist/index.html'` — теперь читает тот же ключ. Два владельца одного
решения — та же болезнь, что три копии схемы.

### Побочная находка: инъекция дублировала SEO-блок

Первая версия фикстуры упоминала в **комментарии** строки `</head>`, `<title>`,
`<div id="app"></div>` — и тесты дали «4 блока JSON-LD вместо 2». Причина в
`renderSpaShell()`: `str_replace('</head>', ...)` без счётчика вставляет блок
столько раз, сколько строка встречается в документе, а `preg_replace` по
`<title>`/`description` заменял **все** вхождения. У соседней замены `#app`
ограничение `1` было с самого начала — непоследовательность и была дефектом.
Теперь ограничение у всех; `</head>` — через `preg_replace_callback`, потому что
`preg_replace` трактует `$1`/`\1` в строке замены как ссылки на группы, а в блоке
лежит заголовок события (пользовательский текст).

Фикстуру всё равно переписали без буквальных конструкций в комментарии — она
обязана повторять настоящую оболочку, а не быть состязательной.

`if ($force || !isset($_ENV[$name]))`. Значит `force="true"` **перезаписывает**
`$_ENV`, а не «заполняет только если пусто». Прежняя заметка в этом файле (партия
