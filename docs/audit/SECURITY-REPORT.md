## 2. Требуется ротация

В git-истории остались токены локальных диагностических стендов (`.shots/.token`, `.shots/admin-token.env`, `.shots/club-token.env`, `.tmp-hall/club-token.php`). Удаление из индекса **не удаляет историю**. Если эти токены когда-либо использовались вне изолированного стенда, их нужно отозвать и заменить; порядок ротации описан в `docs/SECRET-ROTATION.md`.

## 3. Открытые риски (не исправлены в этой ветке)

1. **Platform-admin fallback.** `StaffRole::isPlatformAdmin()` при пустом `nabilet.platform_admins` возвращает true для любого арендаторского admin. Затрагивает админские роуты резервных копий, платежей, системы и обновлений. Изменение меняет правила доступа действующих установок — требуется решение владельца.
2. **Публичные inventory endpoints** (`GET /api/v1/inventory?session_id=…`, позиции по id) не проверяют видимость события иOrganization. Возвращают схему/цены/занятость чужого сеанса. Исправление изменит контракт витрины и потребует пересмотра тестов checkout.
3. **Перечисление организаций.** `GET /api/v1/organizations` доступен любому авторизованному пользователю.
4. **Байты медиа** отдаются статикой без проверки прав; доступность определяется знанием URL.
5. **NULL-владельцы медиа** (`organization_id IS NULL`) доступны любому admin.
6. **organization_id в payload** площадки/сеанса проверяется не везде явно; часть защиты достигается скоупом моделей, а не явной проверкой.
7. **MySQL 5.7** не исполняет CHECK и trigger; на таком хостинге DB-барьеры из раздела 1 не работают. Требуется MySQL 8.0+.

## 4. Рекомендации

- Сформировать явно заполненный список `platform_admins` как обязательный шаг установки; убрать permissive fallback.
- Добавить общий helper «виден ли сеанс гостю» и применять его во всех публичных inventory-контроллерах.
- Закрыть перечисление организаций для обычных пользователей.
- Перевести выдачу файлов медиа через подписанные URL с TTL.
- Добавить в CI проверку «никаких `withoutScope()` в новых admin-роутах без явной проверки владельца» как linternое правило.

## 5. Граница ответственности

Риски 1–4 меняют публичные контракты или бизнес-правила и поэтому не были изменены «молча» в рамках технического аудита. Они внесены в `BUG-REGISTER.md` со статусом Risk.
