# NABILET Core — Машины состояний

> Реализация: `app/Core/StateMachine/StateMachine.php` + `app/Modules/*/StateMachines/`
> Проверка: `php tests/run.php` — 34 теста на доменные машины, включая запрещённые переходы.

---

## 1. Почему это отдельный документ

Статусы `Order`, `Payment`, `Ticket` — несущий каркас домена. Если они закодированы как свободные строки с разбросанными проверками `if ($order->status === 'paid')`, система неизбежно приходит к возвращённому заказу, у которого одновременно есть `paid_at` и активный билет.

Поэтому каждый законный переход объявлен **один раз, в одном месте** и принудительно проверяется. Всё остальное — следствие.

---

## 2. Общий механизм

```php
$machine = StateMachine::define(
    name: 'Order',
    initial: 'pending',
    states: [...],
    transitions: ['pending' => ['awaiting_payment', 'cancelled'], ...],
    terminal: ['refunded', 'cancelled', 'expired'],
);
$machine->guard('partially_refunded', 'refunded', fn (array $ctx): bool => ...);
$machine->assert($from, $to, $context);   // бросает InvalidStateTransitionError
```

| Свойство | Смысл |
|---|---|
| `transitions` | Граф законных переходов, читаемый как есть |
| `guard` | Переход может зависеть от данных («только если возвращено всё») |
| `terminal` | Явные конечные состояния: UI скрывает кнопки, job'ы пропускают работу, не выводя правило заново |
| `assert()` | Бросает, а не возвращает `false` — невнимательный вызывающий не сможет проигнорировать запрет |

Ошибка несёт полный контекст попытки: `machine`, `from`, `to`, `allowed`, `reason`. Это то, что попадает в audit log и в сообщение администратору.

## 3. Order (ТЗ §26)

```
                    ┌──────────┐
                    │ pending  │
                    └────┬─────┘
        ┌────────────────┼────────────────┬──────────────┐
        │                │                │              │
        ▼                ▼                ▼              ▼
┌────────────────┐ ┌───────────┐  ┌──────────┐ ┌────────────────┐
│awaiting_payment│ │ cancelled │  │ expired  │ │ payment_failed │
└───────┬────────┘ └───────────┘  └──────────┘ └───────┬────────┘
        │             terminal      terminal           │
        │                                              │
        │  ┌───────────────────────────────────────────┘
        │  │  (повторная попытка оплаты)
        ▼  ▼
     ┌──────┐
     │ paid │
     └───┬──┘
         │
         ├──────────────────┐
         ▼                  ▼
┌───────────────────┐  ┌──────────┐
│partially_refunded │─►│ refunded │
└───────────────────┘  └──────────┘
                          terminal
```

### Решения

**Имена состояний берутся из пакета, а не из этого документа.** Здесь намеренно
сохранена британская орфография `cancelled` (двойная L) для заказов и сеансов и
американская `canceled` (одна L) для платежей — ровно как в
`nabilet_core_spec/migrations.sql` и `state-diagrams.md`. Это не опечатка, а
зафиксированный словарь: `orders.status` и `payments.status` перечисляются
CHECK-ограничениями `ck_orders_status` и `ck_payments_status`, поэтому расхождение
в одну букву теперь отклоняется базой.

**`expired` отделён от `cancelled`.** Cancelled = человек решил; expired = закрылось
10-минутное окно оплаты и hold'ы освобождены (ТЗ §84). Поддержке и аналитике эта разница нужна.

**`payment_failed` не терминальное.** Клиент с отклонённой картой должен иметь возможность оплатить другой картой: `payment_failed → awaiting_payment` законен. Без этого отклонённый платёж — ловушка для покупателя.

**Из `paid` нельзя в `cancelled` или `expired`.** Деньги взяты — законен только путь возврата.

**Guard на `partially_refunded → refunded`** требует, чтобы возвращённая сумма действительно равнялась сумме заказа. Без этого guard'а частичный возврат одного места из четырёх пометил бы весь заказ возвращённым и освободил три места, которые никто не возвращал. Тот же guard стоит на `paid → refunded`.

## 4. Payment (ТЗ §27, §28)

```
┌─────────┐    ┌──────────────────────┐
│ pending │───►│ waiting_for_capture  │
└────┬────┘    └──────────┬───────────┘
     │                    │
     ├────────────────────┴──────────────┐
     ▼                                   ▼
┌───────────┐                    ┌────────────┐  ┌──────────┐
│ succeeded │                    │  canceled  │  │  failed  │
└─────┬─────┘                    └────────────┘  └──────────┘
      │                             terminal       terminal
      ├──────────────┐
      ▼              ▼
┌───────────────────┐  ┌──────────┐
│partially_refunded │─►│ refunded │
└───────────────────┘  └──────────┘
```

Словарь взят из YooKassa (`pending`, `waiting_for_capture`, `succeeded`, `canceled`), но имена провайдер-нейтральны: второй провайдер **отображается на этот** словарь, а не наоборот.

`waiting_for_capture` существует потому, что двухстадийная оплата — норма для предзаказов и мероприятий с политикой отмены: деньги заморожены на карте, но не списаны до подтверждения организатором.

### Ключевое следствие для идемпотентности

`succeeded → succeeded` **запрещён**. Поэтому повторный вебхук вынуждает обработчик трактовать «уже в целевом состоянии» как успех, а не выполнять работу снова. Именно это даёт требование ТЗ §28: три вебхука → один оплаченный заказ, одна выдача билетов.

## 5. Refund (ТЗ §85)

```
┌───────────┐    ┌────────────┐    ┌───────────┐
│ requested │───►│ processing │───►│ succeeded │  terminal
└─────┬─────┘    └──────┬─────┘    └───────────┘
      │                 ▼
      │            ┌────────┐
      └───────────►│ failed │
                   └───┬────┘
                       │  (повтор при временной ошибке)
                       └──────► processing
```

`processing` как отдельное состояние — то, что не даёт сказать покупателю «возвращено» раньше, чем деньги действительно ушли. `failed → processing` позволяет повторить при временной ошибке провайдера, не создавая дублирующую заявку.

## 6. Ticket (ТЗ §29, §30, §32)

```
                ┌────────┐
                │ issued │
                └───┬────┘
     ┌──────────┬───┴────┬──────────┬───────────┐
     ▼          ▼        ▼          ▼           ▼
┌──────┐  ┌──────────┐ ┌────────┐ ┌─────────┐ ┌─────────┐
│ used │  │ refunded │ │canceled│ │ revoked │ │ expired │
└──┬───┘  └──────────┘ └────────┘ └─────────┘ └─────────┘
   │        terminal     terminal    terminal    terminal
   │
   └──────► revoked  (только так)
```

### Решения, определяющие поведение на входе

**Перехода `used → issued` нет намеренно.** «Отменить сканирование» сделало бы двойной проход возможным из-за ошибки оператора. Ошибка на входе решается через `revoked` + перевыпуск билета — с аудит-следом.

**Второе сканирование `used` — не ошибка.** API возвращает «уже использован» с исходным временем и устройством (ТЗ §32). Сканеру нужно показать оператору, что произошло, а не просто код отказа.

**`expired`** ставится job'ом после окончания сеанса, чтобы старые билеты нельзя было предъявить на другом мероприятии.

> **✅ `revoked` реализован (миграция `010_tz_gaps.sql`).** ТЗ §43 требует, чтобы Android
> Checker загружал список **отозванных** билетов, а §44 описывает конфликты
> офлайн-сканирования, которые разрешаются именно отзывом. Состояние добавлено в
> `tickets.status`, а ограничение `ck_tickets_status` расширено: база теперь принимает
> `issued / used / cancelled / refunded / expired / revoked` (проверено загрузкой DDL —
> 64 таблицы, 35 CHECK-ограничений).
>
> Семантика сохранена раздельной: `cancelled` — отмена с возвратом или по инициативе
> покупателя; `revoked` — мошенничество, чарджбэк, разбор дубля, часто **без** возврата.
> Поэтому `revoked` намеренно **не** включён в `ck_tickets_terminal_exclusive`: билет,
> пропущенный на входе и отозванный позже по чарджбэку, — законная и отчётная ситуация,
> в отличие от возврата после прохода.
>
> Для отзыва добавлены колонки `tickets.revoked_at` и `tickets.revoked_reason`.
> Подробнее — `REVIEW-spec-bundle.md` §3.10.

`TicketStateMachine::admissible()` = `['issued']` — единственный статус, который API принимает на входе.

## 7. InventoryItem (ТЗ §23)

```
  ┌───────────┐   вместимость исчерпана   ┌───────────┐
  │ available │ ────────────────────────► │ sold_out  │
  └─────┬─────┘ ◄──────────────────────── └─────┬─────┘
        │        вместимость вернулась         │
        │                                      │
        ├────────────┬─────────────┬───────────┤
        ▼            ▼             ▼           ▼
  ┌────────┐   ┌────────┐   ┌─────────┐  ┌──────────┐
  │  held  │   │  sold  │   │ blocked │  │ disabled │
  └────────┘   └────────┘   └─────────┘  └──────────┘
```

- `available → sold_out` и `held → sold_out` — вместимость исчерпана
  (`available_quantity = 0`). Для **места** это обычный путь, а не край: у места
  `capacity = 1`, поэтому первое добавление в корзину сразу обнуляет остаток и
  даёт `sold_out`. `held` достаётся стоячим зонам, где свободная вместимость
  ещё есть.
- `sold_out → available` и `sold_out → held` — вместимость вернулась: истёк
  hold, опустела корзина, отменён заказ.
- `sold_out → sold` — подтверждение оплаты.
  **Отсутствие этого перехода в машине было дефектом, а не пробелом в
  документации:** `PaymentService::markInventorySoldForOrder()` охраняет запись
  вызовом `can()`, поэтому `can('sold_out', 'sold')` возвращал `false` и
  ОПЛАЧЕННАЯ позиция навсегда оставалась `sold_out` — её не было ни в отчётности
  по `sold`, а `OrderService` сбрасывал её в `available` при отмене заказа так же
  охотно, как `held`. Воспроизведение и защита:
  `tests/Feature/Inventory/InventorySoldOnPaymentTest.php`.
- **`sold_out` ≠ `sold`.** Первое — «купить нельзя, но за это ничего не
  заплачено» (единицы лежат в корзинах); второе — «оплачено». Путать их значит
  считать выручкой брошенные корзины.
- `held → available` — истечение hold'а или явное освобождение.
- `held → sold` — подтверждение оплаты.
- `sold → available` — **только путь возврата**, никогда прямая запись статуса.
- `held → held` **запрещён** — второй hold на то же место отклоняется.
- `blocked` — коммерческое решение (служебные места, плохой обзор), обратимо.
- `disabled` — места для этого сеанса не существует.

`purchasable()` = `['available']`.

Словарь закреплён CHECK `ck_inventory_status` (сплит `014_inventory_status_check.sql`);
`tools/verify-state-machines.php` сверяет шесть состояний машины с ограничением
на каждом прогоне. `blocked` и `disabled` пока не пишет ни одна ветка приложения —
они объявлены для админского слоя и включены в ограничение намеренно: выкинуть
объявленное состояние — продуктовое решение, а не уборка.

## 8. SeatHold (ТЗ §24, §84)

```
┌────────┐
│ active │
└───┬────┘
    ├─────────────┬──────────────┐
    ▼             ▼              ▼
┌───────────┐ ┌─────────┐ ┌──────────┐
│ converted │ │ expired │ │ released │
└───────────┘ └─────────┘ └──────────┘
  все три терминальные
```

Три терминальных состояния не сведены в одно «закрыт», потому что у них разная аналитика и разные сообщения покупателю:

- `expired` → «время брони истекло»
- `released` → «вы убрали место»
- `converted` → нормальное завершение

`expired → converted` **запрещён**: истёкший hold никогда не должен превратиться в заказ.

## 9. Event и Session

### Event (ТЗ §12)

```
draft ──► scheduled ──► published ──► completed ──► archived
  │           │             │            │            (terminal)
  │           │             ├──► cancelled ──► archived
  │           │             └──► archived
  └──► published / archived
```

`archived` терминально: SEO-URL прошедших мероприятий должны оставаться разрешимыми через менеджер редиректов (ТЗ §37), а не отдавать 404.

`EventStateMachine::publiclyVisible()` = `['published', 'completed']`. Это единственный источник правды для каталога и sitemap: черновики исключаются по построению (ТЗ §38).

**Словарь закреплён CHECK `ck_events_status`** (сплит `015_events_status_check.sql`).
До него это была последняя колонка с PHP-машиной и без ограничения в схеме:
`tools/verify-state-machines.php` писал «machine is unenforced» на каждом прогоне.
Код и раньше был дисциплинирован — все авторы записей идут через `EventStatus` или
`Event::PUBLISHED`, — так что база лишь перестала молчать. Это важно не только ради
чистоты: `status` СОЗНАТЕЛЬНО отсутствует в `StoreEventRequest`/`UpdateEventRequest`
(иначе `PUT {"status":"published"}` публиковал событие без сеансов в обход
`EventPublicationPolicy`), и защитой от этого была одна деталь фреймворка — «правила
нет, значит `validated()` его выбросит». Теперь есть второй замок.
Написание `cancelled` (две L) больше не держится одним соглашением.

### Session (ТЗ §13)

```
draft ──► scheduled ──► on_sale ⇄ sold_out ──► closed ──► completed
  │           │            │           │                    (terminal)
  └───────────┴────────────┴───────────┴──► cancelled (terminal)
```

`on_sale ⇄ sold_out` двусторонний: сеанс может снова открыться, если истёк hold или вернули билет.

Состояние продаж намеренно отделено от **окна продаж** (`sales_start_at` / `sales_end_at`): окно — временной шлюз, `on_sale` — операционный переключатель, которым организатор останавливает продажи немедленно (погода, болезнь артиста), не трогая расписание.

`completed` и `cancelled` терминальны: состоявшийся сеанс нельзя «отсостоять», а его inventory — историческая запись.

**Словарь приведён к пакету.** §25 перечисляет семь значений — `draft`, `scheduled`,
`on_sale`, `sold_out`, `closed`, `completed`, `cancelled`. В сессии 1 этот документ
использовал `finished` вместо `completed` и не знал состояния `closed`. Значения
закреплены ограничением `ck_sessions_status`, поэтому расхождение теперь отклоняется базой.

## 10. Сводка переходов, критичных для денег и доверия

Эти девять правил покрыты тестами и не должны ослабляться:

| # | Правило | Что предотвращает |
|---|---|---|
| 1 | `Order: partially_refunded → refunded` требует полного возврата | Освобождение неоплаченных мест |
| 2 | `Payment: succeeded → succeeded` запрещён | Повторное выполнение побочных эффектов по вебхуку |
| 3 | `InventoryItem: held → held` запрещён | Двойная продажа места |
| 4 | `SeatHold: expired → converted` запрещён | Заказ из истёкшей брони |
| 5 | `Ticket: used → issued` отсутствует | Двойной проход из-за ошибки оператора |
| 6 | `Order: paid → cancelled` запрещён | Отмена оплаченного заказа в обход возврата |
| 7 | `Order: payment_failed → awaiting_payment` разрешён | Ловушка для покупателя с отклонённой картой |
| 8 | `Event: archived → published` запрещён | Воскрешение мероприятия в каталоге |
| 9 | `Session: finished → on_sale` запрещён | Продажа на прошедший показ |
