# NABILET Core

## Техническая спецификация разработки

### Версия 1.0

---

# 1. Назначение

**NABILET Core** — модульная монолитная система для публикации мероприятий, управления площадками и схемами залов, продажи билетов, обработки платежей, выпуска QR-билетов и контроля входа.

Основной бизнес-цикл:

```text
Organization
    ↓
Venue
    ↓
Hall
    ↓
Hall Schema
    ↓
Event
    ↓
Session
    ↓
Inventory
    ↓
Cart
    ↓
Order
    ↓
Payment
    ↓
Ticket
    ↓
QR
    ↓
Check-in
    ↓
Analytics
```

Система должна работать как самостоятельный сайт, а также предоставлять:

```text
REST API
Telegram Bot
Telegram Mini App
iframe Embed
n8n Webhooks
Android Checker
```

Главный архитектурный принцип:

> Один deployable application, одна БД, единое ядро, модульная внутренняя архитектура.

Микросервисы для MVP не используются.

Каждый модуль должен быть максимально автономным.

Пример:

```text
Modules/Payments/
├── Contracts/
├── Models/
├── Services/

├── Exceptions/
├── Jobs/
├── Events/
├── Listeners/

└── ServiceProvider.php
```

Модуль не должен напрямую менять внутренние классы другого модуля.

Разрешено взаимодействие через:

```text
Contracts
DTO
Events
Actions
Hooks
Services
```

Запрещено:

```text
прямое изменение чужой модели;
SQL из frontend;
обход business service;
доступ к чужой внутренней реализации.
```

# 6. Hook System

Система хуков должна быть аналогом WordPress actions/filters, но реализована поверх Laravel.

## Actions

```php
Hook::do('order.created', $order);
Hook::do('order.paid', $order);
Hook::do('ticket.issued', $ticket);
```

## Filters

```php
$price = Hook::filter(
    'ticket.price',
    $price,
    $ticket
);
```

Основные hooks:

```text

event.updated
```

Сторонний модуль должен иметь возможность подписаться на hook без изменения Core.

# 8. Public ID

Все основные сущности должны иметь:

```text
internal numeric id
public ULID
```

Например:

```text
id = 542

```

Во внешних URL и API используется `public_id`.

Внутренние foreign keys используют numeric IDs.

# 27. Почему Inventory является отдельной сущностью

Физическое место:

```text
Seat A-12
```

не равно продаваемому билету.

В одном сеансе:

```text
A-12 = 5000 ₽
```

в другом:

```text
A-12 = 7000 ₽
```

Поэтому:

```text
Seat
  ↓
InventoryItem
  ↓
Ticket
```

Это позволяет независимо управлять ценой и остатком.

# 36. YooKassa

При создании платежа использовать `Idempotence-Key`. ЮKassa рекомендует уникальный ключ операции и указывает V4 UUID как рекомендуемый вариант.

Webhook:

```text
POST /api/v1/webhooks/yookassa
```

Поддерживаемые события должны как минимум включать изменение статусов платежей, включая `payment.succeeded`.

ЮKassa предоставляет собственную OpenAPI-спецификацию, которая обновляется вместе с API, поэтому при реализации интеграции не следует вручную копировать устаревшие контракты.

# 42. Онлайн check-in

```text
POST /api/v1/checkin/validate
```

Сначала выполняется read-only проверка.

Затем:

```text
POST /api/v1/checkin/use
```

Вторая операция должна выполняться транзакционно:

```text
BEGIN

SELECT ticket
FOR UPDATE

if status != issued
    reject

status = used
used_at = NOW()

create scan

COMMIT
```

Это исключает двойной проход одного билета при конкурентном сканировании.

# 44. Конфликты Offline Check-in

Ситуация:

```text
Checker A → Ticket 100 → valid
Checker B → Ticket 100 → valid
```

до синхронизации не может быть гарантированно обнаружена вторым устройством.

После синхронизации сервер определяет:

```text
first accepted scan
duplicate scan
```

В админке появляется:

```text
OFFLINE CONFLICT
```

с указанием устройств и времени.

# 132. Coding Rules для AI-кодера

AI-разработчик должен:

```text

не создавать две одинаковые функции под разными названиями;

не оставлять fake implementation;
не менять API контракт без обновления OpenAPI;
не изменять database schema без migration;
не обходить service layer;
не хранить secrets в коде.
```

Перед созданием нового класса AI обязан искать:

```text

существующий service;
существующий DTO;
```

# 143. Главные архитектурные инварианты

### Invariant 1

Одно физическое место не может иметь два активных paid tickets для одного Session.

### Invariant 2

Оплата не может привести к созданию двух комплектов билетов.

### Invariant 3

Один ticket может перейти в `used` только один раз.

### Invariant 4

Published Hall Schema immutable.

### Invariant 5

Frontend никогда не является источником истины о наличии места.

### Invariant 6

Цена из frontend не считается доверенной.

### Invariant 7

Payment success устанавливается сервером.

### Invariant 8

QR не содержит персональные данные.

### Invariant 9

Все critical POST операции идемпотентны.

### Invariant 10

Все административные изменения критичных сущностей попадают в Audit Log.

# 151. Итог

Архитектурно **NABILET Core** должен быть не «сайтом продажи билетов», а платформенным ядром с четырьмя центральными подсистемами:

```text
CMS
Commerce
Ticketing
Check-in
```

При этом критически важная модель:

```text
Hall
 ↓
HallSchema
 ↓
Session
 ↓
Inventory
 ↓
Order
 ↓
Ticket
```

является основой всего продукта.

Особое внимание при реализации требуется уделить трем зонам:

```text
1. конкурентное резервирование Inventory;
2. идемпотентная обработка Payment/Webhooks;
3. атомарный Check-in.
```

Именно эти три механизма определяют надежность всей билетной платформы.
