# Модуль Matrix — административная лента уведомлений

Канал уведомлений в комнату Matrix (клиент Element X), работающий через
Client-Server API удалённого Synapse.

> **Адресат — только сотрудники.** Сообщения уходят в одну настроенную комнату,
> которую читают администраторы магазина. Покупателю Matrix-канал не отправляет
> ничего: привязки «покупатель ↔ Matrix ID» в схеме нет и не заводится, личных
> сообщений нет, входящего бота (webhook от Synapse) нет. Это внутренняя лента
> продаж, а не канал обслуживания клиента — для писем покупателю существует
> модуль `Notifications` (SMTP).

Модуль **не меняет схему БД**: счётчики (таблицы / колонки / FK / UNIQUE /
CHECK) остаются прежними, новых сплитов миграций нет. Настройки лежат в уже
существующей таблице `settings` (scope=`matrix`).

## 1. Что делает модуль

| Возможность | Статус |
|---|---|
| Уведомление в комнату об оплаченном заказе | ✅ |
| Тестовое сообщение из админки («Проверить») | ✅ |
| Правка настроек из админки без доступа к `.env` | ✅ |
| Токен Synapse шифруется в БД и не возвращается наружу | ✅ |
| Повтор отправки при сетевом сбое (3 попытки) | ✅ |
| Личные сообщения покупателям | ❌ намеренно |
| Входящие сообщения из Matrix (бот-приёмник) | ❌ намеренно |
| Форматирование HTML (`org.matrix.custom.html`) | ❌ намеренно, см. §7 |
| Схема БД под Matrix | ❌ не требуется |

## 2. Поток «заказ оплачен»

```
Order::status → paid
        │
        ▼
OrderMatrixObserver::updated()          ← 6-й наблюдатель на Order
   ├─ wasChanged('status')?             ← иначе повторный markPaid() дал бы второе сообщение
   ├─ status === OrderStateMachine::PAID?
   ├─ MatrixSettings::isEnabled() && notifyOrders()?
   └─ MatrixSettings::isConfigured()?   ← без этого в очередь копились бы заведомо падающие задачи
        │
        ▼
MatrixNotice::orderPaid([...])          ← чистый текст, Domain/
        │
        ▼
SendMatrixMessageJob::dispatch($body)
        ->onConnection('database')->afterCommit()
        │
        ▼
MatrixClient::send()
   PUT {homeserver}/_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId}
   Authorization: Bearer <access_token>
   {"msgtype":"m.text","body":"…"}
```

**Почему наблюдатель, а не вызов из сценария оплаты.** Заказ становится `paid`
из нескольких мест (`OrderService::markPaid()`, подтверждение платежа, админские
сценарии). Уведомление привязано к *событию* «заказ оплачен», а не к пути, которым
оно наступило, — иначе один путь уведомлял бы, а остальные нет. Тот же приём, что
у `OrderBonusObserver`, `OrderLoyaltyObserver`, `OrderReferralObserver` и
`OrderRaffleObserver`; Laravel вызывает все наблюдатели модели.

**Почему `afterCommit()` и очередь.** Наблюдатель срабатывает *внутри*
транзакции, записывающей статус заказа. Сетевой вызов оттуда держал бы транзакцию
открытой до 10 секунд, а падение Synapse откатило бы оплату — «уведомление не
ушло» превращалось бы в «деньги не приняты». Задача ставится с `afterCommit()`,
уходит только после фиксации заказа, и её провал платёж не трогает.

**Почему тело готовится заранее.** В задачу передаётся уже собранная строка, а не
модель `Order`: задача не сериализует Eloquent (и не зависит от состояния БД на
момент выполнения), а текст можно проверить в наблюдателе, не поднимая очередь.

### Как выглядит сообщение

```
Новый оплаченный заказ
Номер: NBL-2026-000123
Сумма: 1 500,00 ₽
Мероприятие: Тестовое событие
Покупатель: Иван Петров
```

Строки «Мероприятие» и «Покупатель» опускаются, если значение пустое. Сумма
форматируется единственным форматтером проекта — `Nabilet\Core\Support\Money`
(тот же вид, что в чеках и письмах; пустая валюта трактуется как `RUB`).

## 3. Как включить

Нужны три значения: адрес homeserver, идентификатор комнаты и токен доступа.
Задать их можно двумя способами — оба эквивалентны, значения из БД перекрывают
`.env`.

### 3.1 Через админку (рекомендуется)

**Настройки → Matrix (Element X)** (`/admin/matrix`, страница
`AdminMatrixSettingsPage.vue`). Токен вводится в поле, но никогда не показывается
обратно: форма получает только признак «задан». Кнопка **«Проверить»** отправляет
тестовое сообщение и показывает ответ Synapse в тексте ошибки.

### 3.2 Через `.env`

```dotenv
NABILET_MATRIX_HOMESERVER_URL=https://matrix.example.org
NABILET_MATRIX_ROOM_ID=!abcdefghijklmnop:matrix.example.org
NABILET_MATRIX_ACCESS_TOKEN=syt_…
NABILET_MATRIX_ENABLED=true
NABILET_MATRIX_NOTIFY_ORDERS=true
```

Полный блок с комментариями — в `.env.example`. Для наблюдаемости значения
видны в `php artisan config:show nabilet.matrix` (провайдер применяет настройки
из БД к runtime-конфигу на бутстрапе).

### 3.3 Где взять `room_id` и `access_token` в Element X

* **room_id** — Настройки комнаты → Дополнительно → «Внутренний ID». Он начинается
  с `!` и выглядит как `!AbCdEf…:matrix.example.org`. **Это не алиас** `#name:server`:
  Synapse принимает алиас в пути Client-Server API только после резолвинга через
  `/directory/room/{alias}`, поэтому `PUT /rooms/#name:server/send/…` вернёт 404
  «Unknown room». Форма предупредит об этом до сохранения (§5).
* **access_token** — токен аккаунта бота. Проще всего получить входом:

  ```bash
  curl -s -XPOST https://matrix.example.org/_matrix/client/v3/login \
    -H 'Content-Type: application/json' \
    -d '{"type":"m.login.password","identifier":{"type":"m.id.user","user":"nabilet-bot"},
         "password":"…"}' | grep -o '"access_token":"[^"]*"'
  ```

  Учтите: токен даёт полный доступ к аккаунту бота и **не отзывается вместе с
  сессией администратора** — см. §7.

> **Шифрование комнаты.** Рекомендуется использовать для этого канала
> **нешифрованную** комнату (или отдельную комнату для бота). Сервер отправляет
> `m.text` без E2EE; в зашифрованной комнате Element X покажет такое сообщение с
> предупреждением «не зашифровано». Скрытно подмешивать шифрование модуль не
> умеет и не должен — это отдельная (olm/megolm) инфраструктура.

## 4. Настройки

Таблица `settings`, `scope = 'matrix'`. Механика та же, что у `MailSettings`
(scope=`mail`) и `PaymentSettings` (scope=`payment`): значение из БД перекрывает
`.env`, а ключ, которого в таблице нет, конфиг не трогает — поведение свежей
установки ровно как было.

| Ключ | Тип | Секрет | `.env`-фолбэк |
|---|---|---|---|
| `homeserver_url` | строка | — | `NABILET_MATRIX_HOMESERVER_URL` |
| `room_id` | строка | — | `NABILET_MATRIX_ROOM_ID` |
| `access_token` | строка | ✅ шифруется | `NABILET_MATRIX_ACCESS_TOKEN` |
| `enabled` | bool | — | `NABILET_MATRIX_ENABLED` (по умолчанию `false`) |
| `notify_orders` | bool | — | `NABILET_MATRIX_NOTIFY_ORDERS` (по умолчанию `true`) |

### Семантика сохранения — почему у секрета правило обратное

| Что пришло в `PUT` | Несекретный ключ (`homeserver_url`, `room_id`) | Секрет (`access_token`) |
|---|---|---|
| не пришёл вовсе | не меняется | не меняется |
| `null` (пустое поле формы) | **стереть** → снова значение из `.env` | **не менять** |
| непустая строка | записать | записать зашифрованным |
| `clear_access_token: true` | — | **стереть** |

Причина расхождения — `ConvertEmptyStringsToNull` в Laravel: пустое поле формы
превращается в `null` ещё до валидации. Если трактовать `null` как «не менять»,
очистить адрес или комнату из формы стало бы **невозможно** (администратор
стирает поле, сохраняет и видит прежнее значение). У токена правило обратное,
потому что форма не присылает токен никогда — он не отдаётся наружу, — и «пусто»
здесь означает «оставить как есть»; стереть можно только явным флагом.
Тот же выбор сделан в `MailSettings` для пароля SMTP.

`enabled` выключает канал целиком (ни одна задача не ставится), `notify_orders`
выключает только уведомления о заказах, оставляя рабочей кнопку «Проверить».

## 5. HTTP API

Все три пути — под `auth:api` + `admin` (покупателю здесь делать нечего, а токен
даёт полный доступ к аккаунту бота). Префикс `/api/v1` даёт `routes/api.php` —
провайдер маршруты не грузит (`tools/verify-route-ownership.php`).

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/v1/admin/matrix/settings` | `{"data": {…}}` — настройки без секретов |
| `PUT` | `/api/v1/admin/matrix/settings` | `{"data": {…}}` — те же поля после сохранения |
| `POST` | `/api/v1/admin/matrix/test` | `{"data": {"ok": bool, "error": ?string}}` |

`GET`/`PUT` возвращают:

```json
{
  "data": {
    "homeserver_url": "https://matrix.example.org",
    "homeserver_url_from_env": false,
    "room_id": "!abcdefghijklmnop:matrix.example.org",
    "room_id_from_env": false,
    "access_token_set": true,
    "enabled": true,
    "enabled_from_env": false,
    "notify_orders": true,
    "notify_orders_from_env": false,
    "configured": true
  }
}
```

`*_from_env` — признак «значение пришло из `.env`, в таблице записи нет»: форма
показывает его бейджем, чтобы владелец понимал, что он правит. `configured` —
заполнены ли все три обязательных значения (адрес, комната, токен); это то, что
транспорт реально использует сейчас. **Токен наружу не уходит** — только
`access_token_set`.

`PUT` принимает `homeserver_url`, `room_id`, `access_token`, `enabled`,
`notify_orders` (все `sometimes`) и `clear_access_token`. Формат адреса и комнаты
проверяется доменными правилами, а не только `string|max:255`, — потому что
админка не единственный вход в API, тот же `PUT` можно послать curl'ом. Неверный
формат даёт **422** с `error.details.fields`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "…",
    "details": {
      "fields": {
        "room_id": ["Нужен идентификатор комнаты вида !room:server, а не алиас #name:server. Скопируйте ID комнаты из Element X."]
      }
    }
  }
}
```

`POST /test` отвечает **200 и `ok: false`**, а не 4xx/5xx: неверный токен или
алиас вместо ID комнаты при настройке — ожидаемый результат, и админке нужен
текст ошибки, а не голый код. Тот же приём, что у тестового письма SMTP
(`MailSettingsController::sendTest`).

> Эти три пути **не входят в OpenAPI** (`docs/openapi.yaml` /
> `nabilet_core_spec/openapi.yaml`). Это осознанно: контракт описывает
> интеграционную поверхность, и ни один другой раздел настроек
> (`/admin/mail/settings`, `/admin/payments/settings`, `/admin/loyalty/settings`)
> в него не входит — добавлять только Matrix значило бы создать расхождение.

## 6. Транспорт и обработка ошибок

`MatrixClient` (`app/Modules/Matrix/Services/MatrixClient.php`):

* **`PUT`, а не `POST`** — отправка в Matrix идемпотентна по построению:
  `PUT /_matrix/client/v3/rooms/{roomId}/send/{eventType}/{txnId}`, где `txnId` —
  идентификатор транзакции от клиента. Повтор с тем же `txnId` не создаёт второе
  сообщение, а возвращает результат первой попытки. Это ровно то, что нужно
  задаче с ретраями: если ответ Synapse потерялся в сети, повтор **не**
  задублирует уведомление в комнате. `POST` такой гарантии не даёт.
* **Токен — заголовок, а не параметр.** Synapse принимает и `?access_token=`, но
  параметры URL попадают в логи прокси, историю и `Referer`.
  `Authorization: Bearer` (`Http::withToken`) — единственная форма, которая не
  утекает в логи промежуточных узлов.
* **Комната кодируется** (`rawurlencode`): идентификатор начинается с `!` и
  содержит `:` — в пути URL это недопустимые символы.
* **Таймаут 10 с**, тело чужого ответа обрезается до 300 символов — оно идёт в
  текст ошибки для админки, целиком не нужно.

Ошибки — доменные (`DomainRuleViolation`, HTTP 422 в конверте §66), чтобы
администратор различал исходы в тест-отправке:

| `code` | Когда |
|---|---|
| `MATRIX_NOT_CONFIGURED` | не задан адрес, комната или токен |
| `MATRIX_INVALID_ROOM` | комната не вида `!room:server` (например, алиас `#name:…`) |
| `MATRIX_SEND_FAILED` | Synapse ответил не-2xx (в тексте — код и начало тела) |

Задача `SendMatrixMessageJob`: `tries = 3`, `backoff = [10, 30, 60]`. Отказ
Synapse обычно временный (перезапуск, сеть), и три попытки переживают короткий
сбой, но не превращаются в бесконечный ретрай навсегда неверной настройки —
неверная настройка отсекается в наблюдателе до постановки задачи.

## 7. Безопасность

| Риск | Решение |
|---|---|
| Утечка токена Synapse через DevTools админки | В БД `encrypted = 1` (`Crypt`), наружу — только `access_token_set`. Токен даёт полный доступ к аккаунту бота и не отзывается вместе с сессией администратора, поэтому утечка была бы долгой |
| SSRF через адрес homeserver | `MatrixHomeserver` допускает только схемы `http`/`https`; `file://` (локальное чтение файла) и `ftp://` отвергаются. Адрес без схемы дополняется до `https://` — «случайный» `http` означал бы токен в открытом виде |
| Алиас вместо ID комнаты → 404 без объяснения | `MatrixRoomId` требует вид `!opaque:server` и отсекает `#name:server` на входе |
| Инъекция разметки в чужой клиент | Отправляется только `m.text`; HTML не используется, потому что содержимое приходит из данных заказа (частично пользовательский ввод) |
| Управляющие символы из БД («квадратики» в Element X, сломанные переносы) | `MatrixMessage::sanitize()` вырезает `\x00-\x08\x0B\x0C\x0E-\x1F\x7F`, нормализует CRLF/CR → LF. Чистка на выходе, а не при сохранении: чужие данные портить нельзя |
| Аномально длинное поле | Потолок `MAX_BODY_LENGTH = 4000` символов, усечение по символам UTF-8 (не по байтам), с многоточием |
| Нечитаемый шифротекст (сменился `APP_KEY`) | Трактуется как «токен не задан», запрос не падает — владелец введёт токен заново |
| Падение на свежей установке (таблицы `settings` ещё нет) | Чтение настроек в `try/catch` — модуль не мешает даже логину |
| Доступ покупателя | Весь раздел под `auth:api` + `admin`; в модуле нет ни одного пути, читающего чужой id |

## 10. Что намеренно не сделано

* **Личные сообщения покупателям.** Ни схемы привязки, ни отправки. Для писем
  покупателю — модуль `Notifications`.
* **Входящий бот (webhook от Synapse).** Команды в комнате не принимаются:
  канал односторонний, и это убирает целый класс рисков (аутентификация
  вебхука, права на команды).
* **HTML-форматирование.** См. §7 — содержимое частично из пользовательского
  ввода.
* **E2EE.** Не поддерживается; см. врезку в §3.3.
