# Отчёт об аудите производительности и устойчивости Nabilet

**Статус:** Статический анализ кода, миграций и конфигурации. Нагрузочные тесты на production не проводились, фактические метрики (RPS, p95) отсутствуют — указаны методы измерения для верификации рисков.
**Дата анализа:** 10 октября 2026 г.

## 1. Критические риски и доказательства в коде

### 1.1. Отсутствие кеша публичных данных (P0)
*   **Проблема:** Прикладной кеш полностью отсутствует (`CACHE_STORE=database`). Каждый запрос к каталогу или странице события выполняет полный набор SQL-запросов (events, sessions, venues, organizations).
*   **Доказательство:** `EventPageController::show()` и `StorefrontController::show()` не используют `Cache::`. В nginx нет настроек микрокеша для динамики.
*   **Влияние:** Волна трафика при старте продаж напрямую нагружает MySQL и PHP-FPM, вызывая деградацию времени ответа и риск отказа БД.
*   **Метод измерения:** Сравнение QPS к MySQL до/после внедрения `Cache::remember` для статической части ответов; лог hit-ratio.

### 1.2. N+1 запросы и тяжелые выборки (P0/P1)
*   **Проблема:** Неоптимальная загрузка данных в горячих путях.
    *   `EventRepository::paginate()`: Жадно грузит все позиции инвентаря всех сеансов для списка событий (десятки тысяч строк на страницу).
    *   `EventController::showBySlug()`: Подсчет доступных мест выполняется в PHP после загрузки всего инвентаря сеанса.
    *   `TicketService::issueTicketsForOrder()`: Классический N+1 (`find` внутри цикла) при выпуске билетов.
*   **Доказательство:** Код в `app/Modules/Events/Repositories/EventRepository.php`, `InventoryController.php`.
*   **Влияние:** Раздувание памяти PHP, высокая нагрузка на CPU и IO БД именно в момент пикового спроса.
*   **Метод измерения:** Анализ `DB::enableQueryLog()` на эндпоинтах `/api/v1/events` и `/event/{slug}`; замер `memory_get_peak_usage`.

### 1.3. Конкурентное бронирование и блокировки (P1)
*   **Проблема:** Риски взаимных блокировок (deadlocks) и длительных транзакций.
    *   Разный порядок захвата локов между `CartItemService` (сначала inventory, потом cart) и `CartCheckoutService` (сначала cart, потом inventory).
    *   Длительная транзакция в вебхуке оплаты: выпуск билетов и обновление цен происходят синхронно внутри `DB::transaction` вместе с сетевыми вызовами провайдера.
*   **Доказательство:** `CartItemService.php`, `PaymentService::processWebhook()`.
*   **Влияние:** Ошибки 500/409 при массовом оформлении, блокировка продажи мест во время обработки платежей.
*   **Метод измерения:** Мониторинг `innodb_lock_waits` и счетчика deadlocks; замер времени жизни транзакций в `information_schema.innodb_trx`.

### 1.4. Внешние сервисы и таймауты (P0)
*   **Проблема:** HTTP-вызовы к платежному шлюзу выполняются без явных таймаутов и retry-политик, часто внутри транзакций БД.
*   **Доказательство:** `YooKassaProvider` использует `Http::post` без `timeout`; `PaymentService::initiatePayment` вызывает провайдера внутри `DB::transaction`.
*   **Влияние:** Зависший внешний сервис приводит к удержанию блокировок в БД и исчерпанию пула PHP-FPM воркеров.
*   **Метод измерения:** Chaos-тест с искусственной задержкой ответа провайдера; наблюдение за ростом очередей fastcgi.

### 1.5. Индексы и пагинация (P1)
*   **Проблема:**
    *   Отсутствие индексов для фильтров каталога (`is_featured`, сортировка по дате сеанса).
    *   Нет ограничения на `per_page` в API каталога (риск DoS через запрос с `per_page=100000`).
    *   `HoldSweeper` удаляет просроченные холды одним запросом без `LIMIT`, что может вызвать гигантскую транзакцию после простоя cron.
*   **Доказательство:** `EventRepository.php`, `ListEventsRequest` (не применяется в контроллере), `HoldSweeper.php`.
*   **Влияние:** Полное сканирование таблиц, нестабильная пагинация, блокировки инвентаря при очистке холдов.
*   **Метод измерения:** `EXPLAIN` типовых запросов; проверка наличия `ORDER BY` и лимитов; моделирование накопления 10k+ просроченных холдов.

### 1.6. Очереди и наблюдаемость (P2)
*   **Проблема:**
    *   Нет подтвержденной работы Queue Worker в проде (риск накопления задач в таблице `jobs`).
    *   Отсутствие метрик Prometheus/APM и алертинга на глубину очереди или ошибки приложений.
    *   Логирование есть (request_id), но нет агрегации и slow-query логов MySQL.
*   **Влияние:** Невозможность оперативно диагностировать причины сбоев под нагрузкой.
*   **Метод измерения:** Проверка статуса worker'ов; наличие экспортеров метрик; настройка `long_query_time`.

## 2. План нагрузочного тестирования (Staging Only)

> **Важно:** Тесты проводятся только на изолированном стенде с данными, близкими к продакшену (≥10k событий, ≥50k мест). Production не затрагивается.

### Инструменты
*   k6 / Gatling для генерации нагрузки.
*   Сбор метрик: nginx access logs, `performance_schema` MySQL, глубина очереди `jobs`.

### Сценарии

| ID | Сценарий | Модель нагрузки | Цели проверки |
| :--- | :--- | :--- | :--- |
| **S1** | Просмотр каталога | 200→1000 VU, steady state. Смесь GET запросов. | Выявить влияние отсутствия кеша и тяжелых eager-load запросов (R1.1). |
| **S2** | Flash Crowd (Открытие события) | Резкий скачок 0→3000 VU за 30 сек на страницу популярного мероприятия. | Измерить стоимость загрузки полной карты мест (R1.2); найти первый узел (CPU/DB/Network). |
| **S3** | Массовый выбор мест | 500 VU одновременно бронируют топ-50 популярных мест + случайные места. | Детектировать deadlocks (R6.2), конкуренцию за строки инвентаря, корректность идемпотентности холдов. |
| **S4** | Пик оформления заказов | 300 VU непрерывно оформляют корзины (checkout) и инициируют платежи. | Проверить поведение при медленном ответе платежного шлюза (R7.5); целостность данных при высокой конкуренции. |
| **S5** | Шторм вебхуков | Эмуляция 200–1000 callback/сек от провайдера оплаты (включая replay атак). | Замерить latency вебхука (R7.1); проверить отсутствие двойных выпусков билетов; восстановление после падения queue worker. |

## 3. Критерии приёмки (Pass/Fail)

Критерии устанавливаются командой после калибровочного прогона baseline, но включают следующие обязательные условия:

1.  **Целостность данных (Жёсткие требования):**
    *   Инвариант инвентаря: `sold + held ≤ capacity` всегда соблюдается.
    *   Отсутствие дубликатов билетов и транзакций при повторных вебхуках.
    *   Все released-холды корректно возвращают места в `available_quantity`.
2.  **Производительность (Относительно baseline):**
    *   Время ответа API (p95) не превышает согласованный SLA (например, <500ms для чтения).
    *   Доля ошибок 5xx < 0.1%.
    *   Количество deadlocks = 0 (или < 0.05% с корректным обработчиком 409 Conflict).
3.  **Устойчивость ресурсов:**
    *   Пул PHP-FPM не исчерпан (нет отказов в обслуживании из-за нехватки воркеров).
    *   Очередь задач (`jobs`) очищается за разумное время (<15 мин) после окончания пиковой нагрузки.
    *   CPU и Memory базы данных находятся в безопасных пределах.
4.  **Диагностируемость:**
    *   По `request_id` можно восстановить полную цепочку действий пользователя (запрос → заказ → платеж → билет → письмо) в логах.

## 4. Рекомендации по исправлению (Приоритизация)

1.  **P0 (Немедленно):**
    *   Внедрить Rate Limiting (`throttle`) на публичные маршруты.
    *   Ввести кеш Redis для неизменяемой части публичных страниц (SEO shell, справочники).
    *   Добавить явные таймауты и circuit breaker для HTTP-клиента платежного провайдера.
    *   Вынести сетевые вызовы провайдера из транзакций БД.
2.  **P1 (Перед крупными продажами):**
    *   Оптимизировать запросы каталога: убрать eager-load инвентаря, использовать агрегатные функции (COUNT/SUM) вместо загрузки строк.
    *   Валидировать `per_page` (максимум 100) и добавить стабильную сортировку.
    *   Унифицировать порядок захвата блокировок (locks) в сервисах корзины и заказа для предотвращения deadlocks.
    *   Модифицировать `HoldSweeper` для пакетной обработки (batch with LIMIT).
3.  **P2 (Среднесрочно):**
    *   Перенести генерацию билетов и отправку писем в фоновые задачи (Queue) из синхронного обработчика вебхука.
    *   Настроить мониторинг (Prometheus/Grafana) и алертинг на глубину очереди, ошибки 5xx и медленные запросы.
    *   Настроить CDN/Cache-Control заголовки для статики и изображений залов.
