# NABILET — инженерный гайд по качеству кода

> Этот документ написан по итогам разбора реальных дефектов витрины (поток выбора
> мест → корзина → оформление → оплата). Здесь нет общих советов: каждый раздел
> начинается с бага, который действительно был в коде, и заканчивается правилом,
> которое этот класс багов закрывает.
>
> Смежные документы: [`ARCHITECTURE.md`](ARCHITECTURE.md) ·
> [`TESTING_GUIDE.md`](TESTING_GUIDE.md) · [`openapi.yaml`](openapi.yaml)

## 1. Главная болезнь этого проекта: расхождение контрактов между слоями

Девять из одиннадцати найденных дефектов — не «ошибки в логике», а **рассогласование
двух слоёв, каждый из которых по отдельности прав**. Такие баги не воспроизводятся
чтением одного файла: нужно держать в голове обе стороны стыка.

### 1.1. Пространства идентификаторов

**Что было.** В системе три разных «id» для одной сущности:

| Значение | Что это | Кто его ждёт |
|----------|---------|--------------|
| `inventory_items.id` | числовой PK | `POST /cart/items` (`inventory_item_id`) |
| `inventory_items.public_id` | ULID | `CartItemResource.inventory_item.id` |
| `cart_items.id` | числовой PK | `DELETE /cart/items/{id}` |

Фронтенд хранил `cart.meta[seatId] = inventoryId`. Всё работало, пока место было
выбрано в текущей сессии: `POST /cart/items` возвращает `data.id` — это уже
`cart_items.id`, и он сохранялся правильно. Но после перезагрузки страницы корзина
восстанавливалась из `GET /cart`, и там `cart.meta` заполнялся **id инвентаря**.
Результат: `DELETE /cart/items/26` → `404 CART_ITEM_NOT_FOUND`. Покупатель нажимал
«убрать место», получал зелёное уведомление, а место оставалось удержанным за ним.

**Правило.** Любой идентификатор, который уходит в URL или в тело запроса, должен
иметь в коде **имя, содержащее его тип**: `cartItemId`, `inventoryItemId`,
`inventoryPublicId`. Переменная `id` без уточнения на стыке слоёв — запрещена.
Если тип неясен из имени, следующий разработчик повторит эту ошибку.

**Как проверять.** В `lib/inventory.ts` тип поля документирован комментарием:
`/** cart_items.id — именно этот id ждёт DELETE /cart/items/{id}. */`. Такие
комментарии — не украшение, а защита: они превращают догадку в контракт.

### 1.2. Конверт ошибок

**Что было.** Сервер отдаёт §66-конверт:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "…",
             "request_id": "…", "details": { "fields": { "quantity": ["…не больше 10"] } } } }
```

`lib/api.ts` в функции `request()` читал `error.errors` — поля, которого сервер не
отправляет. `ApiError.details` всегда был `null`, поэтому серверные ошибки валидации
**никогда** не привязывались к инпутам: на оформлении покупатель видел общую плашку
«Оплата не началась» вместо «Нужен e-mail — на него придёт билет».

Отдельная пикантность: функция `upload()` в том же файле читала **правильный** путь
`details.fields`. То есть в проекте одновременно существовали две реализации одного
парсинга, и они разошлись.

**Правило.** Разбор ответа сервера — **одна функция на весь проект**. Дублирование
парсинга конверта и есть корневая причина; сам путь `details.fields` — лишь симптом.
Если два места читают один формат — они разойдутся, вопрос только когда.

**Что сделано.** `extractFieldErrors()` / `extractErrorMeta()` — единственный парсер;
`request()` и `upload()` вызывают его. Канонический путь — `error.details.fields`;
дополнительно принимаются плоский `error.details` и legacy `error.errors`, чтобы
правка не сломала существующих потребителей.

### 1.3. Выбор ветки по статусу вместо кода

**Что было.** `CART_EXPIRED` — это `ConflictError`, то есть **HTTP 409** — тот же
статус, что у `SEAT_UNAVAILABLE`. Обработчик проверял `status === 409` раньше кода,
поэтому «корзина протухла, освежите схему» показывалось как «место занял другой
покупатель». Пользователь шёл выбирать другое место вместо перезагрузки — и получал
ту же ошибку снова.

**Правило.** Ветвление — по `error.code` (машинный код), а не по `status`.
HTTP-статус — грубая категория; он не различает два разных сценария восстановления.
Если статус и код противоречат друг другу — прав код.

## 2. Вторая болезнь: формула, продублированная в трёх местах

### 2.1. «Позиция» и «билет» — разные числа

**Что было.** В корзине одна позиция может содержать N билетов: стоячая зона
(танцпол) с `quantity = 3`. Сводка заказа считала билеты как `seats.length`, а цену
строки — как `seat.priceMinor`. Для танцпола qty=3 это давало «1 билет» и цену одного
билета. Итог на экране не совпадал с `orders.total_amount` на чеке — прямое нарушение
инварианта 6 («цена — только с сервера»).

**Правило.** Бизнес-формула живёт в **одном** месте. Если одна и та же арифметика
встречается в двух компонентах — это не «немного дублирования», это будущее
расхождение.

**Что сделано.** В `stores/cart.ts` появились чистые функции — единственный источник
истины о количестве:

```ts
export function seatQuantity(seat)      // билетов в позиции
export function seatLineTotal(seat)     // стоимость позиции с учётом количества
export function seatsTicketCount(seats) // билетов в наборе позиций
export function seatLineLabel(seat)     // «Партер, ряд 3, место 12» / «Танцпол · 3 билета»
```

Компоненты (`OrderSummary`, `CheckoutPage`, `StorefrontShell`) их вызывают и больше
не считают сами. `cart.count` (позиции) и `cart.ticketsCount` (билеты) — **разные**
computed, и в интерфейсе сознательно используется нужный из них.

### 2.2. Число, продублированное в трёх местах

**Что было.** Лимит «10 билетов на заказ» был продублирован: дефолт `SeatMap`, проп
`:max-selection` на странице, текст уведомления. Плюс `5` — максимум пикера танцпола.
При правке одного места остальные расходились: кнопка не нажимается, а сообщение
говорит про другое число.

**Правило.** Магическое число, влияющее на поведение, экспортируется один раз.
Источник истины — сервер; константа на клиенте должна быть помечена как отражение
серверного правила:

```ts
/** Источник истины — сервер (CartController::addItem: quantity max:10). */
export const MAX_TICKETS_PER_ORDER = 10
```

## 3. Третья болезнь: проверка, которая «есть, но не работает»

Это самый коварный класс: код выглядит завершённым, но не делает ничего.

| Симптом в коде | Реальность |
|----------------|------------|
| Проп `maxQuantity` объявлен и передан | Нигде не читается — лимит не работает |
| `defineEmits<{ limit: [] }>` объявлен | Событие никогда не эмитится |
| `const ticketsCount = computed(...)` | Не возвращён из стора — недостижим |
| `const danceSelected = ref(false)` | Не синхронизирован с пропсом `selected` |
| `headers: options.body === undefined ? headers : headers` | Тернарник с одинаковыми ветвями |
| `isset($request->session_id)` | Пропускает пустую строку → фильтр не применяется |

**Что было.** `CoordSeatMap` принимал `maxQuantity`, но не использовал его; `@limit`
был объявлен, но не эмитился. Покупатель выбирал 11-е место, запрос уходил на сервер
и возвращался `422 VALIDATION_ERROR` с техническим текстом вместо понятного
«не больше 10 билетов».

**Правило.** Объявленный, но неиспользуемый параметр — **дефект**, а не задел на
будущее. Если проп нужен для контракта, но пока не читается, это отмечается
комментарием; иначе он будет удалён «как мусор» ровно тогда, когда понадобится.

**Как ловить.** Мёртвый код и «висящие» пропсы видит линтер (`noUnusedLocals`),
но неиспользуемый **проп** линтер не видит. Здесь работает только ревью: у каждого
пропса должен быть читатель, у каждого `emit` — эмиттер.

### 3.1. Мёртвая ручка конфигурации — худшая версия того же

Этот подкласс дороже всего, потому что жертва — **оператор, а не разработчик**.
Он меняет настройку в `.env`, получает «сохранено», и ничего не происходит. Отказ
молчаливый: ни ошибки, ни предупреждения.

**Что было.** «Anti-scalping guard» существовал в трёх объявлениях, и работало
ни одно:

| Объявление | Значение | Кто читал |
|---|---|---|
| `NABILET_MAX_SEATS_PER_ORDER` в `.env` и `.env.example` | 8 | никто |
| `nabilet.checkout.max_items_per_order` (`CHECKOUT_MAX_ITEMS`) | 10 | никто — ключ конфига не читался |
| `max:10` литералом в `CartController::addItem` | 10 | **только это и работало** |

Оператор считал, что лимит равен восьми. Фактически было десять. Настроить было
нельзя: любое значение в `.env` игнорировалось.

**Правило.** Ручка конфигурации без читателя — это **дефект**, а не «задел».
Проверка — обратный `grep`: не «где объявлено», а «где **прочитано**».

```bash
# Объявлена, но не читается → мёртвая
grep -rn "CHECKOUT_MAX_ITEMS" --include=*.php .   # только config/nabilet.php
# Убедиться, что ключ конфига кем-то используется
grep -rn "max_items_per_order" --include=*.php app/
```

**Обязательное условие.** Значение, влияющее на поведение, должно иметь **один**
источник, и этот источник должен быть проверяем изменением. Если настройка
читается — это надо доказать, а не предположить:

```bash
# Единственный способ убедиться, что ручка живая: изменить её и посмотреть
CHECKOUT_MAX_ITEMS=3   # в .env, перезапуск
curl ... -d '{"quantity":4}'   # ожидаем 422 «не больше 3»
curl ... -d '{"quantity":3}'   # ожидаем 201
```

Если после смены значения поведение не изменилось — ручка мёртвая, и это
надо исправлять, а не документировать.

**И не дублируйте значение на клиенте.** Константа `MAX_TICKETS_PER_ORDER = 10`
на фронтенде была копией серверного лимита; снижение лимита на сервере давало
«кнопка нажимается, а запрос отвергается 422-м с техническим текстом». Правильно —
отдать число в ответе API (`meta.max_tickets_per_order`), а константу оставить
только фолбэком для старой сборки.

### 3.2. Домен, который описывает несуществующее поведение

Самый коварный вариант: класс с безупречным докблоком, который **не участвует
в боевом пути**. Он проходит ревью (докблок убеждает), покрыт тестами (тесты
гоняют сам класс), и при этом не влияет ни на что.

**Что было.** `HoldWindow` заявлял «DEFAULT 10 MINUTES» и grace 30 секунд;
`ReservationPolicy` — лимит 8 и докблок «enforced in one place it is a rule».
Реальность: срок удержания — 15 минут (`CHECKOUT_HOLD_DURATION`), grace — 5 минут
(был **продублирован литералом** в пяти местах: `HoldSweeper` ×3,
`Orders\Models\SeatHold`, `Payments\Services\PaymentService`), лимит — 10
(литерал в контроллере). `HoldWindow` встречается только в тестах,
`OrderPlacement` (единственный потребитель `ReservationPolicy`) не создаётся
в `app/` нигде.

**Частично закрыто.** Grace сведён к одному ключу
`nabilet.checkout.hold_grace_minutes` (`CHECKOUT_HOLD_GRACE_MINUTES`) —
пять копий числа больше не могут разъехаться. Лимит сведён к
`nabilet.checkout.max_items_per_order` (`CHECKOUT_MAX_ITEMS`). Остаётся
незакрытым «оживление» доменного кластера (`OrderPlacement`/`ReservationPolicy`)
— см. §9.

**Правило.** Перед правкой доменного класса проверьте, что он **достижим**:

```bash
grep -rn "new OrderPlacement" app/      # пусто → класс в проде не работает
grep -rn "HoldWindow" app/ | grep -v "^app/.*HoldWindow.php"   # только докблоки
```

Класс, который никем не создаётся, — это либо мёртвый код, либо недоделанная
интеграция. В обоих случаях докблок, описывающий его как действующее правило,
**врёт читателю**, и это надо исправлять явной пометкой «в боевом пути не
участвует» с таблицей «заявлено / факт».

## 4. Состояние: локальное против серверного

**Что было.** `danceSelected` в `CoordSeatMap` — локальный `ref`, инициализированный
`false`. Он не был связан с пропсом `selected`. Сценарий: покупатель выбрал танцпол →
удалил его из сводки (серверный холд отпущен, `selected` пуст) → **зона осталась
«выбранной» навсегда** до перезагрузки страницы, потому что локальный флаг никто не
сбрасывал.

**Правило.** Компонент — **отражение** состояния, а не его владелец. Всё, что
описывает выбор пользователя, выводится из пропсов через `computed`. Локальный
`ref` допустим только для состояния, которое не является бизнес-фактом: открыт ли
пикер, какой пункт в фокусе, сколько пикселей сдвинута карта.

Проверка на запах: если `ref` дублирует то, что уже есть в пропсе, — это баг, а не
оптимизация.

**Следствие, найденное тем же разбором.** Ветка `standing` в `onToggleCoord`
безусловно вызывала `holdSeat()` и `cart.toggle()`. `cart.toggle()` — тумблер, поэтому
повторный клик локально снимал выбор, а **серверный холд оставался**. Зона числилась
занятой за покупателем до истечения TTL, хотя он считал её свободной. Правило:
для каждой ветки «выбрать» обязана существовать ветка «снять», и обе должны ходить
на сервер.

## 5. Протокол проверки правки

Правка не считается сделанной, пока не пройдены все шаги. Каждый шаг ловит свой класс
ошибок, и ни один не заменяет остальные.

| Шаг | Команда | Что ловит |
|-----|---------|-----------|
| 1. Типы | `npx vue-tsc --noEmit` | несоответствие контрактов, опечатки в полях |
| 2. Тесты | `npx vitest run` + `php tests/run.php` | регрессии в уже закреплённом поведении |
| 3. Сборка | `npx vite build` | проблемы сборки, невидимые в dev-режиме |
| 4. Живой стенд | `php artisan serve` + `curl` | **расхождение с реальным API** — то, что тесты с моками не видят |
| 5. Уборка | SQL-скрипт | тестовые данные не остаются в БД |

### Шаг 4 — обязательный, и вот почему

Мок отвечает то, что мы **думаем** отдаёт сервер. Живой стенд отвечает то, что он
отдаёт **на самом деле**. Дефект S1 (неверный id для `DELETE`) тесты с моками не
поймали бы в принципе: мок был написан по тому же неверному предположению.

Реальный пример из этого разбора — одна команда, которая доказала дефект:

```bash
curl -s --noproxy '*' -X DELETE -H "X-Cart-Token: $TOK" -d '{"session_id":"6"}' \
     http://127.0.0.1:8391/api/v1/cart/items/26
# → 404 CART_ITEM_NOT_FOUND     ← id инвентаря
# → 200 (с id 23)               ← cart_items.id
```

**Локальные особенности стенда** (иначе шаг 4 не работает):

- `--noproxy '*'` для `localhost` — иначе запрос уходит в прокси и падает;
- `--ssl-no-revoke` для внешних HTTPS — иначе schannel не проверит отзыв сертификата;
- `artisan serve` запускать в фоне, иначе процесс блокирует сессию;
- `X-Cart-Token` обязателен: корзина ключуется парой `(cart_token, session_id)`.

### Шаг 5 — не «потом», а часть правки

Стенд меняет БД. Тестовые корзины, холды и остатки инвентаря нужно вернуть в исходное
состояние **в той же сессии**. Оставленный холд ломает следующий прогон и создаёт
ложные «баги».

## 6. Закрепление инвариантов тестами

Тест пишется не «на функцию», а **на инвариант**, который уже однажды нарушался.
Разница принципиальная: тест на функцию проверяет, что код делает то, что делает;
тест на инвариант проверяет, что код делает то, что **должен**.

Пример из этого разбора — `tests/Unit/Cart/cartStore.test.ts`:

```ts
it('count считает позиции, ticketsCount — билеты', () => {
  cart.toggle(seat({ id: 'seat-1' }))
  cart.toggle(seat({ id: 'dance', row: 0, number: 0, quantity: 3 }))

  expect(cart.count).toBe(2)          // позиции
  expect(cart.ticketsCount).toBe(4)   // билеты
})
```

Этот тест падал бы на исходном коде и упал бы при любой будущей попытке «упростить»
`ticketsCount` обратно до `selectedIds.size`. Комментарий в шапке файла объясняет,
**почему** тест существует — иначе через полгода его удалят как избыточный.

### Чек-лист теста на инвариант

- [ ] В шапке файла назван **реальный дефект**, который тест сторожит.
- [ ] Тест падает на исходном (сломанном) коде — иначе он ничего не проверяет.
- [ ] Граничные значения проверены явно: `0`, отрицательное, `NaN`, пустая строка.
- [ ] Если контракт общий для двух путей (`request` и `upload`) — тестируются **оба**.

## 7. Чек-лист ревью для этого проекта

Быстрый список для pull request, затрагивающего витрину или корзину.

**Контракты**
- [ ] Ни один `id` не передаётся без указания типа в имени (`cartItemId`, `inventoryItemId`).
- [ ] Новые поля ответа читаются с **того же** пути, что отдаёт сервер (проверено `curl`, не догадкой).
- [ ] Ветвление по ошибкам — по `error.code`, не по `status`.
- [ ] Новый разбор ответа не дублирует существующий парсер.

**Числа**
- [ ] Бизнес-арифметика живёт в одном месте, компоненты её вызывают.
- [ ] Магические числа экспортированы; серверные лимиты помечены как отражение серверного правила.
- [ ] Различаются «позиции» и «билеты» там, где это разные величины.
- [ ] **У каждой настройки конфигурации есть читатель** — проверено обратным `grep`, а не предположением.
- [ ] Изменение настройки **проверено сменой значения** на стенде: поведение изменилось.
- [ ] Значение не продублировано на клиенте; если продублировано — приходит из API.

**Состояние**
- [ ] Всё, что описывает выбор пользователя, — `computed` от пропсов, не локальный `ref`.
- [ ] У каждой ветки «выбрать» есть ветка «снять», и обе ходят на сервер.

### P3. Процесс

- **CI-гейт существует, но в нём не было главного ратчета.** `.github/workflows/ci.yml`
  содержит три job'а: `verify` (12 dependency-free проверок — линт, ядро,
  чистота домена, граф модулей, миграции, машины состояний, OpenAPI ×2,
  контракт↔схема ×2, модели↔схема, автозагрузка, структура модулей), `docker` и
  `schema` (применение спеки к MySQL 8.4 + проверка триггера неизменяемости).
  Это больше, чем «ничего». Но `tools/verify-error-envelope.php` — ратчет
  §1.2, той самой болезни, которая в этом проекте встречалась чаще всего —
  **  в CI отсутствовал**, хотя он не требует ни `vendor/`, ни MySQL. Он добавлен
  в job `verify` этим проходом. Правило на будущее: верификатор, которому не
  нужен Composer, обязан быть в CI — иначе он запускается только тогда, когда
  о нём вспомнят.
- **Чего в CI по-прежнему нет и почему.** `vendor/bin/phpunit` (96 тестов, в том
  числе весь `tests/Feature/`) и фронтенд-гейты (`npm run typecheck`,
  `npm test`, `npm run build`) не подключены: job `verify` намеренно не ставит
  ни Composer, ни Node, и это его достоинство, а не упущение — он остаётся
  зелёным при недоступном Packagist. Подключать их нужно **отдельным job'ом**,
  чтобы падение сети не выдавало себя за падение кода:

  ```yaml
  frontend:
    name: Frontend (typecheck, unit, build)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

          node-version: '22'
          cache: npm
  ```

  Не добавлено этим проходом сознательно: `npm ci` в этой среде не проверялся,

## 10. Второй проход: конструктор залов. Правила, выведенные из дефектов

Первый проход (§1–§9) разбирал поток покупки. Этот — **конструктор схем залов**
(создание концертного зала любой конфигурации и площадки со столами), его
**импорт/экспорт** и **модели + схему БД**. Дефекты здесь другого класса, чем в
§1: не рассогласование «фронт ↔ API», а **данные, у которых оказалось два
источника истины**, и **таблицы, которые существовали, но были мертвы**. Ниже —
шесть правил; каждое выведено из конкретного дефекта и проверено исполнением.

Сводка того, что было найдено и закрыто этим проходом:

| # | Дефект | Класс | Где правило |
|---|---|---|---|
| 1 | Геометрия стола (`tableCx/Cy/Ring`) хранилась и в payload, и вычислялась | два источника истины | §10.1 |
| 2 | `hall_tables` — 0 строк во всех трёх БД; `HallTable::create()` всегда падал | мёртвая таблица | §10.2 |
| 3 | Только `backgrounds[0]` переживал сохранение; повторные автосейвы дублировали фон (2→4→6→8) | дублированный сериализатор | §10.3 |
| 4 | `rowPrices: {}` читался фронтом как `[]` после круга через MySQL | типовая нестабильность PHP | §10.4 |

### 10.1. Производные данные не могут иметь двух источников истины

**Что было.** У сектора-стола в схеме есть геометрия: центр (`cx`, `cy`) и радиус
(`ring`). Она **выводима** из координат мест — это среднее по местам и максимальное
расстояние до них. Но редактор писал её в payload отдельными полями `tableCx`,
`tableCy`, `tableRing`, а сервер при чтении схемы считал её заново. Два источника
истины на одно число: правка одного не меняет второго, и они расходятся молча.

**Правило.** Производное значение **не сериализуется**. В файл едет только
инвариантный источник (координаты мест); всё выводимое пересчитывается на чтении.
`serializeSchema()` сознательно **не** пишет `tableCx/tableCy/tableRing` — они
появляются только в момент потребления (`HallSchemaVersion::toInventoryFormat()` →
`tableGeometry()`).

**Второе следствие — идемпотентность импорта.** Если файл минимальный, первый
импорт навешивает на него умолчания. Второй импорт обязан дать **байт-в-байт тот
же** экспорт. Иначе каждое сохранение что-то дописывает, и схема «растёт» сама.
Именно так вскрылся дефект №3: экспорт после импорта отличался.

**Как проверить.** `tests/Unit/HallEditor/schemaSerialization.test.ts` (28 тестов)
держит round-trip и отдельный тест «normalize-minimal-statics-once-then-stable».
Сквозная проверка на живом стенде: экспорт → импорт → **второй экспорт идентичен
первому** (`.shots/hall-export-import.mjs`, 12/12 PASS).

### 10.2. Таблица, в которую никто не пишет, — это ложь

**Что было.** Таблица `hall_tables` существовала: миграция, модель, внешний ключ,
колонки под геометрию стола. При этом **ни одной строки** — ни в `nabilet`, ни в
`nabilet_test_suite`, ни в `nabilet_hall_lab`. Причина оказалась составной: во‑первых,
`HallTable` не генерировал `public_id` (не было `booted()` с ULID), поэтому любой
`HallTable::create()` падал на `Field 'public_id' doesn't have a default value`; во‑вторых,
и вызывать его было некому — `InventoryService::generateFromSchema()` создавал места,
но секторы-столы в `hall_tables` не переносил.

**Правило.** **У каждой новой таблицы обязаны быть три вещи: писатель, читатель и
тест.** Таблица без пишущего кода — не «задел на будущее», а мину: она проходит
`models↔schema` в CI, выглядит как реализованная фича и вводит в заблуждение при
разборе. Если читателя/писателя пока нет — таблицу не создают, а пишут задачу.

**Как закрыто.** `toInventoryFormat()` теперь отдаёт `shape` и блок `table`
(`{cx, cy, ring}` в **координатах канваса**); `generateFromSchema()` создаёт по
строке `HallTable` на каждый сектор со `shape: 'table'`, кладя геометрию в
`metadata_json`. `HallTable` получил `booted()` с ULID. Замок —
`tests/Feature/HallTableGeometryTest.php` (4 теста): геометрия в канвас-координатах,
не-столы едут без блока `table`, `hall_tables` заполняется (2 строки, вместимости
8 и 6), повторная генерация не дублирует.

### 10.3. Дублированный парсер обязательно разъедется

**Что было.** Payload схемы собирался **дважды** внутри одного компонента: отдельно
в `buildSchemaPayload()` (для автосейва) и отдельно в `exportSchema()` (для файла).
Две копии одного литерала. Разошлись они предсказуемо: в одной ветке фон писался
как массив `backgrounds[]`, в другой — как одиночное поле `background`. Результат —
дефект №3: переживал только `backgrounds[0]`, остальные терялись, а повторный
автосейв дублировал выживший фон (наблюдалось 2→4→6→8 за четыре цикла).

**Правило.** **Один контракт — один чистый модуль.** Сериализация вынесена в
`resources/js/pages/hall-editor/schemaSerialization.ts` (~470 строк, ноль зависимостей
от Vue). Компонент стал тонким адаптером: `exportSchema()` вызывает
`buildSchemaPayload()`, а тот — единственный `serializeSchema()`. Разбор тоже один:
`parseSchemaPayload()` принимает и строку, и объект, и различает формат
`editor` / `db` / `empty`.

**Побочная выгода, ради которой это и делалось.** Логику, живущую в `.vue`,
протестировать почти нельзя: `vitest` без мока Konva монтирование не переживает.
Чистый `.ts` тестируется напрямую — отсюда 28 тестов там, где раньше было 0.

**Ловушка, которую стоит запомнить.** `danceZoneFor()` возвращает танцпол только
при `format === 'db'`. Если бы он возвращал зону и для `editor`, каждый цикл
импорта добавлял бы **второй** танцпол — та же болезнь «растёт само». Тест на
идемпотентность это ловит.

### 10.4. PHP: пустая карта и пустой список — не одно и то же

**Что было.** У сектора есть `rowPrices` — карта «ряд → цена». Пустая карта в
корректном JSON — это `{}`. Но `json_encode([])` в PHP даёт `[]`, а `[]` на
фронте — не объект. После круга «PHP → MySQL → PHP → JSON» пустая карта
приезжала как `[]`, и код, ожидавший объект, ломался на пустом словаре — то есть
на самом частом случае.

**Правило.** **Карта обязана быть `(object)`.** Любой `array<string, mixed>`,
уезжающий в JSON как словарь, приводится к объекту на границе. Сделано в
`SchemaPayloadNormalizer::normalize()`: кастует `sectors[].rowPrices` в `(object)`,
идемпотентен, не мутирует вход.

**Отдельное правило — про место нормализации.** Первая попытка поставила
нормализацию **до** `validateSchemaPayload()` — и уронила 3 теста
`ValidationError`: валидатор ждёт массив, а получал объект. Порядок в
`HallService::createSchemaDraft()`:

```php
$this->assertPayloadSize($payload);
$this->validateSchemaPayload($payload);   // 1. валидация — на «сыром» виде
$payload = SchemaPayloadNormalizer::normalize($payload);  // 2. нормализация
// 3. только теперь — запись
```

Правило: **валидация работает с входным контрактом, нормализация — с тем, что
идёт в хранилище.** Менять их местами нельзя.

**Ловушка теста.** MySQL печатает `"rowPrices": {}` **с пробелом**, поэтому
`assertStringContainsString('"rowPrices":{}')` падает на корректном коде.
`tests/Feature/HallSchemaPayloadContractTest.php` (6 тестов) использует
`assertMatchesRegularExpression('/"rowPrices":\s*\{\}/')`.

### 10.5. Инвариант, живущий только в коде приложения, — это пожелание

**Что было.** «У зала не может быть больше одной опубликованной версии схемы и
больше одного черновика» проверялось в `SchemaVersionPolicy` — то есть в
приложении. Любой другой путь записи (миграция, скрипт, ручной `INSERT`, гонка
двух запросов) это правило не видел. Инвариант существовал ровно до первого
обхода приложения.

**Правило.** **Инвариант целостности живёт в схеме БД, а не в сервисе.** Если
правило можно выразить индексом или ограничением — оно выражается там. Приложение
может дублировать проверку ради понятной ошибки, но источник истины — БД.

**Как закрыто.** Миграция
`database/migrations/2026_10_06_000200_enforce_single_live_schema_version.php`:
генерируемые `VIRTUAL`-колонки

```sql
published_hall_id = CASE WHEN status = 'published' THEN hall_id END
draft_hall_id     = CASE WHEN status = 'draft'     THEN hall_id END
```

плюс уникальные индексы `uq_schema_one_published_per_hall` /
`uq_schema_one_draft_per_hall`. `NULL` в MySQL не конфликтует, поэтому архивных
версий сколько угодно, а вторая published/draft на тот же зал получает
`QueryException`.

**Правило fail-closed миграции.** Миграция **не чинит** существующие данные молча.
`assertNoExistingViolations()` сначала ищет уже нарушенные залы и, если находит,
падает с их идентификаторами. Автопочинка данных в миграции — это тихая потеря
чужих данных; миграция обязана остановиться и потребовать решения человека.
Проверено: 0 нарушений во всех трёх БД. Замок —
`tests/Feature/HallSchemaSingleLiveVersionTest.php` (6 тестов).

### 10.6. Порядок удаления — часть контракта

**Что было.** `generateFromSchema()` при повторном вызове падал с
`1451 Cannot delete or update a parent row: fk_inventory_seat`. Инвентарь сессии
удалялся **после** геометрии, а места на него ссылаются. Это был боевой дефект:
**регенерация инвентаря для уже настроенной сессии не работала вообще**, с первого
раза.

**Правило.** **Сначала зависимые, потом опорные.** Удаление — обратный порядок к
созданию. Если FK стоит `RESTRICT`, порядок не «желателен», а обязателен; при
`CASCADE` — обратный случай (удаление родителя утащит детей, и это надо
предвидеть). В сервисе это оформлено явным шагом:

```php
// 0. Снимаем инвентарь сессии ДО удаления геометрии.
InventoryItem::where('session_id', $session->id)->delete();
// 1. Пересоздаём геометрию …
```

### 10.7. Дефект, который видит только глаз

**Что было.** Танцпол рисовался поверх мест амфитеатра — на скриншоте витрины
пунктирная зона перекрывала часть ряда. Ни один юнит-тест этого не поймал бы:
координаты каждого элемента «правильные», неверна **компоновка** — слой поверх
слоя.

**Правило.** Геометрию, которую проверяют числами, всё равно надо **один раз
посмотреть глазами** после каждой смены раскладки. Для этого раскладка танцпола
вынесена в `resources/js/lib/danceZone.ts` (чистая функция `danceZoneLayout`,
9 тестов), а `CoordSeatMap.vue` резервирует нижнюю полосу через `reservedBottom` —
зона больше не может наехать на места арифметически, и это подтверждено
скриншотом (`outputs/storefront-seats-concert.png`).

**Мораль для ревью.** «Тесты зелёные» и «выглядит правильно» — два независимых
утверждения. Второе доказывается только рендером.

### 10.9. Два `phpunit` на одной тестовой БД — и «Unknown column», которого нет

**Что было.** Полный прогон `phpunit` внезапно дал **96 тестов, 87 ошибок**, все —
`SQLSTATE[42S22] Unknown column 'revision' in 'field list'` при вставке в
`hall_schema_versions`. Колонка `revision` при этом **есть**: `information_schema`
её показывает, все 27 миграций применены, 74 таблицы на месте. Отдельный прогон
одного класса проходил (`OK, 6 tests`), следующий — падал. Состояние базы **мигало**
между «есть колонка» и «нет колонки» без единой правки кода.

**Что оказалось.** В системе одновременно жили **два процесса `phpunit`**, каждый
на своей стадии: один прогонял `RefreshDatabase` → `migrate:fresh`, второй в это же
время работал с той же базой `nabilet_test_suite`. Замер по шагам это доказал:
сразу после `phpunit --filter AnalyticsReportTest` в базе было **14 таблиц и
1 миграция**, через минуту — **63 таблицы и 9 миграций**, ещё через минуту — **74 и
27**. Схема не «мигала» — её **строил второй процесс**, а первый в это время
вставлял строки в ещё не достроенную таблицу.

**Правило.** `migrate:fresh` **разрушителен и не является конкурентно-безопасным**.
Тестовая база — это разделяемый ресурс с эксклюзивным доступом: **один прогон
тестов в один момент времени**. Если в проекте есть фон/CI/второй агент, который
может запустить `phpunit` параллельно, — нужен либо отдельный database-per-run
(`DB_DATABASE=nabilet_test_${PID}`), либо файловая блокировка прогона. Молчаливое
разделение одной базы даёт **ложные дефекты**, которые дороже настоящих: они
выглядят как ошибка в коде и уводят отладку на часы.

**Диагностический признак, который стоит запомнить.** Если ошибка утверждает, что
**колонки/таблицы нет**, а `information_schema` показывает обратное — не читайте
миграции. Сначала проверьте, не строит ли кто-то схему **прямо сейчас**:
`SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=…` дважды с
интервалом, и список процессов `php.exe`. Растущее число таблиц между двумя
замерами = идёт чужой `migrate:fresh`, и ваш прогон недействителен.

**Урок про доверие к «красному» прогону.** Прежде чем заводить дефект по
упавшему тесту, надо убедиться, что прогон вообще был валидным: один процесс, одна
база, схема достроена. 87 «ошибок» здесь не содержали ни одного дефекта кода.

### 10.10. Короткий чек-лист ревьюера залов

- [ ] Ни одно **производное** поле не уезжает в payload (проверить экспорт глазами).
- [ ] Импорт идемпотентен: экспорт → импорт → экспорт совпадают.
- [ ] У новой таблицы есть писатель, читатель и тест — или таблицы нет.
- [ ] Сериализация схемы существует **в одном** месте (`schemaSerialization.ts`).
- [ ] Словари в JSON — `(object)`; валидация до нормализации, нормализация до записи.
- [ ] Инвариант «один published / один draft» держит БД, а не только сервис.
- [ ] Удаление идёт от зависимых к опорным; регенерация проверена **вторым** вызовом.
- [ ] После смены раскладки сделан скриншот — числа не заменяют взгляд.
- [ ] Перед прогоном тестов убедиться, что тестовую БД не делит другой процесс: один `phpunit` за раз (§10.9).
