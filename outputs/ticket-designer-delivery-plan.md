# Билет на мероприятие: конструктор → письмо покупателю

**Дата:** 2026-10-08 · **Режим:** активная разработка, MVP
**Клиент:** **«Сургут-Концерт»** — организатор концертов (не перекуп, не площадка над
другими организаторами). Проект делается **для него**.
**Задача:** под каждое мероприятие — индивидуальный билет с афишей и QR-кодом, который
уходит на почту покупателю (в том числе анонимному).
**Связано с:** `outputs/loyalty-architecture-plan.md`

---

## 0. Что даёт «один организатор» для этой задачи

Три следствия, все упрощающие:

1. **`ticket_templates.organization_id` практически не нужен.** Он остаётся в схеме (не
   трогаем пакет), но реально шаблоны будут принадлежать одной организации. Дилемма
   «шаблон мероприятия vs шаблон организации» **исчезает**: любой шаблон — «их» шаблон.
2. **Фолбэк проще.** «Шаблон по умолчанию» — это просто активный шаблон единственной
   организации, а не выбор между наследованием от организации и глобальным дефолтом.
3. **Афиша — всегда своя.** `events.poster` / `events.cover` — это постеры самого
   «Сургут-Концерта», а не чужие. Значит вставлять их в билет можно без вопросов о правах и
   без проверки «а это точно наше мероприятие».

## 2. Решение по бонусам: кошелёк один

«Сургут-Концерт» — сам организатор, поэтому вопрос «бренд или организатор» снят:

- **Кошелёк один** — `bonus_balances` ключуется по `user_id`, без `organization_id` в ключе.
- **Но `organization_id` пишется в каждую проводку** `bonus_transactions` как источник
  начисления. Формулировка правила: *баланс один на человека, но каждая проводка помнит,
  кто начислил*.

Зачем второе: стоит ноль сейчас. Если продукт однажды будет поставлен второму организатору
(а `README` описывает именно такой сценарий установки — это шаблон, который можно продать
повторно), разбивка восстановится из истории. Без `organization_id` в проводках восстановить
её **не из чего** — это была бы потеря данных, а не миграция.

**Эмитент бонусов — сам «Сургут-Концерт».** Долг по бонусам на его стороне, и он же получает
выгоду от возврата покупателя. Никакой третьей стороны в схеме нет — поэтому вариант с одним
кошельком здесь не «компромисс», а точное описание реальности.

## 3. КРИТИЧНО: внешний рендер QR — утечка токена входа

Это самая важная находка, и она относится прямо к запросу про QR.

`resources/js/lib/ticketBuilder.ts:164–167`:

```ts
export function getQrCodeUrl(data?: string): string {
  const qrData = encodeURIComponent(data || 'https://nabilet.com')
  return `https://api.qrserver.com/v1/create-qr-code/?size=150x150&data=${qrData}`
}
```

Что здесь происходит на самом деле. `qr_payload` — это **подписанный токен входа**
`NB1.<publicId>.<token>.<signature>` (`QrSigner`, ТЗ §30). Кто его получил — тот проходит на
мероприятие. Функция отправляет его **третьей стороне** (`api.qrserver.com`) как параметр
запроса. Третья сторона получает:

- сам токен входа (может сохранить и переиспользовать),
- IP и Referer покупателя,
- по сути — карту «кто когда покупал билет» в разрезе запросов.

Это **тот же класс дефекта**, который в проекте уже закрывали: открытый `GET /tickets/{id}/qr`
отдавал `qr_payload` анонимно, и его убрали под `auth:api` (см. комментарий в
`app/Modules/Tickets/routes/api.php`). Вернуть тот же токен через внешний сервис — значит
обойти закрытую дыру с другой стороны.

**Требование:** рендерить QR **только локально** — клиентской библиотекой в браузере, чтобы
payload не покидал устройство. На сервере QR-пакета нет намеренно (это записано в докблоке
`TicketGeneratorService`), и это правильно.

Пока конструктор не подключён к реальным данным, функция безвредна — она рисует
`https://nabilet.com` в превью. **Опасность возникает ровно в момент подключения данных.** Поэтому
это надо исправить до подключения, а не после.

Замечание о письме: там внешний рендер тоже невозможен по той же причине. Сейчас в письме —
текстовая строка payload (`email/ticket.blade.php:39`).

## 4. Что нужно построить (и что не нужно)

### 4.1 Подключить конструктор

1. **Роуты** `ticket-templates` в модуле `Tickets` (CRUD по `ticket_templates`).
   Таблица в пакете уже есть — миграция не нужна.
2. **Контроллер + сервис** для сохранения/версионирования `template_json`.
   Важно: `template_json` — произвольный JSON, поэтому **форма шаблона не требует
   миграций при развитии конструктора**. Это правильное решение, оставить как есть.
3. **Страница админки** + пункт меню + маршрут Vue рядом с `hall-editor` (он уже там).
4. **Привязка шаблона к мероприятию.** Здесь единственное реальное расширение схемы:
   сейчас `ticket_templates` знает только `organization_id`. Чтобы «под каждое мероприятие —
   свой билет», нужно либо `events.ticket_template_id`, либо связующая таблица. Решение —
   см. §4.3.

### 4.2 Почему привязка к мероприятию важна (и дешевле)

`events.poster` и `events.cover` — колонки-URL и уже существуют в спеке. Модуль `Media`
(`enabled: true`, priority 145) заявлен именно под афиши и логотипы. Значит **афиша для
вставки в билет уже есть** — её не нужно ни загружать заново, ни хранить второй раз.

Собирать билет «вручную под каждое мероприятие» не нужно: шаблон описывает **раскладку и
переменные**, а данные (афиша, название, дата, место, ряд) подставляются из мероприятия. Тогда
«индивидуальный билет под каждое мероприятие» — это **выбор шаблона + свой постер**, а не
рисование с нуля каждый раз.

### 4.3 Одно расширение схемы (минимальное)

```
events.ticket_template_id  BIGINT UNSIGNED NULL  → ticket_templates(id) ON DELETE SET NULL
```

Одна nullable-колонка с `ON DELETE SET NULL`. Почему так, а не связующая таблица:

- шаблон у мероприятия **один** (не many-to-many) — связующая таблица была бы лишней сущностью;
- `ON DELETE SET NULL` означает, что удаление шаблона не ломает мероприятие — оно просто
  падает на шаблон по умолчанию. Это правильное поведение для «настройки оформления»;
- NULL = «использовать шаблон организации/по умолчанию», то есть старое поведение сохраняется
  без миграции данных.

**Отвергнуто:** хранить оформление билета внутри `events` (раздувает событие, мешает
переиспользовать шаблоны) и отдельная таблица `event_ticket_designs` (сущность-дубль
`ticket_templates`).

### 4.4 Формат и PDF: отвергаю «сейчас»

Заманчиво добавить колонку `builtin` / `format_version` и серверную PDF-генерацию. Отвергаю
на этом этапе, потому что:

- `format VARCHAR(32) DEFAULT 'mobile'` **уже есть**, а `template_json` — произвольный JSON.
  Значит **формат A4/PNG PDF можно добавить позже без единой миграции**: старые шаблоны
  останутся валидными, новые получат `format = 'a4'`.
- PDF-генерация требует нового пакета (`dompdf`/`tcpdf`) + шрифтов + веса образа. Для письма
  это не нужно: письмо и веб-страница решают задачу.
- Правило проекта: отложенная функция не должна требовать правки ядра, когда её добавят.
  Здесь она и не требует — значит можно спокойно отложить.

**Итог: ноль изменений в `ticket_templates`.** Только одна колонка в `events`.

### 4.5 Как билет попадает в письмо (без нового пакета)

Вложения письма сейчас не поддерживаются — ни `attach`, ни `embed` в Notifications не
используется. Три пути, по возрастанию цены:

| Способ | Что нужно | Оценка |
|---|---|---|
| **A. Ссылка на страницу билета** (QR рисуется в браузере) | ничего нового | **рекомендую** |
| **B. QR-картинка прямо в письме через Data URI / CID-embed** | генератор QR, но **свой**, локальный | дёшево, но нужно решить, где считать |
| **C. Вложенный PNG/PDF билета** | серверный рендер шаблона | дорого, отвергаю сейчас |

Способ A честно решает задачу «билет с афишей и QR на почте»: письмо содержит оформленный
блок (афиша картинкой по URL, название, дата, место, ряд) + кнопку «Открыть билет», а QR
рисуется на странице браузером, где payload не покидает устройство. Текстовая строка payload
остаётся как fallback — она нужна и сегодня, и проверяющему на входе.

Способ C стоит денег и времени, а выигрыш — только у тех, кто печатает билет. Это запрос
меньшинства; при появлении спроса добавится без миграций (§4.4).

## 5. Порядок работ

| Этап | Содержание | Цена | Риск |
|---|---|---|---|
| **1** | **Убрать `api.qrserver.com`** из `getQrCodeUrl` → локальный рендер | часы | 🔴 безопасность, до подключения данных |
| **2** | Роуты + контроллер + страница админки + меню + маршрут Vue для `ticket_templates` | мало | низкий |
| **3** | `events.ticket_template_id` (nullable, `ON DELETE SET NULL`) + выбор шаблона в форме мероприятия | мало | низкий |
| **4** | Резолв шаблона при выпуске билета + письмо со стилизованным блоком (афиша + кнопка) | средне | средний |
| **5** | Страница билета в SPA с QR (локальный рендер), доступ по `X-Cart-Token` | средне | средний |
| **6** | (опц.) Локальный QR → Data URI прямо в письмо | средне | низкий |

Этап 1 не зависит ни от чего и должен быть сделан **первым** — пока функция не подключена к
реальным данным, исправление бесплатно; после подключения это уже инцидент.

Этапы 2–3 дают «индивидуальный билет под каждое мероприятие» в минимальном виде: выбор
шаблона + афиша мероприятия. Этапы 4–5 замыкают доставку покупателю, включая анонимного.

## 6. Что проверить при реализации

1. **`qr_payload` нигде не уходит наружу.** Grep по `api.qrserver.com` и любым внешним
   image/CDN-сервисам в шаблонах билета. Тест: превью и рендер не делают внешних запросов.
2. **Аноним получает билет.** `order.user_id = null`, но `customer_email` заполнен — резолв
   шаблона не должен зависеть от пользователя. Резолв идёт от `order.event_id` / `session_id`,
   как уже сделано в `TicketService` (эти поля NOT NULL — см. комментарий там же).
3. **Шаблон удалён — заказ не сломан.** `ON DELETE SET NULL` + фолбэк на шаблон по умолчанию.
4. **Положительный тест на письмо.** Урок `REVIEW §3.25.2`: набор проверок из одних отказов
   не отличает рабочее от сломанного. Нужен тест, который **сам вызывает**
   `generateTicketData()` и утверждает, что билет реально попал в письмо. Сейчас оба
   потребителя глотают `Throwable` и делают `continue` — письмо уходит **без билетов молча**.
5. **`template_json` остаётся произвольным JSON.** Не превращать его в типизированную схему —
   это единственное, что позволяет развивать конструктор без миграций.
