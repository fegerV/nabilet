## 3. Дефекты, доказанные исполнением

### 3.1 Нет CHECK-ограничений — инвариант остатка не защищён

```sql
UPDATE inventory_items SET available_quantity = -1;          -- ВЫПОЛНЕНО
UPDATE inventory_items SET available_quantity = capacity+50;  -- ВЫПОЛНЕНО
UPDATE inventory_items SET capacity = 0;                      -- ВЫПОЛНЕНО
UPDATE inventory_items SET type = 'bogus';                    -- ВЫПОЛНЕНО
UPDATE tickets SET status = 'nonsense';                       -- ВЫПОЛНЕНО
```

MySQL 8.4 поддерживает настоящие `CHECK`-ограничения. Сам `migrations.sql` признаёт пробел
комментарием в конце файла («Recommended application-level CHECKS»). Но пока проверка живёт
только в приложении, **любая ошибка в коде даёт отрицательный остаток молча**, без сигнала.

Дешёвое усиление:

```sql
ALTER TABLE inventory_items
  ADD CONSTRAINT ck_inventory_qty   CHECK (available_quantity BETWEEN 0 AND capacity),
  ADD CONSTRAINT ck_inventory_type  CHECK (type IN ('seat','standing'));
ALTER TABLE tickets
  ADD CONSTRAINT ck_ticket_status   CHECK (status IN ('issued','used','cancelled','refunded','expired'));
ALTER TABLE sectors
  ADD CONSTRAINT ck_sector_type     CHECK (type IN ('seated','standing','mixed'));
```

### 3.2 Hold не защищён на уровне БД

| Попытка | Результат |
|---|---|
| Второй hold на то же место | **принят** |
| `quantity = 999` на место ёмкостью 1 | **принят** |
| `expires_at` в прошлом | **принят** |

У `seat_holds` нет ни UNIQUE, ни CHECK. Это осознанный компромисс (holds аддитивны по
количеству для standing-зон), но означает, что **единственная защита — сервисный слой**.
Для мест (`type='seat'`) имеет смысл частичный уникальный индекс активного hold.

### 3.3 Неизменяемость опубликованной схемы не обеспечена

```sql
UPDATE hall_schema_versions SET schema_json = '{"v":999}' WHERE status = 'published';  -- ВЫПОЛНЕНО
UPDATE hall_schema_versions SET version = 99              WHERE status = 'published';  -- ВЫПОЛНЕНО
```

§20 и §98 объявляют опубликованную версию неизменяемой, комментарий в DDL это повторяет,
но **ничто не мешает изменению**. Удаление при этом блокируется (FK `sessions` RESTRICT).

Это **самый опасный из app-level пробелов**: один случайный `save()` в Eloquent молча
переписывает геометрию зала, на которую ссылаются уже проданные сеансы. Историческая
целостность теряется без единой ошибки. Нужен либо `BEFORE UPDATE`-триггер, либо guard
в модели + запрет массового обновления.

### 3.4 NULL-distinctness

Строка `inventory_items` с обоими NULL (`seat_id` и `standing_zone_id`) **допускается и
дублируется без ограничений**: в MySQL NULL-значения в UNIQUE-ключе считаются различными.
Оба уникальных ключа работают лишь потому, что ровно одно из пары полей заполнено.
То же в `ab_assignments` (`uq_ab_assignment_user` / `uq_ab_assignment_anon`): пользователь
может получить назначение дважды — как аноним и как авторизованный.

### 3.5 Мультитенантность тонкая

`organization_id` присутствует только у **16 из 64** таблиц:
`ab_experiments, api_keys, audit_logs, checkin_devices, embed_domains, events,
media_assets, offline_bundles, orders, pages, promo_codes, ticket_templates,
user_organization, user_roles, venues, webhooks`.

**Отсутствует** у: `tickets`, `payments`, `refunds`, `carts`, `cart_items`, `order_items`,
`inventory_items`, `seat_holds`, `ticket_scans`, `sessions`, `analytics_events`,
`payment_transactions`, `notifications`, `privacy_requests` и др.

Следствие: тенант-скоуп для билетов, платежей и check-in требует JOIN в 2–3 шага
(`tickets → orders → organization_id` либо `tickets → events → organization_id`).
**Любой запрос, забывший JOIN, — это утечка между тенантами** (BOLA/IDOR), причём именно
на самых чувствительных сущностях. Это архитектурное расхождение с fail-closed подходом,
принятым в сессии 1, и его стоит обсудить отдельно.

### 3.10 Функциональные пробелы пакета относительно исходного ТЗ — закрыто в `010_tz_gaps.sql`

Это самое серьёзное из найденного. Пакет не просто переименовал таблицы — он **потерял
требования исходного `Мысли.md`**, и потеря произошла на уровне производной спеки, а не
только DDL.

**Промокоды.** `Мысли.md` §86 посвящён целиком этой сущности:

```
# 86. Промокоды
Сущность: PromoCode
Условия: fixed / percent / first_purchase / event / category / date / quantity
Например: WELCOME10 → -10%
```

В `Техническая спецификация разработки.md` слово «промокод» **не встречается ни разу**
(0 совпадений на 4603 строки). В `migrations.sql` и всех 8 сплит-файлах нет ни одной
таблицы промокодов. При этом `orders.discount_amount` и `order_items.discount_amount`
существуют — то есть скидка предусмотрена, но взять её неоткуда: нет ни справочника
кодов, ни счётчика использований, ни связи заказа с кодом.

**Переводы площадок и страниц.** §73 явно перечисляет три таблицы:

```
event_translations
venue_translations
page_translations
```

В пакете есть только `event_translations`. `venue_translations` и `page_translations`
отсутствуют — при том, что §73 объявляет локализацию URL (`/ru/events/…`, `/en/events/…`)
сквозной.

**Медиатека.** §73 определяет базовую модель `locale / translation_key /
translation_value`; в структуре проекта присутствует модуль `Media/`. В пакете нет
таблицы медиа — только URL-колонки `logo`, `poster`, `cover`. Следствие: нет учёта
загрузок, alt-текста, вариантов размера, порядка в галерее. Отметим честно: §2336
`Мысли.md` помечает медиа как «опционально», поэтому это пробел мягче двух предыдущих.

**Офлайн-бандлы Checker.** §43 требует, чтобы Android-устройство перед мероприятием
загрузило event, session, список действительных и отозванных билетов и публичный ключ.
Таблицы для учёта выданных бандлов (что именно и когда получило устройство) нет —
есть только `checkin_devices`.

**Роли много-ко-многим.** В пакете роль одна на пару (пользователь, организация) —
`user_organization.role_id`. Разделяемая таблица `user_roles` отсутствует.

**Состояние `revoked` у билета.** §43 требует, чтобы Android Checker перед мероприятием
загружал список **отозванных** билетов, а §44 описывает конфликты офлайн-сканирования,
которые разрешаются именно отзывом. Но `tickets.status` перечисляет только
`issued / used / cancelled / refunded / expired` — состояния `revoked` нет.

Свести `cancelled` и `revoked` в одно нельзя без потери смысла: `cancelled` — отмена с
возвратом или по инициативе покупателя; `revoked` — мошенничество, чарджбэк, разбор
дубля, часто **без** возврата. Различие существует ровно ради аудит-следа и отчётности.

Отдельно отметим: добавленное ограничение `ck_tickets_status` построено на перечислении
из самого пакета, поэтому оно **закрепляет** отсутствие `revoked` — теперь состояние
отклоняется базой. Если `revoked` решено вернуть, ограничение нужно расширить
одновременно с изменением схемы.

**Итого.** Шесть возможностей исходного ТЗ не имели отражения в схеме пакета.

### 3.11 Неограниченные `status`-колонки: 19 словарей, которых нет ни в БД, ни в контракте

Найдено обратным проходом `tools/verify-state-machines.php` (2026-09-20): инструмент
раньше проверял только таблицы, у которых **уже есть** машина состояний в PHP, поэтому
колонка без машины была невидима. Проход по DDL вместо PHP даёт такой список:

```
ab_experiments.status        carts.status              checkin_devices.status
consents.status              event_categories.status   events.status
halls.status                 idempotency_keys.response_status
inventory_items.status       notifications.status      offline_bundles.status
orders.payment_status        organizations.status      pages.status
payment_transactions.status  privacy_requests.status   promo_codes.status
users.status                 venues.status
```

Ни одна из них не имеет CHECK. Для `carts.status` это подтверждается и контрактом:
OpenAPI описывает её как `status: { type: string }` — то есть «любая строка».

**Почему это дефект, а не свобода.** Словарь статуса — это то, на что опираются
обработчики: «можно ли ещё оформлять заказ», «можно ли возвращать», «занято ли место».
Пока его нет, он существует только в виде строк, которые напишет первый же контроллер, —
и расхождение всплывёт в рантайме, как уже всплыли четыре расхождения машин состояний
(§6). Отдельно стоит `orders.payment_status`: она живёт рядом с `orders.status`, и две
колонки про деньги без ограниченного словаря — это два источника истины об одном.

Часть колонок **осознанно** свободна: `idempotency_keys.response_status` — это HTTP-код,
`payment_transactions.status` — словарь провайдера (как и `canceled` у платежа). Это
нужно зафиксировать, а не «забыть».

**Что сделано.** `CartState` задаёт минимальный словарь корзины (`active`, `converted`,
`abandoned`, `expired`), но он помечен в коде как **предложение**, а не спека: до появления
`ck_carts_status` в пакете эти четыре значения не считаются авторитетными. CHECK в пакет
не добавлен — пакет является источником истины, и менять его в одиночку нельзя.

**Попутно: у `revoked` нетtimestamp-колонки.** В `tickets` есть `used_at`, `cancelled_at`,
`refunded_at`, `expired_at` — но нет `revoked_at`, хотя `revoked` — терминальный статус
и единственный переход из `used`. То есть момент отзыва, единственное, что отличает
«отозван до входа» от «отозван после входа (чарджбэк)», в схеме не сохраняется.
`TicketRevocation` считает статус, но записать дату ему некуда. Это пробел пакета,
а не реализации; решение — добавить колонку в пакет.

### 3.12 У одного зала может быть две опубликованные версии схемы

`hall_schema_versions` имеет `uq_schema_hall_version (hall_id, version)` — это запрещает
дубли **номеров**, но не дубли **опубликованных состояний**. Нет ни CHECK, ни индекса,
которые мешали бы двум строкам одного зала иметь `status = 'published'`.

Чем это грозит: сеанс продаёт места по конкретной версии схемы. При двух
опубликованных версиях у сеанса два кандидата, и «правильная» схема — та, которую
первой вернул запрос. Место 12 ряда 4 перестаёт быть фактом.

**Почему правило живёт в коде, а не в БД.** `SchemaVersionPolicy::canPublish()`
отклоняет публикацию, если у этого зала уже есть опубликованная версия. CHECK в
пакет не добавлялся — пакет источник истины.

**Решение реализуемо**, если решите принять: MySQL 8.4 не умеет частичные индексы,
но их заменяет генерируемая колонка с NULL:

```sql
ALTER TABLE hall_schema_versions
  ADD COLUMN is_published TINYINT AS (IF(status = 'published', 1, NULL)) VIRTUAL,
  ADD UNIQUE KEY uq_schema_hall_published (hall_id, is_published);
```

UNIQUE в MySQL разрешает сколько угодно NULL, поэтому черновиков может быть много,
а опубликованная — ровно одна. Триггер иммутабельности при этом не затрагивается.

**Проверено исполнением на MySQL 8.4** (Docker `nabilet-mysql`, БД `sv_probe`), а не
только предложено:

| Шаг | Результат |
|---|---|
| два черновика одного зала | ✅ разрешено, `is_published` = NULL у обоих |
| опубликовать v1 | ✅ разрешено, `is_published` = 1 |
| опубликовать v2 при опубликованной v1 | ❌ `ERROR 1062: Duplicate entry '1-1' for key 'uq_schema_hall_published'` |
| архивировать v1, опубликовать v2 | ✅ разрешено |

Попутно подтвердилось, что триггер иммутабельности не мешает смене статуса
(`published → archived` прошла).

### 3.13 Глобальный UNIQUE на контент-хэш: второе устройство не может получить офлайн-бандл

`offline_bundles` несёт `UNIQUE KEY uq_offline_bundles_hash (bundle_hash)` — **без**
квалификатора устройства. Бандл — это список билетов сеанса, то есть для двух
устройств одного сеанса содержимое **одинаково**, а значит одинаков и контент-хэш.

Чем это грозит: у входа два контролёра. Первый синхронизируется, второй получает
`ER_DUP_ENTRY` и остаётся без бандла — то есть без возможности пускать кого-либо
при отсутствии сети. Отказ не «на всякий случай», а гарантированный: хэш один и тот
же всегда.

**Проверено исполнением на MySQL 8.4** (Docker `nabilet-mysql`, БД `nabilet_p6`,
схема пакета загружена целиком):

| Шаг | Результат |
|---|---|
| бандл для устройства 1, `bundle_hash = 'SAMEHASH'` | ✅ вставлен |
| бандл для устройства 2, тем же содержимым | ❌ `ERROR 1062 (23000) Duplicate entry 'SAMEHASH' for key 'offline_bundles.uq_offline_bundles_hash'` |
| хэш считается с учётом устройства: `hash_for_device_A` / `hash_for_device_B` | ✅ оба бандла вставлены |
| то же устройство, то же содержимое, повторно | ❌ `ERROR 1062` — столкновение сохраняется |

**Почему правило живёт в коде, а не в БД.** Лечение — включить `public_id`
устройства в хэшируемую структуру. Это не требует DDL и сохраняет полезную половину
ограничения: содержимое не изменилось → хэш тот же → генерация обязана
**переиспользовать** существующую строку, а не вставлять новую. Правило реализовано
в `OfflineBundleBuilder` (`app/Modules/Checkin/Domain/`), пакет не изменялся.

Следствие, которое легко упустить: `generated_at` **не** входит в хэшируемую
структуру. Войди он туда — каждая регенерация давала бы новый хэш, и «синхронизируйся
ещё раз» стало бы невозможным.

Альтернатива, если решите менять пакет: `UNIQUE KEY (checkin_device_id, bundle_hash)`
или отказ от уникальности вообще. Первый вариант сохраняет дедупликацию и снимает
меж device-конфликт одновременно; CHECK в пакет не добавлялся.

### 3.14 Сеанс можно перевести на другую схему зала — проданные места остаются вне его карты

Цепочка: `sessions.schema_version_id` → `hall_schema_versions` → `sectors` →
`hall_rows` → `seats` → `inventory_items.seat_id` / `tickets.seat_id`.

Каждый внешний ключ в этой цепочке корректен **сам по себе** — и ни один не говорит
ничего о согласованности целого. `inventory_items.seat_id` проверяет, что место
**существует**; он не проверяет, что место принадлежит той версии схемы, на которую
сейчас указывает сеанс.

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p3`, схема пакета загружена
целиком; фикстура: зал, две версии схемы, сеанс на версии 1, сектор → ряд → место →
строка инвентаря):

| Шаг | Результат |
|---|---|
| INSERT сеанса на версии схемы со `status = 'draft'` | ✅ принят — ни CHECK, ни триггер не требуют, чтобы карта была опубликована |
| UPDATE `sessions.schema_version_id` = 2 при существующей строке инвентаря | ✅ принят |
| Сверка после UPDATE | ❌ `session_points_at = 2`, `seat_belongs_to = 1` |

Итог последней строки: у клиента билет на место 1, а сеанс теперь показывает карту,
в которой этого места нет. Оба внешних ключа удовлетворены, ошибок нет, расхождение
всплывает на входе в зал.

Второе следствие: сеанс, продающий с **черновой** карты. Черновик ещё редактируется
(триггер иммутабельности замораживает только `published`/`archived`), то есть место
может сдвинуться или исчезнуть после того, как его купили.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Правила реализованы в `app/Modules/Sessions/Domain/`
(`SessionSeating`, `SeatingDecision`, `SessionSeatingPolicy`), 15 тестов:
* открытие продаж требует, чтобы карта не была черновиком;
* смена карты запрещена, если инвентарь уже создан;
* новая карта должна принадлежать тому же залу;
* повторная привязка той же версии — это `NO_CHANGE`, а не запись;
* завершённый или отменённый сеанс не меняет карту.

**Уточнение, которое легко упустить:** условие — «не черновик», а не «опубликована».
`archived` допустима: архивация — это как раз способ заменить раскладку, и сеансы,
уже продающие по старой, продолжают продавать. Запрет `archived` сломал бы каждый
сеанс на списанной, но валидной карте. Дефект именно в черновике.

Решение, если решите менять пакет: триггер `BEFORE UPDATE ON sessions`, запрещающий
смену `schema_version_id` при `OLD.schema_version_id <> NEW.schema_version_id` и
наличии строк в `inventory_items`; плюс CHECK на непустой `published_at` у версии,
на которую указывает сеанс со статусом `on_sale`. Второе триггером не выразить
(нужен доступ к другой таблице) — CHECK на `sessions` сослаться на
`hall_schema_versions` не может, следовательно, либо остаётся в коде, либо нужен
GENERATED-столбец-флаг, поддерживаемый процедурно.

### 3.15 Согласие нельзя отозвать с сохранением момента, а у запроса субъекта нет срока

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p3`, схема пакета загружена
целиком).

`consents` — `created_at` и больше ничего. Ни `updated_at`, ни `withdrawn_at`:

| Проверка | Результат |
|---|---|
| колонок, имя которых содержит withdraw/revoked/ended | **0** |
| INSERT согласия с `user_id = NULL` и `anonymous_id = NULL` | ✅ принят — согласие, не принадлежащее никому |
| INSERT согласия со `status = 'banana'` | ✅ принят — CHECK на `consents.status` нет |
| UPDATE согласия до `status = 'withdrawn'` | ✅ принят, но момент отзыва **не сохранён** — записать его некуда |

Отзыв — главное событие в жизни согласия: это ровно то, что делает согласие
согласием, а не галочкой. База умеет перевести статус, но не умеет ответить на
вопрос «когда именно отозвали?» — а это первый вопрос проверяющего. Тот же класс
дефекта, что и `tickets.revoked_at` (§3.11).

`privacy_requests`:

| Проверка | Результат |
|---|---|
| колонок, имя которых содержит due/deadline/respond | **0** |
| INSERT с `type = 'banana'` и `status = 'banana'` | ✅ принят — CHECK нет ни на тип, ни на статус |

Срок ответа на запрос субъекта — величина установленная, и записать её некуда.
Часы, которые нельзя сохранить, нельзя и показать: просрочка не видна ни в
отчёте, ни в очереди.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Privacy/Domain/`
(`ConsentRecord`, `ConsentDecision`, `ConsentPolicy`, `PrivacyRequest`,
`PrivacyDecision`, `ErasurePlan`, `PrivacyRequestPolicy`), 29 тестов:

* **согласие обязано принадлежать ровно одному субъекту** — user или anonymous,
  но не никому и не обоим;
* **отзыв обязан нести момент**; повторный отзыв и отзыв «раньше выдачи»
  отклоняются;
* **по умолчанию — запрет**: отсутствие записи — не согласие;
* **согласие на одну цель — не согласие на другую.** Отдельный вердикт
  `NOT_FOR_PURPOSE` для случая «что-то подписывал, но не это» — самый частый
  реальный провал: проверяют «есть ли хоть какое согласие», а не «есть ли на
  эту цель». Ради этого и существует `consents.consent_type`;
* **срок вычисляется, а не хранится**, и передаётся аргументом: ни ТЗ, ни
  контракт не задают период ответа, а выдуманная цифра в единственном доверенном
  месте — это долг (то же решение, что и по сервисному сбору в Pricing);
* **удаление — это не DELETE.** План (`ErasurePlan`) явно разделяет: личные
  данные удаляются, финансовая запись заказа **сохраняется** с отсоединённой
  личностью. Уплаченный заказ — бухгалтерская запись, её хранение требует закон;
  удалить строку ради запроса — нарушить другую обязанность, а сделать это
  молча — хуже обеих.

Решение, если решите менять пакет: `consents` — добавить `withdrawn_at
DATETIME(6) NULL` и `CHECK (status <> 'withdrawn' OR withdrawn_at IS NOT NULL)`;
`privacy_requests` — добавить `due_at DATETIME(6) NOT NULL` и CHECK на `type` и
`status`. Плюс CHECK «ровно один субъект»:
`(user_id IS NOT NULL) <> (anonymous_id IS NOT NULL)`.

### 3.16 Корзина может держать места чужого сеанса, а срок её жизни ни с чем не связан

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p2`, схема пакета загружена
целиком: 64 таблицы). Скрипт, которым это воспроизводится, лежит рядом —
`tools/repro-cart-gaps.sql`; каждая строка таблицы ниже — это запрос из него.

| Проверка | Результат |
|---|---|
| INSERT в `cart_items` позиции, принадлежащей **другому сеансу** | ✅ принят — `cart.session_id = 1`, `inventory_items.session_id = 2` |
| `total_price = 1` при `unit_price = 100000, quantity = 2` | ✅ принят — CHECK, связывающего итог с арифметикой, нет |
| `unit_price = -500000` | ✅ принят — `BIGINT` знаковый, CHECK нет |
| `carts.expires_at = NULL` | ✅ принят — корзина без срока жизни |
| `carts.expires_at = 2027-01-01` при `sessions.starts_at = 2026-12-01` | ✅ принят — корзина переживает сеанс |
| `carts.status = 'banana'` | ✅ принят — CHECK нет (см. §3.11) |
| `cart_items.quantity = 0` | ❌ отвергнут — `ck_cart_items_quantity` есть, это **не** дефект |

**Почему первая строка — самая дорогая.** `cart_items.inventory_item_id`
ссылается на `inventory_items.id`: внешний ключ проверяет, что позиция
**существует**, но не что она принадлежит тому сеансу, который продаёт корзина.
Оба ключа удовлетворены, строка легальна. Дальше по цепочке: заказ, позиции
которого относятся к двум разным сеансам; `seat_holds.session_id`, который
вынужден солгать хотя бы об одном из них; билеты, выпущенные на чужую дату.
Тот же класс дефекта, что и §3.14 (FK проверяет существование, а не
принадлежность), но в контуре, который ближе всего к деньгам.

**Почему хранимый итог важнее пересчитанного.** `cart_items.total_price` —
реальная колонка, и ничто не связывает её с `unit_price * quantity`. Если домен
молча пересчитывает итог, корзина становится самосогласованной, а дефект —
невидимым; при этом списание пройдёт по **сохранённому** числу. Поэтому объект
хранит оба значения и сообщает расхождение (`CartItem::moneyDrift()`), а
`Cart::storedTotal()` складывает сохранённые итоги, а не правильные.

**Срок жизни.** `expires_at` обнуляемый, и ничто не связывает его ни с холдами,
ни с сеансом. Корзина, которая живёт дольше своего холда, выглядит открытой в
те минуты, когда её места уже вернулись в продажу: покупатель видит «ваша
корзина» и платит в пустоту. Корзина без холдов срока не требует — она ничего не
держит.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Cart/Domain/` (`Cart`, `CartItem`,
`CartDecision`, `CartPolicy`), 38 тестов:

* **позиция обязана принадлежать сеансу корзины** — иначе отказ `WRONG_SESSION`;
* **хранимый итог обязан равняться `цена × количество`** — иначе отказ
  `INCOHERENT_MONEY`;
* **отрицательная цена невозможна** — это возврат, одетый в покупку;
* **пишет только `active`-корзина.** Словарь статусов — предложение (§3.11),
  поэтому статус не валидируется, а сравнивается: всё неизвестное — не `active`,
  то есть отказ;
* **повторное добавление той же позиции — `MERGE_REQUIRED`, а не INSERT.**
  `uq_cart_inventory` не даст вторую строку; правильная запись — UPDATE
  количества. Без этого вердикта вызывающий делает INSERT и получает 1062,
  отрендеренный покупателю как 500;
* **корзина с холдами обязана иметь срок**; срок не может быть позже начала
  сеанса и позже истечения **самого раннего** холда (граница: равенство
  разрешено — последний момент продажи и есть начало сеанса);
* **порядок проверок — часть контракта:** состояние корзины важнее состояния
  строки (мёртвая корзина не примет ничего), а среди дефектов строки
  принадлежность важнее арифметики (место чужого сеанса не обслужишь ни за
  какие деньги, а неверный итог — хотя бы исправимое число);
* отдельный аудит уже записанной корзины (`compositionDecision`) — единственный
  способ найти строки, созданные до появления правила.

Решение, если решите менять пакет: составной FK
`cart_items (cart_id, inventory_item_id)` на `inventory_items (id, session_id)`
при денормализованном `carts.session_id` — либо `BEFORE INSERT` триггер, который
сверяет `inventory_items.session_id` с `carts.session_id`. Плюс
`CHECK (total_price = unit_price * quantity)` и `CHECK (unit_price >= 0)`;
`carts.expires_at` сделать `NOT NULL` либо добавить
`CHECK (expires_at IS NOT NULL OR <нет холдов>)` — второе выразимо только
триггером.

### 3.17 Удалённый аккаунт удерживает свой адрес, а отметка проверки переживает смену контакта

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p7`). Скрипт —
`tools/repro-user-identity.sql`; каждая строка таблицы — запрос из него.

| Проверка | Результат |
|---|---|
| soft-delete аккаунта, затем регистрация с тем же email | ❌ **1062** — удалённый аккаунт держит адрес |
| `UPDATE users SET email = 'attacker@example.com'` при установленном `email_verified_at` | ✅ принят — «подтверждён» адрес, который никто не подтверждал |
| `UPDATE users SET email = NULL` при установленном `email_verified_at` | ✅ принят — подтверждено отсутствие адреса |
| то же для `phone` / `phone_verified_at` | ✅ принят |
| INSERT пользователя без email, без телефона и без пароля | ✅ принят — аккаунт, до которого невозможно достучаться |
| `status = 'banana'` | ✅ принят — CHECK нет (§3.11) |
| INSERT `A@EXAMPLE.COM` при существующем `a@example.com` | ❌ **1062** — collation регистронезависим |
| INSERT `a@example.com ` (с пробелом) | ❌ **1062** — collation PAD SPACE |
| после обезличивания на месте (`email = NULL`) повторная регистрация | ✅ принята — **лечение работает** |

**Почему удалённый аккаунт держит адрес — худшее из двух.**
`uq_users_email` не включает `deleted_at`. Soft-delete оставляет **и** персональные
данные, **и** блокировку адреса: человек не может вернуться, а его данные всё ещё
лежат в строке. Hard DELETE освободил бы адрес, но запрещён внешними ключами от
заказов и билетов. Обезличивание на месте (`email = NULL`, `phone = NULL`, имена и
пароль в NULL) — единственная форма, удовлетворяющая обеим обязанностям: данных
нет, и адрес свободен, потому что NULL в UNIQUE не конфликтует. Это проверено
исполнением, а не предположением (последняя строка таблицы).

Тот же дефект у `events` (`uq_events_org_slug`) и `promo_codes`
(`uq_promo_codes_org_code`) — у обеих таблиц есть `deleted_at`, не входящий в ключ.
Для промокода это особенно обидно: сезонный код нельзя завести заново.

**Почему отметка проверки — это высказывание о контакте, а не о человеке.**
Перенесли контакт — высказывание стало ложным, но база этого не замечает.
Практическая цена: аккаунт, «подтверждённый» на адрес, который ему не принадлежит,
— это готовый канал для чужих билетов и сброса пароля.

**Почему сравнение адресов — решение базы, а не PHP.** `utf8mb4_unicode_ci`
регистронезависим и PAD SPACE: `A@EXAMPLE.COM` и `a@example.com ` — тот же
человек. Проверка на `===` в PHP ответит «адрес свободен», после чего INSERT
умрёт на 1062. Телефон при этом нормализуется **только** trim: вырезание
разделителей сделало бы PHP строже базы (`+7 900 000 00 00` и `+79000000000` —
две разные строки для колонки), и мы бы отказали в регистрации, которую база
готова принять. Асимметрия между каналами записана, а не сглажена.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Users/Domain/` (`ContactChannel`,
`UserIdentity`, `IdentityDecision`, `UserIdentityPolicy`), 37 тестов:

* **`EMAIL_TAKEN_BY_DELETED` — отдельный вердикт, а не «адрес занят».** База
  сворачивает две разные ситуации в одну ошибку 1062: «адрес использует живой
  аккаунт» и «адрес использует аккаунт, которого нет». Первое означает «войдите»,
  второе — «нужно вычистить или обезличить могилу». Саппорт по тексту ошибки их
  не различает, поэтому здесь они разделены.
* **смена контакта сбрасывает его подтверждение** — но только если нормализованное
  значение реально изменилось. Повторное сохранение формы профиля не должно
  расчеловечивать всю базу: тот же принцип, что у `NO_CHANGE` в перепривязке карты
  сеанса. Смена одного регистра или хвостового пробела **не** сбрасывает — база их
  не различает, значит и правило не должно.
* **удалённый аккаунт не аутентифицируется.** Soft-delete, который не закрывает
  вход, — это не удаление.
* **аккаунт обязан быть достижим** — email или телефон. Строка без того и другого
  принята базой, а OAuth/социальной таблицы в пакете нет: такой аккаунт нельзя ни
  залогинить, ни доставить билет, ни сбросить пароль. Он может только копить
  заказы, которые никто не увидит.
* **осиротевшие отметки сообщаются, а не исправляются.** Объект обязан
  представлять плохую строку, иначе её нельзя загрузить, чтобы проаудировать;
  `orphanedVerifications()` и `verificationDecision()` — аудит строк, созданных до
  правила.
* **обезличивание (`anonymised()`) — не DELETE и не soft-delete**, а обнуление
  колонок: данных нет, ключи свободны (`releasesContactKeys()`).

Решение, если решите менять пакет: `uq_users_email` заменить на функциональный
индекс или генерируемую колонку, учитывающую `deleted_at`
(`UNIQUE KEY (email, (deleted_at IS NULL))` так не выразить — нужна генерируемая
колонка `active_email` = `IF(deleted_at IS NULL, email, NULL)` с UNIQUE по ней);
то же для `events` и `promo_codes`. Плюс `CHECK (email IS NOT NULL OR
email_verified_at IS NULL)` и `CHECK (phone IS NOT NULL OR phone_verified_at IS
NULL)`, и `CHECK (email IS NOT NULL OR phone IS NOT NULL)`.

### 3.18 Сессию нельзя отозвать: колонки для этого нет, а срок жизни необязателен

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p8`). Скрипт —
`tools/repro-session-lifecycle.sql`.

| Проверка | Результат |
|---|---|
| INSERT сессии с `expires_at = NULL` | ✅ принята — колонка обнуляемая |
| INSERT сессии, истёкшей за час до `created_at` | ✅ принята |
| INSERT с `last_seen_at` на три дня позже `expires_at` | ✅ принята |
| `SELECT COUNT(*)` колонок, способных записать отзыв | **0** |
| `UPDATE user_sessions SET revoked_at = …` | ❌ **1054 Unknown column** |
| «выйти на этом устройстве» | только `DELETE` — строка, которая и была единственной записью |

**Почему отсутствие колонки отзыва — это не «мелочь схемы».** У `user_sessions`
нет ни `status`, ни `revoked_at`: весь срок жизни — три таймстемпа. Значит
«выйти на этом устройстве» физически реализуется только удалением строки.
Строка и была единственным свидетельством, что сессия существовала: после logout
нечем ответить на вопрос «когда и откуда заходили». Это direct-конфликт с
§3.15/§3.17, где выяснилось то же самое про момент отзыва согласия и про
`consents`: база умеет перевести состояние, но не умеет записать, когда.

**Почему NULL в `expires_at` — это не «длинная сессия».** Это неограниченная
сессия: токен, который переживёт устройство, смену пароля и закрытый инцидент.
Именно поэтому `isImmortal()` — отдельный вопрос, а не разновидность «не истекла».

**Две строки, которые база приняла и которые противоречат сами себе.**
`expires_at < created_at`: код, читающий `expires_at`, считает сессию
никогда не валидной; код, читающий `created_at`, — валидной всегда. Ответ
зависит от того, какая строка спросила. `last_seen_at > expires_at` означает
одно из двух: срок не соблюдается нигде, или токен реплеят.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Auth/Domain/` (`UserSession`,
`SessionDecision`, `SessionPolicy`), 19 тестов:

* **сессия обязана иметь срок** — иначе её нельзя ограничить, а «неограниченная»
  не означает «действительная». Отказ и при выдаче, и при использовании: правило
  fail-closed, как и отсутствие записи о согласии, и неизвестный статус корзины.
  Честное следствие: существующие неограниченные строки перестают работать —
  в этом и смысл.
* **срок не может быть раньше создания.**
* **`REVOKABLE_ONLY_BY_DELETE` — отдельный вердикт, разрешённый, но с другой
  записью.** Отказать было бы ложью: сессию завершить можно. Но вызывающий обязан
  записать аудит **до** DELETE — в `login_logs`, которая существует. Ту же роль
  играет `MERGE_REQUIRED` в корзине.
* **`usedAfterExpiry()` сообщается, а не молча считается «не истекшей»**, и в
  аудите проверяется **раньше** истечения: для строки с перепутанной хронологией
  «истекла» — обманчиво нормальный ответ.
* **Idle-таймаут и TTL не выдуманы.** Ни ТЗ, ни контракт их не задают, поэтому
  объект сообщает факт (`idleSecondsAt()`), а решение принимает вызывающий —
  то же решение, что по сроку ответа на запрос субъекта и по сервисному сбору.

Решение, если решите менять пакет: `user_sessions.expires_at` сделать
`NOT NULL`, добавить `revoked_at DATETIME(6) NULL` и
`CHECK (expires_at > created_at)`, `CHECK (last_seen_at IS NULL OR
last_seen_at <= expires_at)`.

### 3.19 Ключ API может не принадлежать никому, а правило IP — не называть адреса

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p9`). Скрипт —
`tools/repro-api-key-rules.sql`.

`api_keys`:

| Проверка | Результат |
|---|---|
| INSERT ключа с `organization_id = NULL` | ✅ принят — ключ, не принадлежащий ни одному арендатору |
| INSERT ключа без `expires_at` | ✅ принят |
| INSERT ключа с `scopes_json = NULL` | ✅ принят |
| INSERT ключа с `revoked_at` на год вперёд | ✅ принят |
| `UPDATE … SET revoked_at = NULL` | ✅ принят — отзыв отменён без следа |
| продление `expires_at` у отозванного ключа | ✅ принят |
| `SELECT COUNT(*)` колонок, фиксирующих последнее использование | **0** |

Схема делает две вещи правильно: `key_hash CHAR(64)` уникален, и `revoked_at`
**существует** — в отличие от `user_sessions` (§3.18), где отзыв записать нечем.
Но нет как раз того, что делает эти две вещи работающими.

**`organization_id` обнуляемый.** В схеме, где `organization_id` носят лишь 16
таблиц из 64, «никто» — не арендатор, а неопределённость.

**`scopes_json = NULL` — двузначен.** Прочитать как «нет прав» — не даёт ничего;
как «без ограничений» — даёт всё. Оба чтения оправданны, они противоположны, и
колонка не говорит, какое имел в виду автор. Таблица авторизации, оставляющая это
открытым, — дыра, ждущая читателя.

**Отзыв обратим без следа.** `revoked_at` можно вернуть в NULL; колонки истории
нет, а подсчёт колонок последнего использования дал 0 — то есть неизвестно и то,
работал ли ключ вообще.

`ip_rules`:

| Проверка | Результат |
|---|---|
| правило без IP и без CIDR | ✅ принято |
| правило **и** с IP, **и** с CIDR | ✅ принято |
| `rule_type = 'banana'` | ✅ принято |
| правило, истёкшее год назад, с `active = 1` | ✅ принято |
| два противоречащих правила на один адрес | ✅ приняты |

Правило без адреса — это `deny`, который либо не блокирует никого, либо блокирует
всех: строка не говорит, какое чтение имелось в виду. Правило с двумя адресами
заставляет код выдумать ответ («совпадение любого» или «совпадение обоих»).
И отдельно: таблица смешивает allow и deny и **нигде не записывает, что бывает,
если не совпало ни одно правило** — а от этого зависит, является ли набор
списком разрешённых или списком заблокированных.

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Security/Domain/` (`ApiKey`,
`ApiKeyDecision`, `ApiKeyPolicy`, `IpRule`, `IpRuleDecision`, `IpRulePolicy`),
43 теста:

* **любой отзыв — это отзыв, включая будущий**, иначе ключ молча умрёт в момент,
  которого никто не ждёт; нелепость при этом сообщается отдельно;
* **`scopes_json = NULL` — отказ, а не «без ограничений»**: fail-closed на том
  чтении, которое окажется катастрофой, если имелось в виду другое;
* **отзыв необратим.** Отказывать — не ложь: ключ можно завершить. Но отмена
  отзыва не оставляет следа ни в истории, ни в last-used, поэтому правильный ответ
  — выпустить новый ключ;
* **порядок проверок — часть контракта:** отзыв (явное действие человека) важнее
  часов, часы — важнее прав;
* **нечитаемое правило делает весь набор невычислимым**, и запрос
  **отклоняется**. Это fail-closed, как и везде в проекте; цена названа прямо:
  одна битая строка блокирует трафик, пока её не исправят. Альтернатива — молча
  игнорировать битое правило — отключает список блокировок, и это ровно та
  поломка, которую никто не заметит;
* **deny важнее allow безотносительно специфичности**: если allow может
  перекрыть deny, одна широкая разрешающая строка тихо отменяет все блокировки;
* **умолчание передаётся аргументом** (`ABSTAIN`): таблица не хранит его, а
  угадывание — это способ превратить список разрешённых в список заблокированных
  или наоборот.

Решение, если решите менять пакет: `api_keys` —
`organization_id BIGINT UNSIGNED NOT NULL`, `expires_at DATETIME(6) NOT NULL`,
`scopes_json JSON NOT NULL` с `CHECK (JSON_LENGTH(scopes_json) > 0)`,
`CHECK (revoked_at IS NULL OR revoked_at <= NOW())` — последнее выразимо только
триггером; плюс `last_used_at`. `ip_rules` —
`CHECK (rule_type IN ('allow','deny'))`,
`CHECK ((ip_address IS NOT NULL) <> (cidr IS NOT NULL))`,
`CHECK (expires_at IS NULL OR expires_at > NOW() OR active = 0)` (тоже триггер)
и отдельное место для умолчания набора.

### 3.20 Мероприятие публикуется без даты публикации и без сеансов, а пустой перевод запирает язык

**Проверено исполнением на MySQL 8.4** (БД `nabilet_p10`). Скрипт —
`tools/repro-event-publication.sql`.

`events`:

| Проверка | Результат |
|---|---|
| `status = 'published'` при `published_at IS NULL` | ✅ принято — на сайте, и неизвестно с какого времени |
| `status = 'published'` с `published_at` на год вперёд | ✅ принято — законно, но обязано называться «запланировано» |
| `status = 'published'` при нуле сеансов | ✅ принято — страница без даты, без цены и без кнопки |
| `UPDATE … SET status = 'cancelled'` | ✅ принято **без единого условия** — в строке нет колонки, которая могла бы возразить |
| `UPDATE … SET status = 'banana'` | ✅ принято |

`published_at` обнуляемый, а `status` — `VARCHAR(32)` без CHECK
(`verify-state-machines.php` сообщает `events ~ no CHECK on status`). Вместе это
даёт строку, которая «опубликована», но не отвечает на первый вопрос, который
задают карта сайта, заголовок кэша и оператор поддержки: **с какого момента?**

Отмена отдельно неприятна тем, что она проходит молча: ничего не спрашивает о
проданных билетах, а возвраты по ним — отдельная процедура. Отменённое
мероприятие с проданными билетами и невозвращёнными деньгами — это не дефект
схемы самой по себе, а дефект *порядка*, и в схеме нет места, где он записан.

`event_translations`:

| Проверка | Результат |
|---|---|
| строка со всеми контентными колонками `NULL` | ✅ принята |
| после неё — настоящий перевод на тот же язык | ❌ `ERROR 1062 Duplicate entry '1-en'` |

Все контентные колонки обнуляемые (`title`, `short_description`, `description`,
`seo_title`, `seo_description`), а `uq_event_translations (event_id, locale)`
допускает одну строку на язык. Поэтому пустая строка не лежит безвредно — она
**занимает язык**. Настоящий перевод отклоняется, пока кто-нибудь не найдёт и не
удалит заглушку, и ничто не сообщает об этом до первой попытки. Форма та же, что
у нулевой позиции корзины, запирающей `uq_cart_inventory`, — но ту ловит
`ck_cart_items_quantity`, а эту не ловит ничто.

Попутно тем же скриптом:

| Проверка | Результат |
|---|---|
| `seo_meta` для `entity_id = 999999` | ✅ принято — полиморфная пара не имеет внешнего ключа |
| `redirects.status_code = 999` | ✅ принято |
| два **разных** URL длиннее 512 символов | ❌ второй падает `1062` — `uq_redirect_source (source(512))` сравнивает только первые 512 символов |

**Почему правило живёт в коде, а не в БД.** CHECK в пакет не добавлялся — пакет
источник истины. Реализовано в `app/Modules/Events/Domain/` (`Event`,
`PublicationDecision`, `EventPublicationPolicy`, `EventTranslation`,
`EventTranslationPolicy`), 27 тестов:

* **публикация без сеансов отклоняется** — и это **единственное правило здесь,
  которое продуктовый владелец может отменить**. Мероприятие без сеансов не имеет
  ни даты, ни цены, ни кнопки покупки; публикация ставит в карту сайта мёртвую
  страницу. Если нужно «анонсировать до того, как даты известны» — это решение
  продукта, и менять его следует ровно в одном месте; но тогда страница обязана
  это говорить, а сегодня схема таких двух случаев не различает;
* **`published_at` в будущем разрешён и назван `SCHEDULED`**, а не свёрнут в
  `ALLOWED`. Отложенная публикация — настоящая возможность, и запрещать её значило
  бы выдумывать ограничение; важно другое: такая строка не считается видимой
  (`isVisibleAt()` требует, чтобы момент уже наступил);
* **публикация уже опубликованного и имеющего момент — `NO_CHANGE`**, чтобы
  повторное сохранение формы не писало UPDATE, меняющий только `updated_at`;
* **опубликовано без момента — это работа, а не здоровье.** Аудит отвечает отказом
  и говорит, что записать, — вместо того чтобы считать такую строку нормальной;
* **отмена отклоняется, пока продано хоть что-то.** Не потому, что отменить
  нельзя, а потому, что возразить в схеме нечему, поэтому возражение обязано быть
  здесь и обязано случиться **до** расчёта возвратов, а не после;
* **пустой перевод отклоняется, а не игнорируется.** Два очевидных обхода оба
  неверны: «строка есть — рендерим» даст NULL-заголовки, «заголовка нет —
  игнорируем» оставит замок в таблице. Поэтому отказ, и причина называет цену
  замка;
* **замена не может потерять заголовок**: строка, у которой заголовок был, не
  заменяется строкой только из SEO-полей — иначе язык молча становится пустым.

`sessionCount` и `soldUnits` передаются вызывающим: в строке `events` нет ни
счётчика сеансов, ни счётчика продаж, поэтому «продано ли что-нибудь?» из неё не
выводится. Конструктор `Event` отказывается принимать противоречивые факты
(`soldUnits > 0` при `sessionCount === 0`, код `INCONSISTENT_EVENT_COUNTS`).
Словарь `status` не проверяется — только сравнивается, как `carts.status` и
`ip_rules.rule_type`: всё, что не `'published'`, не опубликовано, что отказывает
безопасно.

Решение, если решите менять пакет: `events` —
`CHECK (status IN ('draft','published','cancelled'))` и
`CHECK (status <> 'published' OR published_at IS NOT NULL)`; запрет отмены при
проданных билетах выразим только триггером (нужна другая таблица).
`event_translations` — `CHECK` хотя бы на одно непустое поле из пяти.
`seo_meta` — либо внешние ключи по каждой сущности, либо триггер проверки
существования. `redirects` — `CHECK (status_code IN (301,302,307,308))` и
уникальность по хэшу URL вместо `source(512)`.

### 3.21 Сгенерированный слой Eloquent называет 88 колонок, которых в схеме нет

**Проверено инструментом** `tools/verify-models-schema.php` (не скриптом наката:

Это тот же класс дефекта, за который проект уже заплатил дважды: middleware

масштабе: 88 имён вместо трёх, и все они в коде, который не может упасть здесь.

**Худшее в этом списке — не количество, а то, что он повторяет уже исправленное.**
Сгенерированный слой заново вводит ровно те имена, которые в остальном проекте
уже заменены на правильные:

`ApiKey.last_used_at` здесь показателен: §3.19 доказал исполнением, что колонок
последнего использования в `api_keys` **ноль**, — и сгенерированная модель
объявляет именно ту колонку, отсутствие которой уже задокументировано.

**Как это проверяется.** `verify-models-schema.php` сначала доказывает, что его
разбор DDL вообще что-то прочитал: 64 таблицы / 678 колонок, снятые с
`information_schema` на MySQL 8.4. Разбор, который недосчитывает, сообщает о
фантомных расхождениях, и этот инструмент уже так себя вёл — см. ниже. 88 известных
полей перечислены в самом инструменте (`INVENTED_FIELDS`) с причиной на каждую
модель; список — **храповик**: он может только сокращаться, всё незаписанное
валит сборку. Мутации проверены: отключение разбора `ALTER TABLE` → падает проверка
разбора; ослепление поиска моделей → «no models found»; добавление одной записи в
список → 88 → 87; добавление поля `banana_field` в `Role` → красный с точным именем.

**Побочная находка — тот же дефект разбора в `verify-contract-schema.php`.**
Инструмент читал **только блоки `CREATE TABLE`** и не читал `ALTER TABLE`, а
миграция 010 дописывает колонки именно через `ALTER`: `tickets.revoked_at`,
`tickets.revoked_reason`, `orders.promo_code_id`. Поэтому инструмент считал, что
`tickets` этих колонок не имеет, — и вывод был записан в его же `ACCEPTED_DRIFT`
как «известный пробел» с обоснованием «в `tickets` нет `revoked_at`». **Это было
неверно:** колонки есть. Ошибка разбора превратилась в политику, и храповик получил
ложный зуб. Исправлено: `ALTER TABLE` разбирается, обе записи удалены
(**6 принятых → 4**), и добавлена та же проверка разбора 64/678 — теперь при
недоразборе инструмент говорит «виноват разбор, а не схема». `verify-migrations.php`
знал об `ALTER` с самого начала; в соседний инструмент правку не перенесли.

### 3.22 Дерево модулей разъехалось на три корня пространств имён: 121 файл не автозагружается

Это самый крупный дефект влитой ветки, и он не про схему. Пространство имён — это
утверждение «класс можно найти». Его никто не проверял, и в `app/` накопилось три
корня:

| Корень | Файлов | Покрыт PSR-4? |
|---|---|---|
| `Nabilet\Modules\` | 86 | да |
| `App\Modules\` | 78 | **нет** — в `composer.json` нет префикса `App\` вообще |
| `NabileT\Modules\` | 40 | **нет** — опечатка; сопоставление префиксов в PSR-4 регистрозависимо |

`composer.json` объявляет ровно пять префиксов: `Nabilet\Core\`, `Nabilet\Modules\`,
`Nabilet\Plugins\`, `Database\Factories\`, `Database\Seeders\` (и `Nabilet\Tests\` в
`autoload-dev`). Итого **121 файл не может быть загружен ни одним автозагрузчиком**.

Хуже, чем «эти файлы не грузятся»: **часть модулей разъехалась по всем трём корням
сразу**, то есть классы внутри одного модуля не видят друг друга:

| Модуль | `Nabilet\` | `App\` | `NabileT\` |
|---|---|---|---|
| `Orders` | 6 | 7 | 5 |
| `Tickets` | 10 | 5 | 5 |
| `Payments` | 7 | 4 | 3 |
| `Events` | 6 | 13 | 0 |
| `Carts` | 0 | 5 | 2 |

Почему ни один гейт не заметил: `lint.php` проверяет только синтаксис;
`verify-purity.php` грузит `Domain/` каждого модуля и чистые подкаталоги `app/Core`
(но не `Models/`, не `Http/`); запустить приложение нечем — `vendor/` нет. То есть
класс дефекта, который обычно ловит только рантайм, здесь решается статически.

**Инструмент `tools/verify-autoload.php`.** Читает `autoload.psr-4` **и**
`autoload-dev.psr-4`, сопоставляет по самому длинному префиксу с учётом регистра и
требует, чтобы файл лежал там, куда префикс отображается. Мутации: новый непокрытый
корень → красный; покрытое имя в неправильном каталоге → красный; контроль (правильный
файл на месте) → зелёный.

**Собственный разбор оказался неверен трижды, и это поучительно:**

1. Ожидаемый путь считался без имени класса: `app/Core/Errors.php` вместо
   `app/Core/Errors/AppError.php` — 143 ложных «misplaced».
2. `dirname(__DIR__)` на Windows возвращает обратные слэши, а пути из обхода каталога
   нормализованы в прямые. Строки различались **только разделителями** и печатались
   неотличимо — сравнение всегда было ложным. Это и был настоящий источник ложных
   срабатываний, а не пункт 1.
3. Инструмент читал только `autoload.psr-4`, поэтому объявил `Nabilet\Tests\`
   непокрытым — **это неверно**: корень объявлен в `autoload-dev`. То есть
   инструмент успел сформулировать ложное утверждение о проекте, пока сам был сломан.

Плюс самопроверка «видел ли сканер известные корни» поймала ошибку в собственном
ключе (`Nabilet\` вместо `Nabilet\Core\`) на первом же запуске. Это ровно тот случай,
ради которого самопроверка и пишется: **сначала виноват проверяющий**.

**`config/nabilet.php` — вторая точка отказа.** Файл жёстко перечисляет девять
провайдеров как `::class`-строки, и **все девять под `App\Modules\`** — под корнем,
который не грузится. При этом `config('nabilet.modules')` **не читает никто**: поиск
по репозиторию не находит ни одного потребителя. Провайдеры существуют на диске, их
пространства имён совпадают со строками — и всё равно не загрузятся. Отказ латентный,
а не видимый.

Реестр модулей — другой: `app/Core/Modules/ModuleManager.php` обходит `app/Modules/*`
и читает `module.json` (их **30**). То есть механизмов регистрации два, и они не
согласованы: реестр знает 30 модулей под `Nabilet\Modules\`, конфиг — 9 под `App\Modules\`.

**Инструмент `tools/verify-module-structure.php`.** Проверяет: у каждого каталога есть
`module.json`; имя манифеста совпадает с каталогом; ни одно `Modules\X\` не ссылается
на несуществующий каталог; и каждая `::class`-строка в `config/nabilet.php` совпадает
с файлом, который называет. Мутации: висячий корень → красный; каталог без манифеста →
красный; имя манифеста не совпадает → красный; `::class` на несуществующий файл →
красный; контроль → зелёный.

**Этот инструмент тоже сначала врал.** Обнаружение «ссылок извне» искало только
`App\Modules\X\` и объявило **25 из 34** модулей «не referenced from nowhere» — а
зарегистрированные модули называются `Nabilet\Modules\X\`. После правки на три корня
осталось 16, после учёта `requires` в манифестах (`Events` требует `organizations`,
`venues`) — 13. Список теперь разделён на два разных по смыслу класса:

* **объявлены манифестом, но никуда не подключены (11):** `AbTesting`, `Admin`, `Ai`,
  `Backups`, `Embed`, `Heatmaps`, `Installer`, `Localization`, `Media`, `Seo`, `Telegram`;
* **нет манифеста и ссылок нет — кандидаты в мёртвый код (2):** `Content`, `System`.

Второй список инструмент **не удаляет**: динамическую загрузку он не видит, а запустить
приложение на этой машине нечем. Удаление — решение, а не уборка.

**Что требуется решить (не сделано намеренно).** Переписать 118 файлов в
`Nabilet\Modules\` — это механическая, но широкая правка: она меняет имена классов
в 118 файлах и должна сопровождаться прогоном линта, тестов, чистоты и обоих новых
гейтов. Консолидация `Carts/` → `Cart/`, судьба `Core/` (имя сталкивается с
`app/Core`, ядром без зависимостей), удаление `Content`/`System` и правка
`config/nabilet.php` — решения уровня архитектуры, их нельзя принимать молча.

## 6. Финальная верификация после сверки: что нашлось и что исправлено

Проход выполнялся уже **после** приведения документации к пакету. Цель — проверить, что

### 6.1 Сломанный HTTP-обработчик ошибок (критично)

`app/Core/Errors/AppError::toProblem()` был переименован в `toResponse()` (переход на
конверт §66), но `bootstrap/app.php` продолжал вызывать **старое имя**:

```php
return response()->json($e->toProblem($requestId), $e->status, [
    'Content-Type' => 'application/problem+json',
]);
```

Последствия, если бы ушло в прод: любой операционный `AppError` падал бы с
`Call to undefined method`, а клиент вместо конверта §66 получал бы `problem+json`.
**Почему не поймали тесты:** `ErrorModelTest` проверяет `AppError` напрямую, а обработчик
живёт в `bootstrap/app.php` и требует установленного Laravel, которого в песочнице нет
(нет доступа к Composer/Packagist). Это была слепая зона.

Исправлено: `toResponse()`, `application/json`, тело фоновой 500-й — тоже конверт §66
(`{"error":{"code":"INTERNAL_ERROR","message":…,"request_id":…}}`) вместо полей RFC 7807.
Добавлен `tests/Unit/ErrorEnvelopeWiringTest.php` — статические проверки бутстрапа плюс
контроль, что все ссылки на классы `Nabilet\Core\*` в нём разрешаются в существующие файлы.
**Проверено, что guard не пустой:** при возврате `toProblem()` тест падает с двумя
ошибками, при откате — снова зелёный.

### 3.24.1 База не обеспечивает ни одного CHECK: миграции написаны под MySQL, стенд — на PostgreSQL

`database/migrations/2026_09_20_001000_add_check_constraints.php` оборачивает все 35
`ALTER TABLE … ADD CONSTRAINT … CHECK` в

```php
return in_array(DB::connection()->getDriverName(), ['mysql', 'mariadb'], true);
```

а `…_001100_add_schema_version_immutability_trigger.php` — так же для единственного триггера.
`.env` содержит `DB_CONNECTION=pgsql`, поэтому обе миграции выходят по раннему `return`.

**Миграция, вышедшая по `return`, всё равно считается накатанной.** `migrate:status` показывает
все 13 как `Ran`, а `tools/verify-migrations.php` даёт 13/13 — потому что этот верификатор
разбирает **файлы** миграций, а не базу. Два независимых зелёных сигнала над базой, которая не
обеспечивает ничего:

```
check    live    0   spec   35   MISMATCH
trigger  live    0   spec    1   MISMATCH
```

Не обеспечиваются: все перечисления статусов (`ck_orders_status`, `ck_payments_status`,
`ck_tickets_status`, `ck_sessions_status`, `ck_schema_status`), неотрицательность денег
(orders/payments/refunds/promo_codes), `ck_inventory_target` (у seat-строки обязан быть seat и
не должно быть standing-зоны — и наоборот) и `ck_tickets_terminal_exclusive`.

Два обстоятельства делают это хуже простого пропуска:

- **Спека нацелена на MySQL, а стенд — нет.** `nabilet_core_spec/migrations.sql` использует
  `DELIMITER //` и `SIGNAL SQLSTATE '45000'` — диалект MySQL. Это не дефект миграций, это
  развёртывание, не соответствующее продукту.
- **001000 пропустил молча**, вопреки собственному docblock («on any other driver they are
  skipped loudly, not silently»). Ничто в выводе не намекало, что только что отброшено 35
  инвариантов. (001100 хотя бы писал в stderr.)

**Исправлено:** 001000 теперь пишет такое же громкое предупреждение в stderr, называя драйвер и
прямо указывая, что `migrate:status` всё равно покажет `Ran`. Проверено вызовом миграции на
живом соединении.

**Открыто — нужно решение, а не заплатка:** либо запускать MySQL (то, что описывает спека),
либо перенести 35 CHECK в PostgreSQL (выражения переносимы) и переписать триггер функцией
`PL/pgSQL`. Оставлять развёртывание, где база не обеспечивает контракт, нельзя.

### 3.24.3 `APP_DEBUG=true` при `APP_ENV=production`

### 3.24.7 Решено: 35 CHECK и триггер теперь обеспечиваются и на PostgreSQL

Пункт 3.24.1 закрыт — не документацией, а исполнением.

**Что сделано.** Оба ограничения-миграции сделаны переносимыми, без изменения поведения на MySQL:

- `2026_09_20_001000_add_check_constraints.php` — `supportsCheckConstraints()` принимает также
  `pgsql`. Все 35 выражений оказались стандартным SQL, поэтому отказывать в контракте на
  PostgreSQL было нечем. Громкий пропуск сохранён для драйверов, которые действительно не умеют
  добавлять CHECK к существующей таблице (SQLite требует пересборки таблицы), а молчаливый
  `return` заменён тем же предупреждением в stderr, что и в 001100.
- `2026_09_20_001100_add_schema_version_immutability_trigger.php` — триггер реализован для обоих
  диалектов: MySQL сохраняет `SIGNAL SQLSTATE '45000'` и `<=>`, PostgreSQL получает функцию
  `PL/pgSQL` с `RAISE ... ERRCODE '45000'` и `IS DISTINCT FROM` (null-безопасный аналог `<=>`).
  Сравниваются те же шесть колонок, текст сообщения тот же.

**Проверено на живой базе:**

```
check    live   35   spec   35   ok
trigger  live    1   spec    1   ok
```

**И проверено, что ограничения именно отклоняют запись, а не просто существуют.** Строка в
`pg_constraint` доказывает наличие, но не запрет. Поэтому минимальная валидная цепочка
(`organizations → venues → halls → hall_schema_versions`) построена внутри транзакции и затем
сломана намеренно — **с контролем на каждую попытку**, потому что отказ что-то значит только
тогда, когда то же самое утверждение проходит при допустимом значении:

| Попытка | Результат |
|---|---|
| `INSERT` версии схемы со `status='bogus'` | **отклонено `ck_schema_status`** |
| контроль: тот же INSERT со `status='published'` | принято — значит отказ дал именно CHECK, а не форма строки |
| `UPDATE` геометрии опубликованной версии | **отклонено: возбуждено исключение неизменяемости** |
| контроль: то же изменение при `status='draft'` | разрешено — значит триггер блокирует только `published`/`archived`, как и задумано |

Транзакция откачена, база осталась в исходном состоянии (`org_probe` отсутствует, остаётся
только ранее существовавшая организация «NABILET Demo»).

**Что осталось.** Миграции записаны в таблице `migrations` как уже выполненные, поэтому на
*этой* базе они применены прямым вызовом; на новой базе `php artisan migrate` применит их
штатно. При этом целевой СУБД спеки остаётся MySQL, а стенд работает на PostgreSQL: теперь
поддерживаются два диалекта, и путь MySQL на этой машине ничем не проверяется, то есть может
тихо деградировать. Это по-прежнему требует решения — либо запускать MySQL, либо зафиксировать
PostgreSQL как поддерживаемую цель.

### 3.24.8 Главный блокер: модуль аутентификации — фасад, а не «не установлен Sanctum»

**Это исправление вывода пункта 3.24.2.** Ранее было зафиксировано: «`laravel/sanctum` отсутствует
в зависимостях». Это верно, но это не главная проблема, и установка Sanctum была бы неверным
решением.

**Что происходит на самом деле.** Все шесть эндпоинтов аутентификации падают. Измерено живыми
запросами:

| Эндпоинт | Живой результат |
|---|---|
| `POST /auth/register` | **500** — `Call to undefined method …UserService::registerCustomer()` |
| `POST /auth/login` (неверные данные) | 401 `{"error":"Invalid credentials"}` — плоская строка, не конверт |
| `POST /auth/login` (верные данные) | дойдёт до `$user->createToken()` → **500**, см. ниже |
| `POST /auth/logout` | **500** — `Auth guard [sanctum] is not defined.` |
| `POST /auth/verify-email` | **500** — `Auth guard [sanctum] is not defined.` |
| `POST /auth/forgot-password` | **500** — `Call to undefined method …UserService::sendPasswordResetLink()` |
| `POST /auth/reset-password` | **500** — `Call to undefined method …UserService::resetPassword()` |

`UserService` объявляет десять методов. `AuthController` вызывает пять из них:

| Вызов из `AuthController` | Существует? |
|---|---|
| `authenticate()` | да |
| `registerCustomer()` | **нет** |
| `sendPasswordResetLink()` | **нет** |
| `resetPassword()` | **нет** |
| `verifyEmail()` | **нет** |

То есть контроллер, его `FormRequest` и `AuthResource` написаны, а сервисный слой под ними — нет.
Ничто этого не поймало: единственные тесты, которые эти классы исполняют, требуют `vendor/`
(это те самые три `tests/Feature/Api/*`, которые в этой среде ни разу не запускались), а
`lint.php` читает только код возврата `php -l` — неопределённый метод это ошибка времени
выполнения, а не синтаксиса.

**Механизм токенов тоже отсутствует, и это не Sanctum.** `AuthController` вызывает
`$user->createToken('customer-token')->plainTextToken` и
`auth()->user()?->currentAccessToken()->delete()` — оба метода из Sanctum. При этом
`laravel/sanctum`: в `composer.json` — нет; в `composer.lock` — 0 вхождений; в `vendor/laravel/` —
отсутствует. Модель `User` не использует трейт `HasApiTokens`, поэтому даже с установленным
пакетом `createToken()` был бы неопределённым методом. Дополнительно:
`app/Modules/Auth/Providers/AuthServiceProvider.php` содержит
`use Laravel\Sanctum\Sanctum;` — импорт класса, которого нет на диске. Сейчас он инертен (на него
ссылается только комментарий), но это ловушка для следующей правки.

**Sanctum — не тот механизм, а не просто отсутствующая зависимость.** Спека вообще не описывает
схему Sanctum:

- `personal_access_tokens` не встречается в `nabilet_core_spec/` **ни разу** (проверено grep по
  всему бандлу);
- спека определяет собственную таблицу сессий:

  ```sql
  CREATE TABLE IF NOT EXISTS user_sessions (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    session_token_hash CHAR(64) NOT NULL,
    …
    UNIQUE KEY uq_user_sessions_token (session_token_hash),
  ```

- `config/auth.php` в собственном заголовочном комментарии фиксирует замысел: «The public API is
  bearer-token based (OpenAPI `bearerAuth`) and tokens are backed by `user_sessions` / `api_keys`,
  not by a session cookie. The guard driver for that is registered by the Auth module in phase P2;
  defining it here would leave a dangling guard if the module were disabled»;
- заготовки для этого уже существуют и не используются:
  `app/Modules/Core/Models/UserSession.php`, `app/Modules/Auth/Domain/UserSession.php`,
  `app/Modules/Auth/Domain/SessionPolicy.php`, `app/Modules/Auth/Domain/SessionDecision.php`.

**Следовательно `auth:sanctum` — это ошибка проводки, а не отсутствующая зависимость.** Установка
Sanctum добавила бы таблицу, которой в спеке нет, и навсегда оставила бы `user_sessions` —
таблицу, которая в спеке есть, с `CHAR(64)`-хешем токена и уникальным индексом — неиспользуемой.
Правильное решение — bearer-guard на `user_sessions`, то есть ровно то, что и записано в
комментарии `config/auth.php`.

**В этой сессии не исправлено.** Это разработка функциональности (драйвер guard'а плюс четыре
метода сервиса), и она меняет механизм аутентификации, поэтому решение зафиксировано, а не
сымпровизировано. Затронуто сейчас: Users, Organizations, Payments (index/show), защищённая
половина Halls, а также `/auth/logout` и `/auth/verify-email`.

### 3.24.9 Решено: контракт §66 нарушался на каждом пути, принадлежащем фреймворку

**Находка.** `AppError` и восемь его подклассов существовали, `bootstrap/app.php` рендерил их
правильно, контракт был задокументирован в трёх местах. Но **ни один контроллер модуля никогда
его не бросал**, а собственные исключения Laravel не отображались — поэтому конверт соблюдался
лишь на тех немногих путях, которые принадлежат домену, и нарушался везде остальном. Измерено
живыми запросами, до правки:

| Запрос | Тело ответа | Почему неверно |
|---|---|---|
| `POST /api/v1/cart/items` `{}` | `{"message":"validation.required","errors":{…}}` | нет объекта `error`, нет `code`, нет `request_id`; сообщение — сырой ключ перевода |
| `GET /api/v1/cart` | `{"error":"session_id required"}` | `error` — **строка**, а не объект |
| `GET /api/v1/halls/xyz` | `{"message":"Hall not found","exception":"NotFoundHttpException","trace":[…]}` | не конверт, плюс утечка трассировки |
| `GET /api/v1/events/999999` | `{"message":"No query results for model [Nabilet\Modules\Events\Models\Event] 999999"}` | утечка внутренней структуры пространств имён |
| `GET /api/v1/organizations/x` | 500 с полной трассировкой | `auth:sanctum`, см. 3.24.8 |

Ни один статический гейт этого не видел: они разбирают файлы, а эти тела порождает Laravel во
время выполнения. Набор тестов оставался зелёным, потому что три теста, которые действительно
исполняют фреймворк, в этой среде не запускаются.

**Что сделано.** Один маппер `app/Core/Http/ApiExceptionRenderer.php`, подключённый в обработчик
исключений `bootstrap/app.php`. Он отображает исключения фреймворка в тот же конверт, которым
пользуется домен:

| Исключение фреймворка | Рендерится как |
|---|---|
| `ValidationException` | 422 `VALIDATION_ERROR`, сообщения по полям в `details.fields` |
| `AuthenticationException` | 401 `UNAUTHENTICATED` |
| `AuthorizationException` / `AccessDeniedHttpException` | 403 `FORBIDDEN` |
| `ModelNotFoundException` (обёрнутый Laravel) | 404 `<RESOURCE>_NOT_FOUND`, из короткого имени класса |
| `NotFoundHttpException` | 404 `NOT_FOUND` |
| `MethodNotAllowedHttpException` | 405 `METHOD_NOT_ALLOWED` |
| `ThrottleRequestsException` | 429 `TOO_MANY_REQUESTS` |
| прочие `HttpExceptionInterface` | свой статус, `HTTP_<status>` |
| всё остальное | 500 `INTERNAL_ERROR`, настоящее сообщение заменено, вызван `report()` |

Два правила, оба проверены живьём:

- **Полное имя класса модели никогда не попадает клиенту.** `Event` → `EVENT_NOT_FOUND` /
  `"Event not found."`. Стандартный 404 Laravel встраивает пространство имён, а это раскрывает
  внутреннюю структуру модулей.
- **Неожидаемое исключение — это баг, поэтому его сообщение заменяется.** Ошибки с
  `operational: false` логируются и отдаются как обобщённый 500. Именно это закрывает утечку
  `APP_DEBUG` на путях API.

Рядом исправлены 34 ответа, написанных вручную, в 8 файлах — включая 15 вызовов `abort(404, …)`,
которые рендерятся в форме Laravel, а не в нашей:

| Файл | Мест |

| `Core/Users/Http/Controllers/UserController.php` | 7 (`['message' => …]` с 4xx — ключа `error` нет вовсе) |
| `Modules/Cart/Http/Controllers/CartController.php` | 6 |
| `Venues/Halls/Http/Controllers/HallController.php` | 5 `abort` |
| `Core/Organizations/Http/Middleware/CheckOrganizationAccess.php` | 3 `abort` |
| `Modules/Tickets/Http/Controllers/CheckinController.php` | 1 |
| `Core/Http/Middleware/RateLimiter.php` | 1 — `retry_after` стоял рядом с `code`, а не внутри `details` |

`CartService` теперь бросает `ConflictError`/`DomainRuleViolation` вместо `\RuntimeException`,

### 3.24.10 Решено: валидационные сообщения были «сырыми» ключами

Каталога `lang/` не было **вообще**, поэтому `__('validation.required')` возвращал сам ключ.
`config/app.php` берёт `locale` из `APP_FALLBACK_LOCALE=ru`, и клиент видел
`{"message":"validation.required"}`.

Исправлено: опубликованы языковые файлы фреймворка и добавлен набор `ru` (язык продукта по
умолчанию) — `lang/ru/{validation,auth,passwords,pagination}.php`, с картой `attributes`, чтобы
сообщение читалось как «Поле «Сессия» обязательно для заполнения», а не называло сырую колонку.

### 3.24.11 Решено: нечисловой идентификатор превращал 422 в 500

`POST /api/v1/cart/items` с `{"session_id":"nope"}` возвращал **500**, а не 422. Причина,
воспроизведённая изолированно:

```
Illuminate\Database\QueryException: SQLSTATE[22P02]: Invalid text representation:
неверный синтаксис для типа bigint: "nope"
```

`sessions.id`, `inventory_items.id`, `tickets.id`, `users.id`, `venues.id` и `roles.id` — все
BIGINT, поэтому правило `exists:sessions,id` выполняет `where id = 'nope'`, и PostgreSQL
отклоняет приведение типа. **Любой клиент мог превратить ошибку валидации в 500, просто отправив
строку.** Исправлено в 6 местах добавлением `bail` + `integer` перед `exists`.

Несущая часть здесь — именно `bail`, а не `integer`: Laravel прекращает проверку остальных правил
атрибута только при наличии `bail`, поэтому одного `integer` недостаточно. В `UserController`
`integer` уже стоял, и это правило всё равно было уязвимо ровно по этой причине.

### 3.24.12 Новый ратчет `tools/verify-error-envelope.php` с мутационным тестом

407 файлов, 0 нарушений, 4 обоснованных исключения. Шесть проверок:

| Проверка | Что ловит |
|---|---|
| E1 | `'error' => '<строка>'` |
| E2 | `'error' => $x->getMessage()` |
| E3 | `'error' => […]` с ключом вне `{code, message, details, request_id}` |
| E4 | `response()->json(…)` с 4xx/5xx и без ключа `error` |
| E5 | `abort(…)` |
| E6 | `exists/unique:…,id` без защиты `bail` + `integer` |

Два свойства, без которых зелёная проверка ничего не стоит:

- **Комментарии вырезаются собственным лексером PHP** (`token_get_all`) с сохранением байтовых
  смещений. Без этого файл самого ратчета и классы, которые *документируют* эти антипаттерны,
  спотыкались бы о собственную проверку — докблоки `ApiExceptionRenderer`, `HallController` и
  `OrganizationController` цитируют плохие формы дословно.
- **`--selftest` мутационно проверяет каждую проверку** на нарушающем фрагменте *и* на корректном
  почти-совпадении, причём в обе стороны. Все шесть проходят; проверка, которая не умеет
  краснеть, не доказывает ничего. Дополнительно утверждается, что докблоки не сканируются, —
  эта регрессия была бы молчаливой.

Записи ратчета обязаны оставаться живыми: запись, нарушение которой уже исправлено, помечается
как **устаревшая** и валит гейт, чтобы исключение не могло тихо разрешить повторное внесение того
же дефекта.

### 3.24.13 Урок: страж чистоты был прав, а адаптер стоял не там

`ApiExceptionRenderer` сначала был написан в `app/Core/Errors/` — рядом с `AppError`, что
выглядело естественным. `tools/verify-purity.php` немедленно упал с **12 нарушениями**:
`app/Core/Errors` охраняется как свободный от фреймворка, потому что `AppError` и его подклассы —
это словарь, на котором говорит *домен*, а доменный класс обязан загружаться вообще без vendor.

Этот класс — противоположность: он существует только чтобы знать типы исключений Illuminate и
Symfony. Это адаптер HTTP-слоя, поэтому он переехал в `app/Core/Http/`, где и живёт
Laravel-осведомлённый HTTP-слой. Чистота вернулась к 99 файлам / 0 нарушений.

Продолжение урока — в тесте: `ErrorEnvelopeWiringTest` утверждал точную строку импорта, поэтому
переезд его сломал. Теперь утверждение не зависит от пространства имён (`preg_match` по импорту),
потому что закрепление расположения в тесте превращает корректный рефакторинг в падение.

### 3.24.14 Что по-прежнему открыто из этой области

- **Перестройка аутентификации** (3.24.8) — bearer-guard на `user_sessions` плюс четыре метода
  `UserService`. Это верхний пункт списка: он разблокирует и 7 маршрутов `auth:sanctum`, и
  последнюю запись `E1` в ратчете.
- **`AuthController` — последнее исключение §66** (плоский `{"error":"Invalid credentials"}`),
  принято в ратчете с обоснованием, потому что править строку до перестройки значило бы трогать
  файл дважды.
- **`/api/v1/cart` против `/api/v1/carts` — это структурное расхождение, а не переименование.**
  Спека моделирует корзину как ресурс с адресацией `{cart}`; приложение адресует корзину по
  `session_id` в теле/строке запроса и вообще не имеет идентификатора корзины в URL.
  `GET /api/v1/carts/{cart}` нельзя получить добавлением префикса — и контроллер, и сигнатура
  сервиса исходят из сессионного ключа. Зафиксировано, не патчилось.
- **`/api/v1/checkin/{validate,use,sync}` против `/api/v1/tickets/checkin/{scan,verify}`** — тот же
  класс расхождения, другое пространство имён. Заодно это API, которое нужно Android-клиенту
  проверяющего, и оно не построено.
