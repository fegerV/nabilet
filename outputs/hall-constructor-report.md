## Ответы на вопросы

**1. Можно ли собрать концертный зал любой конфигурации? — Да.**

Собран зал из трёх типов секторов одновременно:

- **Партер** — сетка 10 × 12 = 120 мест, цены по рядам (`rowPrices: {1: 500000, 2: 450000}` перекрывают цену сектора);
- **Амфитеатр** — дуга (`shape: 'arc'`, раствор 140°, 8 рядов × 16 = 128 мест);
- **Балкон** — сетка 4 × 8 = 32 места;
- **Танцпол** — стоячая зона (`kind: 'standing'`, `capacity: 150`, 2 000 ₽);
- **Сцена, вход, подпись** — статические объекты (`stage` / `entrance` / `label`).

Итог: черновик → публикация → сеанс → инвентарь. В БД: 4 сектора, 23 ряда, 280 мест, 1 стоячая зона (150 мест). В продаже 281 позиция инвентаря суммарной вместимостью 430 билетов.

**2. Можно ли сделать площадку с местами за столом? — Да.**

Сектор `shape: 'table'` = кольцо мест вокруг стола, все места в ряду 1, цена одна на стол. Собран банкетный зал из 6 столов (8/8/10/6/12/8 = 52 места). В БД каждый стол — сектор с кодом A…F, вместимостью и ценой 9 000 ₽; в продаже 52 места. В витрине рисуется 6 колец — см. `storefront-seats-banquet.png`.

Ограничение: **продаются отдельные места за столом, а не стол целиком.** Тип позиции инвентаря `table` запрещён констрейнтом `ck_inventory_type CHECK (type IN ('seat','standing'))`, поэтому «купить стол на 8 человек» одним товаром нельзя.

## Найденные дефекты (исправлены)

### 1. Блокирующий: зал из ≥2 секторов не сохранялся

`POST /halls/{id}/schema-versions/draft` отвечал `422 Seats must not overlap` на любую реальную конфигурацию.

Редактор хранит координаты мест **локально** внутри группы сектора (`Konva.Group({ x: sector.x, y: sector.y })`), а смещение — в `sector.x` / `sector.y`. Сервер сравнивал «сырые» координаты как координаты холста, поэтому два сектора, разнесённых по полотну, выглядели наложенными (оба начинались с одной локальной точки).

- Было: `$x = (float) $seat['x']`
- Стало: `$x = (float) $seat['x'] + $sectorOffsetX` (то же для `y`)

`app/Modules/Venues/Halls/Services/HallService.php` — `validateSchemaPayload()`.

### 2. Координатная карта витрины «слепляла» сектора

`HallSchemaVersion::toInventoryFormat()` нормировал координаты места как `x / canvasWidth * 60` **без смещения сектора**. Все сектора получали одинаковые нормированные координаты, и `CoordSeatMap` рисовал их друг поверх друга.

Замер до исправления (bbox в нормированном пространстве):

```
Партер      x=0..16   y=0..16
Амфитеатр   x=0..41   y=0..18     ← все три начинались с нуля
Балкон      x=0..10   y=0..5
→ НАЙДЕНО 3 наложения
```

После:

```
Партер      x=5..21   y=9..25
Амфитеатр   x=35..76  y=10..28
Балкон      x=5..16   y=31..36
→ 0 наложений
```

### 3. Стабильные коды ошибок не доезжали до клиента

`ValidationError::__construct($errors, string $message, array $context)` жёстко проставлял код `VALIDATION_ERROR`, а `HallService::refuse()` передавал `SCHEMA_EMPTY_PAYLOAD` во **второй** аргумент — то есть в текст сообщения. Комментарий в коде при этом обещал «клиент ветвится на `code`, не на текст».

- `app/Core/Errors/ValidationError.php` — добавлен 4-й параметр `string $errorCode = 'VALIDATION_ERROR'` (обратно совместимо).
- `HallService::refuse()` — код передаётся явно.

Теперь публикация зала без продаваемых мест отдаёт `422 SCHEMA_EMPTY_PAYLOAD`.

### 4. Низ карты зала обрезался на десктопе

`CoordSeatMap`: вьюпорт имел фиксированную высоту `min(58vh, 460px)`, а SVG был `w-full h-auto` и масштабировался от ширины (620:400). При ширине карты 814 px SVG получался 525 px — нижние 65 px срезались `overflow-hidden`. Зал, разложенный до нижнего края полотна (банкет со столами во втором ряду), терял нижний ряд мест: их нельзя было ни увидеть, ни выбрать.

Решение: `preserveAspectRatio="xMidYMid meet"` + `h-full w-full` — холст вписывается во вьюпорт целиком. Замер после: `svgHeight 460 = clipHeight 460`, нижний ряд выше границы на 26 px.

## Наблюдения (не менял)

- **`hall_tables` — мёртвая таблица.** Есть в схеме БД и в моделях, но ни одна запись туда не пишется: геометрия стола живёт только в `schema_json`. Центр и радиус кольца из SQL не достать.
- **`kind: 'table'` в `staticObjects` — чистая декорация** (нет ни вместимости, ни цены). Зал, состоящий только из таких объектов и сцены, корректно отвергается на публикации как пустой.
- **`GET /inventory/sessions/{id}/availability` считает позиции, а не билеты.** Зал на 280 мест + фан-зона на 150 отдаёт `total: 281`; суммарная вместимость — 430 (сумма `capacity`). Для «вместимости зала» нужно суммировать `capacity`.
- **Черновик с пустым payload разрешён осознанно** — проверка непустоты стоит на публикации, а не на автосохранении.
- **Подпись «Танцпол»** на карте витрины чуть выходит за рамку пунктирного прямоугольника: рамка фиксированная (150×90), а настоящей геометрии зоны в payload инвентаря нет.

## Как воспроизвести

```bash
# 1. БД для ручного прогона
docker exec nabilet-mysql mysql -uroot -prootpass -e \
  "CREATE DATABASE nabilet_hall_lab CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   GRANT ALL PRIVILEGES ON nabilet_hall_lab.* TO 'nabilet'@'%';"

DB_DATABASE=nabilet_hall_lab DB_USERNAME=root DB_PASSWORD=rootpass php artisan migrate --force
DB_DATABASE=nabilet_hall_lab DB_USERNAME=root DB_PASSWORD=rootpass php artisan db:seed --force

# 2. Сервер на этой БД
DB_DATABASE=nabilet_hall_lab DB_USERNAME=root DB_PASSWORD=rootpass php artisan serve --port=8099

# 3. Прогон
node .shots/hall-lab.mjs            # 10/10
node .shots/hall-coord-check.mjs    # 0 наложений
node .shots/hall-shots.mjs          # скриншоты в outputs/
DB_DATABASE=nabilet_hall_lab ... php .shots/hall-lab-db.php   # состояние БД

# 4. Регресс-тесты
php vendor/bin/phpunit --filter HallSchemaSectorGeometryTest
```

## Регресс-тесты

`tests/Feature/HallSchemaSectorGeometryTest.php` — 5 тестов:

1. два сектора, разнесённых по холсту, **не** считаются наложенными (падал до исправления №1);
2. сектора, реально совпадающие на холсте, отвергаются;
3. нормировка координат учитывает смещение сектора (падал до исправления №2);
4. сектор-стол превращается в продаваемые места;
5. зал из одних декораций отклоняется с кодом `SCHEMA_EMPTY_PAYLOAD`.

Проверено, что тесты 1 и 3 падают на коде до исправления — то есть действительно ловят регресс.

## Замечание по окружению

`phpunit` использует `RefreshDatabase` и полностью пересоздаёт `nabilet_test_suite`, поэтому сервер и тесты нельзя запускать на одной БД одновременно. Для ручных прогонов держите отдельную базу (`nabilet_hall_lab`).
