**Аудитор:** независимый Application Security Engineer
**Методология:** OWASP ASVS v4.0.3 / OWASP Top 10 (2021), статический анализ исходного кода и конфигурации, трассировка реальных путей выполнения запросов и проверок доступа.

### Подтверждённые сильные стороны (не требуют исправлений)

- **Вебхуки платежей fail-closed.** `WebhookAuthenticator::authenticate()` при отсутствии и секрета, и IP-allowlist бросает `WEBHOOK_NOT_AUTHENTICATED` (HTTP 422), а не пропускает запрос. HMAC сверяется через `hash_equals` (`WebhookSignatureVerifier.php:70-73, 106-108, 124-126`).
- **IDOR в заказах закрыт.** `OrderController::store()` перезаписывает `user_id` из аутентификации для не-staff (`OrderController.php:78-84`); `show/cancel` вызывают `assertCanSee()`. Route-model binding + `whereNumber`.
- **Mass assignment в заказах нейтрализован на уровне сервиса.** `OrderService::createOrder()` собирает массив вручную с константными `status='pending'`, `payment_status='pending'`, `total_amount` считается из `$item->price_amount` из БД (`OrderService.php:62, 72-86`) — клиентский `items.*.price` в расчёт суммы не попадает.
- **Хеширование паролей:** `bcrypt` (`UserRepository::update():67-68`); токены сессий — SHA-256 от 32 криптографически случайных байт (`SessionToken.php:39, 53-58`); модель `User` имеет `$hidden = ['password', 'remember_token']` (`Core/Users/Models/User.php:85`).
- **Отзыв сессий при самостоятельном сбросе пароля** реализован (`AccountRecoveryService.php:109` → `SessionIssuer::revokeAllFor()`).
- **XSS:** во фронтенде нет `v-html`; rich-text выводится текстом (`RichTextWidget.vue`), предпросмотр писем — в `<iframe sandbox>` (`AdminNotificationTemplatesPage.vue`).
- **SQLi:** параметризованные билдеры Laravel; в `StoreOrderRequest` — `bail`+`integer` перед `exists` против MySQL-коэрсии BIGINT (`StoreOrderRequest.php:19-28`).
- **SSRF в исходящих вебхуках** защищён: `WebhookEndpointGuard` блокирует localhost/.local/.internal и частные сети, `Http::timeout()->withoutRedirecting()` (`SendWebhookDeliveryJob.php:122`) — редирект-обход guard'а исключён.
- **QR-билеты:** подпись HMAC с отказом работать секретом < 32 байт; повторное сканирование обрабатывается `TicketScanService`/`CheckinEvaluator` (статусы билета), offline-bundle сверяется по `bundleHash`.
- **Мультиарендность медиа:** `MediaService::findForOrganization()` бросает `NotFoundError` при чужом/несуществующем id (`MediaService.php:314-326`) — корректный fail-closed, IDOR нет.
- **Middleware `admin`** — явный алиас `EnsureAdminRole` (`bootstrap/app.php:109`), применяется к CRUD промокодов, шаблонов билетов, scan/verify чекина.

## 1. НАХОДКИ ДЕТАЛЬНО

### S-01. Фолбэк секрета подписи QR-билетов на APP_KEY — CRITICAL

**Затронутый код:**
- `app/Modules/Tickets/Services/TicketService.php:138-148` (`makeQrSigner()`)
- `app/Modules/Tickets/Services/TicketScanService.php:206-217` (дублированная логика)

```php
$secret = config('nabilet.ticket.qr_secret')
    ?: env('NABILET_QR_SECRET')
    ?: (string) config('app.key');   // ← фолбэк на главный ключ приложения
```

**Путь эксплуатации:**
1. Разработчик/оператор не задаёт `TICKET_QR_SECRET` (в `.env.example` он не обязателен).
2. Система молча начинает подписывать QR билетов HMAC-ключом, равным `APP_KEY`.
3. Любая утечка `APP_KEY` (резервная копия `.env`, лог, дамп конфигурации `artisan config:clear -vvv`, скомпрометированный dev-сервер) даёт злоумышленнику возможность генерировать **подписанные QR-коды любых билетов** — идеальная подделка, неотличимая от настоящей на турникете.
4. Обратный вектор: ротация `APP_KEY` (`php artisan key:generate`) делает все ранее выпущенные билеты невалидными — массовый сбой на входах.

**Возможный ущерб:** массовая подделка билетов, проход на мероприятия без оплаты; отказ системы контроля доступа при плановой ротации ключа; компрометация одного ключа вскрывает два несвязанных контура (шифрование cookie/session + подпись билетов).

**Исправление:**
- Удалить фолбэк на `config('app.key')`. При отсутствии `TICKET_QR_SECRET` — бросать `RuntimeException` при boot (fail-fast), как это уже сделано в соседнем пути `TicketService.php:239-243` («QR code signing key not configured»).
- Вынести `makeQrSigner()` в единый сервис/биндинг, чтобы исключить расхождение логики между `TicketService` и `TicketScanService` (сейчас продублирована комментарием «логика скопирована»).

**Как проверить:**
- Unit: удалить `TICKET_QR_SECRET` из env → приложение должно падать на старте с явной ошибкой, а не подписывать билеты APP_KEY.
- Интеграция: выпустить билет, подделать payload и подписать его значением `APP_KEY` → `verifyQr()` обязан вернуть `null`.
- Статический grep-тест в CI: запрет `config('app.key')` в пространстве имён `Tickets`.

### S-02. Небезопасные значения production-конфигурации по умолчанию — CRITICAL

**Затронутый код:** `.env.example:11` (`APP_DEBUG=true`), `.env.example:40` (`SESSION_DRIVER=file`), `QUEUE_CONNECTION=database`.

**Путь эксплуатации:** типовой деплой «скопировать `.env.example` → `.env`» даёт production-сайт с включённым debug-режимом. Любой необработанный exception (например, 422-конверт вебхука при неверном контент-тайпе, ошибка миграции) возвращает Ignition-страницу со **стектрейсом, переменными окружения, SQL-запросами и фрагментами кода** — включая контексты, где могут мелькнуть customer_email/phone и токены. `SESSION_DRIVER=file` при шардировании/контейнеризации ломает изоляцию сессий и оставляет PII на ФС без шифрования.

**Возможный ущерб:** утечка исходников, конфигурации и персональных данных клиентов через страницы ошибок; захват сессий при доступе к ФС (shared hosting, backup-архивы).

**Исправление:**
- В `.env.example` задать `APP_DEBUG=false`; добавить в deploy-pipeline (CI check или boot-проверку в `AppServiceProvider`) hard-fail при `APP_ENV=production && APP_DEBUG=true`.
- Production-чеклист: `SESSION_DRIVER=redis|database`, `CACHE_STORE=redis`, `QUEUE_CONNECTION=redis`.

**Как проверить:** curl любого маршрута, вызывающего ошибку (например, невалидный JSON на вебхук) — ответ должен быть стандартным JSON-конвертом без стектрейса; grep `.env.example` на `APP_DEBUG=false`; e2e-тест boot-проверки.

### S-03. Смена пароля администратором не отзывает активные сессии — HIGH

**Затронутый код:**
- `app/Modules/Core/Users/Http/Controllers/UserController.php:65-81` (`update()`, поле `password`)
- `app/Modules/Core/Users/Repositories/UserRepository.php:65-73` (`update()` → `bcrypt` + `$user->update($data)`)
- Для сравнения: правильный паттерн есть в `AccountRecoveryService.php:109` → `SessionIssuer::revokeAllFor()`.

**Путь эксплуатации:**
1. Аккаунт пользователя скомпрометирован; злоумышленник держит активный Bearer-токен (Sanctum personal access token живёт до истечения срока независимо от смены пароля).
2. Администратор «гасит инцидент»: меняет пользователю пароль через `PUT /users/{publicId}`.
3. `UserController::update()` вызывает `service->updateUser()` → хеш пароля обновляется, но **ни один токен не отзывается**. Злоумышленник продолжает работать со старой сессией.

**Возможный ущерб:** сохранение несанкционированного доступа после, казалось бы, выполненной процедуры реагирования на инцидент; ложное чувство безопасности у оператора.

**Исправление:** в `UserController::update()` (или в `UserService::updateUser()`) при наличии `password` в `$validated` вызывать `SessionIssuer::revokeAllFor($user->id)` — тем же путём, что и recovery. Дополнительно — revoke при установке `status=banned/inactive`.

**Как проверить:** feature-тест: логин → GET `/me` (200) → админ меняет пароль → GET `/me` со старым токеном обязан вернуть 401. Аналогично для бана.

### S-04. Загрузка SVG и PDF: вектор хранения XSS и вредоносных вложений — HIGH

**Затронутый код:** `app/Modules/Media/Http/Controllers/MediaController.php:61`:

```php
private const ALLOWED_MIMES = 'jpg,jpeg,png,webp,avif,gif,svg,pdf,mp4,webm';
```

**Путь эксплуатации:** организатор (или staff,若有 доступ к upload API) загружает SVG с встроенным `<script>`/`onload=`. Laravel-валидация `mimes:svg` проверяет лишь расширение/магию, содержимое не санитизируется. Если витрина или админка отдаёт файл с того же домена (`Content-Type: image/svg+xml` без CSP `sandbox`/`default-src 'self'` отдельного origin), браузер выполнит скрипт в контексте основного сайта → украденные токены localStorage/Cookie, действия от имени жертвы. PDF может содержать JS-автоматизм и фишинговые формы; MP4/WebM допускают скрытые треки.

**Возможный ущерб:** stored XSS в домене приложения → компрометация сессий покупателей и организаторов; фишинг «от доверенного домена».

**Исправление:**
- Либо убрать `svg` из allowlist, либо прогонять через sanitizier (svgo/HTMLPurifier с SVG-конфигом) при сохранении.
- Отдавать user-upload контент с **изолированного домена** (media.nabilet…) с `Content-Security-Policy: default-src 'none'; sandbox` и `Content-Disposition: attachment` для pdf/svg.
- Проверять реальное содержимое (finfo + перекодировка изображений через GD/Imagick, отсекающая метаданные и payload).

**Как проверить:** загрузить SVG с `<svg onload=alert(1)>` и открыть URL файла — скрипт не должен выполняться (пустой CSP/sandbox-заголовки, отсутствующий onload после санитайза); unit-тест на MediaService::store() с malicious-фикстурами; автоматическая проверка заголовков ответов CDN.

### S-05. Отсутствие rate limiting на валидации промокодов — MEDIUM

**Затронутый код:** `app/Modules/Pricing/routes/api.php:21`:

```php
Route::post('/validate', [PromoCodeController::class, 'check']);
```

Единственный публичный POST-эндпоинт модуля без middleware `throttle` (для сравнения: login/forgot/reset защищены `throttle:auth` — `Auth/routes/api.php:23,33,34`).

**Путь эксплуатации:** скрипт перебирает словарь кодов (`BLACKFRIDAY`, `ORG2026…`), бесплатно получая список действующих скидок и их параметры (процент, лимиты). Кодовая база ULID/случайных кодов устойчивее, но эндпоинт также доступен для enumeration существующих кодов и нагрузки на БД.

**Возможный ущерб:** экономический ущерб (использование найденных скидок), утечка коммерческих условий, подготовка таргет-атак на конкретные кампании.

**Исправление:** зарегистрировать `RateLimiter::for('promo-validate', …)` (например, 5/мин на IP + 10/мин на fingerprint устройства/cart) и повесить `throttle:promo-validate` на маршрут; дополнительно — счётчик неуспешных попыток на session/cart с временной блокировкой.

**Как проверить:** 20 последовательных POST `/promo-codes/validate` → начиная с N-го ожидаем HTTP 429 с конвертом ошибки; тест в `tests/Feature`.

### S-06. Отсутствие rate limiting на эндпоинтах проверки билетов — MEDIUM

**Затронутый код:** `app/Modules/Tickets/routes/api.php:52-53` (`POST /tickets/checkin/scan`, `/checkin/verify`) — доступность только под `['auth:api','admin']`, throttle отсутствует.

**Путь эксплуатации:** хотя прямой IDOR закрыт (маршрут под admin-middleware, комментарий на строке 49 подтверждает историю проблемы), скомпрометированный аккаунт оператора/устройство способно:
1. Перебирать `ticketPublicId` для разведки активных билетов (verify — read-only ответ с данными билета).
2. Провести DoS на БД массовыми scan-запросами (каждый scan транзакционно пишет event).
3. Злоупотреблять «мягким» состоянием: многократные verify увеличивают нагрузку и шум в логах чекина, затрудняя аудит реальных инцидентов.

**Возможный ущерб:** разведка перед физическим мошенничеством на входе, деградация сервиса в день мероприятия, размывание аудита.

**Исправление:** `throttle:checkin-scan` (например, 120/мин на device/user — выше, чем человеческий темп, ниже brute-force); алерт на всплеск «отказов» сканирования с одного устройства/локации; привязка scan к разрешённому device-id, а не только роли.

**Как проверить:** нагрузочный curl-скрипт (121+ запросов/мин) → 429; юнит на конфигурацию limiter'а; алерт-тест в мониторинге.

### S-07. Идемпотентность инициации платежа опциональна — MEDIUM

**Затронутый код:** `app/Modules/Payments/Http/Controllers/PaymentController.php:108,131`:

```php
'idempotency_key' => ['nullable', 'string', 'max:255'],
...
['idempotency_key' => $validated['idempotency_key'] ?? null],
```

**Путь эксплуатации:** двойной клик/ретрай клиента (типично для мобильных сетей) создаёт два pending-платежа по одному заказу. Дальнейшая сверка с провайдером порождает дубли-зачисления или ложные reconciliation-разрывы; при возврате — риск возврата обоих платежей против одной оплаты.

**Возможный ущерб:** двойные списания (прямые финансовые претензии), рассинхрон финансового учёта, нагрузка на поддержку.

**Исправление:** сделать `idempotency_key` обязательным (`required`) для create-payment; хранить unique-индекс `(organization_id, idempotency_key)`; повторный запрос с тем же ключом возвращает существующий платёж (HTTP 200, а не 201).

**Как проверить:** два идентичных POST (один ключ) → один payment-ресурс в БД; тест на unique-индекс; contract-тест OpenAPI (поле стало required).

### S-08. Пустой TRUSTED_PROXIES → доверие заголовкам X-Forwarded-* от любых источников — MEDIUM

**Затронутый код:** `bootstrap/app.php:115`:

```php
at: env('TRUSTED_PROXIES') ? explode(',', (string) env('TRUSTED_PROXIES')) : null,
```

При `null` Symfony-механизм trusted proxies не настроен явно; если вместо этого используется wide-list (`'*'`) или приложение стоит за балансировщиком без настройки, `$request->ip()` читает `X-Forwarded-For` от любого клиента.

**Путь эксплуатации:**
1. Обход `throttle:auth` (5/мин на IP): атакующий ставит случайный `X-Forwarded-For` в каждом brute-force запросе → лимитер считает каждый запрос новым IP.
2. Обход IP-allowlist вебхуков (`WebhookAuthenticator` сравнивает `$request->ip()` с allowlist): поддельный заголовок выдаёт источник за IP YooKassa/Stripe.

**Возможный ущерб:** успешный брутфорс паролей вопреки лимитам; **подделка вебхуков оплаты**, если deployment использует только allowlist без HMAC-секрета (комбинация с конфигурационным дрейфом).

**Исправление:** в production — fail-closed: если `TRUSTED_PROXIES` пуст, не доверять `X-Forwarded-*` вообще (использовать `REMOTE_ADDR`); валидировать значение при boot (CIDR-парсинг); документ деплоя обязывает указывать точные CIDR балансировщика.

**Как проверить:** запрос `/login` с поддельным `X-Forwarded-For` при пустом `TRUSTED_PROXIES` → лимитер всё равно считает один IP (6-й запрос = 429); feature-тест `Request::ip()` в тестовом окружении.

### S-09. Слабая политика паролей — MEDIUM

**Затронутый код:** `app/Modules/Core/Users/Http/Controllers/UserController.php:53,71` (`'password' => 'required|min:8'` / `'sometimes|min:8'`); аналогично в регистрации (`RegisterRequest`).

**Путь эксплуатации:** регистрация `Password123` / `qwertyuiop` проходит; в связке с `throttle:auth` всего 5/мин это замедляет, но не останавливает credential stuffing по словарю топ-10k против большой базы (особенно организаторов/операторов с правами).

**Возможный ущерб:** компрометация учётных записей персонала → операции с заказами, билетами, промокодами, чекином.

**Исправление:** минимум 10–12 символов; проверка на совпадение с email/именем; интеграция с pwned-паролями (k-anonymity API); zxcvbn-скоринг на клиенте + сервере; для ролей staff/admin — обязательная 2FA (в проекте уже есть Telegram-модуль как база).

**Как проверить:** отрицательные тесты регистрации/смены пароля на `12345678`, `password`, пароль == email; положительный на `Correc4t-Horse!`.

### S-10. Rate limiter авторизации хранит счётчики в кэше на базе данных — MEDIUM

**Затронутый код:** `config/cache.php:13` (`'default' => env('CACHE_STORE', 'database')`), `Auth/Providers/AuthServiceProvider.php:78` (`RateLimiter::for('auth', …)`), `.env.example:39-43`.

**Путь эксплуатации:** BruteForce-атака на `/login` означает, что каждый запрос выполняет запись/чтение в таблицу `cache` внутри той же СУБД, которая обслуживает каталог и заказы. Атакующий достигает цели дважды: лимитер деградирует вместе с БД (при shared-базах writes конкурируют с бизнес-транзакциями), а 5-attempts-per-minute превращается в общий тормоз платформы.

**Возможный ущерб:** усиление DoS; снижение реальной эффективности защиты от брутфорса под нагрузкой.

**Исправление:** production-recommended: `CACHE_STORE=redis` (уже указано как recommended — сделать обязательным boot-проверкой при `APP_ENV=production`); альтернативно — отдельный лимитер-сторедж.

**Как проверить:** boot-check бросает ошибку при production+database cache; нагрузочный тест `/login` (100 rps) не влияет на latency каталога.

### S-11. Экранирование LIKE-паттернов через addcslashes — LOW

**Затронутый код:** `app/Modules/Orders/Repositories/OrderRepository.php:115`:

```php
$query->where('customer_email', 'like', '%' . addcslashes((string) $filters['customer_email'], '%_\\') . '%');
```

**Путь эксплуатации:** классический SQL injection исключён (привязка значений PDO). Однако `addcslashes` не добавляет `ESCAPE '\\'` к SQL — в MySQL по умолчанию `\` действительно является escape-символом LIKE, поэтому поведение корректно *для MySQL*, но хрупко при смене движка (PostgreSQL требует явного `ESCAPE`). Оставшийся практический риск: инъекция wildcards не удалена полностью для диалектов без автоэкрана → производительностные атаки (`%!%`) и искажение результатов фильтра.

**Возможный ущерб:** минимальный при текущем стеке; information disclosure/медленные запросы при миграции СУБД.

**Исправление:** использовать `whereRaw("customer_email LIKE ? ESCAPE '\\'", [...])` или пакетный helper, единообразный для всех LIKE-фильтров проекта; добавить тесты с `%`, `_`, `\` во входных данных.

**Как проверить:** фильтр `customer_email=%@%` возвращает 0 строк (символы экранированы), а не всю таблицу; smoke-тест на PostgreSQL-совместимость.

### S-12. Клиентский `items.*.price` в контракте создания заказа — LOW (защита от регресса)

**Затронутый код:** `app/Modules/Orders/Http/Requests/StoreOrderRequest.php:29` (`'items.*.price' => ['required','integer','min:0']`) vs `OrderService.php:62` (сумма считается из `$item->price_amount` из БД).

**Ситуация:** фактической уязвимости нет — сервис игнорирует цену клиента. Но контракт API принимает произвольное поле `price`, которое «как бы» участвует в заказе. Это ловушка для будущих изменений: любой рефакторинг, передавший `$itemData` в `fill()`/`create()` целиком (например, переход на generic mapper), мгновенно откроет mass-assignment цени (строка `'price'` окажется рядом с `total_amount` в `$fillable` модели `Order.php:47-68`).

**Исправление:** удалить `items.*.price` из правил (или принимать строго как `present`-эхо для сверки с серверной ценой и отклонять при расхождении); покрыть тестом «клиент прислал price=1 → total_amount из прайса склада».

**Как проверить:** regression-тест на несоответствие цены; PHPStan-правило, запрещающее spread `$itemData` в создание OrderItem.
