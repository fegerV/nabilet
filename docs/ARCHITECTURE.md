## 1. Архитектурный обзор

**Modular Monolith.** Не микросервисы: транзакционная целостность между корзиной, заказом, оплатой и выдачей билетов — главное требование системы, а распределённые транзакции сделали бы её недостижимой ценой. Внутри — жёсткие границы модулей.

```
NABILET CORE
│
├── app/Core/          ← ядро: без бизнес-логики, без зависимости от Laravel
│   ├── Modules/         ModuleManager, ModuleManifest
│   ├── Hooks/           HookRegistry (actions + filters)
│   ├── Errors/          иерархия типизированных ошибок
│   ├── StateMachine/    generic state machine с guard'ами
│   ├── Tenancy/         OrganizationContext (fail-closed)
│   ├── Support/         Money, QrSigner, helpers (do_action / apply_filters)
│   └── Http/Middleware/ request-id, tenancy, CSP, permission, idempotency
│
├── app/Modules/       ← 30 модулей (27 включены по умолчанию; отключены abtesting, ai, heatmaps)
│   ├── Organizations/  Auth/  Users/  Localization/
│   ├── Venues/  HallSchemas/  Events/  Sessions/
│   ├── Inventory/  Pricing/  Cart/  Orders/
│   ├── Payments/  Tickets/  Checkin/  Notifications/
│   ├── Webhooks/  Media/  Seo/  Analytics/  Embed/  Telegram/
│   ├── Security/  Privacy/  Backups/  Admin/  Ai/  AbTesting/  Heatmaps/
│   └── <module>/
│       ├── module.json          манифест: зависимости, permissions, события
│       ├── StateMachines/       машины состояний домена
│       ├── Models/  Services/  Repositories/  Http/Controllers/
│       ├── Events/  Listeners/  Jobs/  Policies/
│       ├── routes/  migrations/  resources/  Config/
│       └── <Module>ServiceProvider.php
│
└── plugins/           ← сторонние расширения, тот же контракт
```

### Границы зависимостей

Правило без исключений:

```
Modules ──→ Core           (модуль может зависеть от ядра)
Module  ──→ Module         (только через объявленный `requires` и события)
Core    ──→ Modules        (ЗАПРЕЩЕНО — ядро не знает о модулях)
Module  ──→ Module (внутрь) (ЗАПРЕЩЕНО — только через сервис-контракт или хук)
```

Ядро не импортирует ни одного класса из `app/Modules`. Это проверяется линтером архитектуры и является причиной, по которой модуль можно удалить, не трогая ядро.

## 2. Ключевые решения

| # | Решение | Обоснование |
|---|---|---|
| AD-1 | **Ядро без зависимости от Laravel** | Хуки, модули, state machines, Money и подпись QR тестируются без БД и фреймворка. Это не эстетика: критичная логика (гонки, деньги, переходы состояний) проверяется в изоляции и переиспользуется сервисом Checker и Embed-бандлом. |
| AD-2 | **Хуки как публичный контракт расширения** | ТЗ §6 требует WordPress-подобный API. `do_action('order.paid', $order)` понятен автору плагина; `$container->get(HookRegistry::class)->addAction(...)` — нет. |
| AD-3 | **`InventoryItem` — продаваемая сущность** | ТЗ §90. Позволяет разные цены для сеансов, VIP, динамическое ценообразование, возврат одного места — без специальных случаев. |
| AD-4 | **Версия схемы зала неизменяема** | ТЗ §14. Единственный способ защитить исторические заказы. |
| AD-5 | **Деньги — целые minor units** | Сумма билетов + процентная скидка + сервисный сбор = три округления. Float теряет копейки, и итог не сходится с отчётом провайдера. |
| AD-6 | **Мультитенантность fail-closed** | Отсутствие контекста организации бросает исключение, а не расширяет выборку до всех арендаторов. |
| AD-7 | **Идемпотентность на уровне БД** | Уникальные индексы, а не «проверить-и-записать». Именно этот паттерн ломается под конкурентностью. |
| AD-8 | **Публичный каталог — SSR, админка — SPA** | SEO (ТЗ §35–38) несовместимо с клиентским рендерингом каталога. Админка остаётся SPA ради отзывчивости. |
| AD-9 | **Redis опционален** | ТЗ §3: система не должна становиться неработоспособной из-за отсутствия Redis. Все драйверы имеют fallback на database/file. |
| AD-10 | **Outbox для побочных эффектов** | Задача, поставленная в очередь внутри транзакции, либо выполнится для несуществующего заказа, либо потеряется. Outbox пишет намерение в ту же транзакцию. |
| AD-11 | **Остаток — количество, а не состояние** | `inventory_items` хранит `capacity` + `available_quantity`, а не enum. Одна строка inventory продаётся N раз для standing-зоны; количество — единственный источник истины об остатке. Enum этого не выражает. |
| AD-12 | **Инварианты денег и остатка проверяет БД, а не только код** | Проверка пакета на реальном MySQL показала, что `available_quantity = -1` принимался молча. 24 CHECK-ограничения и триггер неизменяемости (`migrations/009_integrity_hardening.sql`) делают нарушение громким. Принцип: если БД может это отклонить — она должна. |

## 3. Расширение: система хуков

### Actions — «произошло событие»

```php
do_action('order.paid', $order);
do_action('ticket.issued', $ticket);
do_action('payment.completed', $payment);
```

Подписчик:

```php
add_action('order.paid', function (Order $order): void {
    // n8n, CRM, Telegram, Email — всё здесь, без правки ядра
}, priority: 20);
```

### Filters — «измени значение»

```php
$price = apply_filters('ticket.price', $price, $ticket);
$meta  = apply_filters('event.meta', $meta, $event);
```

```php
add_filter('ticket.price', fn (int $p) => $p + 300, priority: 20);   // сервисный сбор
```

### Порядок и изоляция

- Приоритеты по возрастанию; при равенстве — порядок регистрации.
- `do_action_safe($hook, $onError, ...)` изолирует падение подписчика. **В денежных потоках используется только он**: сторонний плагин, бросающий исключение, не должен отменять оплаченный заказ.
- `did_action($hook)` и `has_action($hook)` — для интроспекции.

### Почему не только Laravel Events

Laravel Events — это in-process доменные события, и они используются. Но они не дают главного: фильтров с преобразованием значения и приоритетов. ТЗ §6 требует и то и другое.

## 4. Система модулей

### Манифест

```json
{
  "name": "telegram",
  "version": "1.0.0",
  "enabled": true,
  "priority": 175,
  "requires": ["notifications", "tickets"],
  "permissions": [],
  "provides": ["telegram.message_sent"]
}
```

### Граф зависимостей

Порядок загрузки выводится из `requires` топологической сортировкой, детерминированно (приоритет, затем имя). `validate()` отклоняет:

| Проблема | Тип |
|---|---|
| Зависимость не установлена | `missing_dependency` |
| Зависимость выключена | `disabled_dependency` |
| Циклическая зависимость | `dependency_cycle` |

Загрузка с невалидным графом **отказывает**, а не деградирует: «class not found» в середине запроса диагностировать намного дороже, чем понятную ошибку на старте.

Отключение модуля, от которого зависят включённые, запрещено — иначе зависимые модули вызывают сервис, которого нет.

Проверка графа:

```bash
php tools/modules.php --validate
```

Текущее состояние: **27 модулей, 72 объявленных события, граф валиден.**

## 5. Слои внутри модуля

```
Controller  →  Service  →  Repository  →  БД
   HTTP         бизнес-      доступ
   только       правила      к данным
```

| Слой | Ответственность | Запрещено |
|---|---|---|
| Controller | разбор запроса, валидация, вызов сервиса, формат ответа | бизнес-логика, запросы к БД |
| Service | бизнес-правила, оркестрация, управление транзакцией | типы HTTP-запроса, прямой доступ к БД |
| Repository | запросы, обращения к внешним API | бизнес-логика, типы HTTP |

Правило маршрутизации: если вопрос про HTTP (коды, заголовки) — контроллер. Если про бизнес-решение (цена, право, правило) — сервис. Если про БД — репозиторий.

## 6. Мультитенантность

Одна установка обслуживает несколько организаторов (ТЗ §10).

**Fail-closed.** Опасный по умолчанию вариант — «если организация не задана, вернуть всё»: тогда забытый контекст превращается в утечку данных между клиентами. Поэтому:

```php
$context->id();            // бросает TenantContextMissingError, если контекста нет
$context->withoutScope(fn () => ...);   // явный, greppable обход для системных задач
$context->assertOwns($orgId, 'order');  // 404, а не 403 — не подтверждаем существование
```

Обход разрешён только для: инсталлятора, миграций, планировщика, кросс-тенантной отчётности. `withoutScope()` закрывается в `finally`, поэтому исключение не оставит обход открытым.

Разрешение контекста: организация аутентифицированного пользователя → маппинг по `Host` (white-label) → явный обход для системных путей. **Догадки «по умолчанию» нет.**

### ⚠ Где схема пакета ослабляет эту модель

Пакет несёт `organization_id` только у **12 из 56** таблиц. Нет его у `tickets`,
`payments`, `refunds`, `carts`, `cart_items`, `order_items`, `inventory_items`,
`seat_holds`, `ticket_scans`, `sessions`, `payment_transactions`, `notifications`,
`privacy_requests`.

Значит, тенант-скоуп для билетов, платежей и check-in требует JOIN в 2–3 шага:

```
tickets  → orders.organization_id     (2 шага)
payments → orders.organization_id     (2 шага)
```

**Любой запрос, забывший JOIN, — это утечка между арендаторами**, причём именно на самых
чувствительных сущностях. `assertOwns()` защищает только там, где его вызвали; он не
подставляет JOIN автоматически.

Это единственное место, где пакет объективно слабее исходной модели сессии 1, и его нужно
закрыть осознанно — одним из двух способов:

1. добавить `organization_id` в перечисленные таблицы и заполнять его при создании
   (денормализация, но fail-closed становится структурным);
2. оставить схему как есть, но сделать скоуп обязательным в репозиторном слое и покрыть
   каждый маршрут тестом на доступ к чужому тенанту.

До этого решения любой код, читающий `tickets` или `payments`, обязан явно подниматься
до `orders`/`events` и вызывать `assertOwns()`.

## 7. Модель ошибок

Единая иерархия от `AppError` с двумя несущими свойствами:

- **`errorCode`** — стабильный машиночитаемый идентификатор (`SEAT_UNAVAILABLE`, `HOLD_EXPIRED`, `IDEMPOTENCY_KEY_REUSED`). Клиенты, Checker и партнёрские интеграции ветвятся по нему, а не по тексту сообщения.
- **`operational`** — отличает «мир как ожидалось, запрос просто неверный» от «у нас баг». Первое безопасно показать; второе логируется и заменяется generic 500.

Ответ — вложенный конверт по ТЗ §66 и схеме `ErrorResponse` в `openapi.yaml`:

```json
{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "This seat is no longer available.",
    "details": { "inventory_item_id": "99120" },
    "request_id": "a3f1c9..."
  }
}
```

```php
$error->toResponse($requestId);   // AppError → готовое тело ответа
```

`details` опускается целиком, когда сказать нечего, — клиент может полагаться на то, что
отсутствие ключа означает «нет дополнительного контекста», а не «пустой объект».

У `ValidationError` ошибки полей лежат под `details.fields`, чтобы `details` оставался
единым пространством имён для дополнительных ключей:

```json
{"error":{"code":"VALIDATION_ERROR","message":"…",
          "details":{"fields":{"email":["Email is required."]}}}}
```

> **Изменилось относительно сессии 1.** Раньше ответ был RFC 7807
> `application/problem+json` (`type`/`title`/`status`/`detail`). §66 ТЗ и пакет задают
> вложенный конверт, поэтому `AppError::toProblem()` заменён на `AppError::toResponse()`.
> Два формата одновременно жить не могут; старый сохранён только в
> `docs/archive/openapi-rfc7807-superseded.yaml` как история.
>
> Обратите внимание на намеренную асимметрию: внутри свойство называется `errorCode`
> (имя `code` занято `\Exception`), на проводе — `code`. HTTP-статус в теле не
> дублируется: он транспортный.

Отдельно: `TenantContextMissingError` — `operational = false`. Атакующий, прощупывающий обход изоляции, не должен узнать, что обход существует.

## 8. Деньги

`Money` — неизменяемый value object: целые minor units + ISO 4217.

```php
Money::of(5000)->times(2)->plus(Money::of(300));      // 10300 копеек
Money::of(1000)->allocate(3);                          // [334, 333, 333] — сумма сходится
Money::fromDecimal('5 300,00');                        // 530000
```

Инвариант, проверяемый тестом на 1400 комбинациях: **сумма частей `allocate()` всегда равна целому**. Это критично для возвратов по отдельным билетам и распределения выручки.

Смешивание валют бросает исключение. Парсинг десятичных — только строковой арифметикой.

## 9. QR и check-in

Payload: `NB1.<ticketId>.<randomToken>.<HMAC-SHA256>`

Требование ТЗ §30 выполнено буквально: в QR нет email, телефона, цены, пароля, ПД. Сканер — недоверенный клиент у подрядчика; всё читаемое в QR фактически публично.

- Сравнение подписи — `hash_equals()` (константное время), чтобы тайминг-атака не позволила подобрать подпись побайтово.
- `offlineDigest()` даёт устройству возможность валидировать билеты локально, **не получая ключ подписи**: компрометация планшета не позволяет подделать билеты.
- В `Ticket` **нет** перехода `used → issued`. Отмена ошибочного сканирования делается через `revoked` + перевыпуск — с аудит-следом. Возврат в `issued` сделал бы двойной проход возможным из-за ошибки оператора.

## 10. Производительность и кэш

Четыре уровня: request (L1) → Redis (L2) → БД (L3) → HTTP/CDN (L4).

**Явный deny-list в конфиге** (`nabilet.cache.never_cache`): `inventory_items`, `seat_holds`, `payments`, `tickets`, `ticket_scans`.

Причина в том, что устаревшие данные о наличии мест **хуже медленного запроса**: они продают одно место дважды. Список вынесен в конфиг, чтобы будущий оптимизатор увидел запрет, а не выяснял его в инциденте.

Редактор схем залов (ТЗ §64): Canvas, разделение static/dynamic слоёв, spatial-индекс (`seats_spatial_idx`) для отсечения по вьюпорту, цель 60 FPS на 500+ местах.

## 11. Безопасность

| Область | Решение |
|---|---|
| CSRF | Laravel + SameSite cookies; API — токен, не cookie |
| XSS | CSP с per-request nonce (без `unsafe-inline` для скриптов), экранирование Blade, `img-src` ограничен |
| SQL injection | Только параметризованные запросы; raw SQL — исключение с ревью |
| Кликджекинг | `frame-ancestors 'self'`; для Embed — whitelist доменов, `'none'` если не настроен |
| HSTS | Только по HTTPS и только в production |
| Пароли | `argon2id` (bcrypt как fallback) |
| 2FA | TOTP + recovery codes |
| Rate limiting | Раздельно: login 5/мин, checkout 20/мин, checkin **600/мин** |
| IP-фильтры | blacklist/whitelist, CIDR, GeoIP, по областям (login/checkout/api/admin) |
| Секреты | Только `.env`; `api_key` и `ai_providers.api_key` шифруются at rest |
| Audit | Кто, что, когда, IP, объект, старое и новое значение |

Отдельно по ТЗ §79 — четыре критичных участка:

1. **Резервирование мест** — транзакция + `SELECT … FOR UPDATE` + уникальный индекс. Три уровня защиты (см. [`DATABASE.md`](DATABASE.md)).
2. **Платёжный вебхук** — уникальный `provider_event_id`, проверка подписи, allowlist IP провайдера, сохранение сырого тела.
3. **Валидация QR** — HMAC с константным сравнением, отдельный лимит запросов.
4. **Admin и Embed API** — permissions + проверка Origin на бэкенде (не только в браузере).

## 13. Проверка и ограничения песочницы

### Что изменилось после сессии 1

В сессии 1 Docker-демон был недоступен и MySQL-сервера не существовало, поэтому схема
проверялась на SQLite через стабы Laravel Schema. **Сейчас Docker работает, MySQL 8.4.11
поднят, и схема пакета проверена исполнением на нём** — включая конкурентность.

Это закрыло главный пробел: SQLite не воспроизводит поведение MySQL по блокировкам,
уровням изоляции и NULL-семантике уникальных ключей.

### Как проверяется сейчас

| Что | Как | Результат |
|---|---|---|
| Синтаксис PHP | `php tools/lint.php` | **62 файла, 0 ошибок** |
| Ядро (хуки, деньги, state machines, модули, tenancy, ошибки, QR) | `php tests/run.php` | **152 теста, 330 утверждений, 0 падений** |
| Граф модулей | `php tools/modules.php --validate` | **30 модулей, 27 включены, граф валиден, 72 события** |
| DDL пакета | `migrations.sql` → реальный MySQL 8.4.11 | **56 таблиц, 73 FK, 71 UNIQUE, 206 индексов, 24 CHECK, 1 триггер** |
| Эквивалентность DDL | консолидированный файл vs сплит 001–009 | **583 колонки и 24 CHECK совпадают** |
| Матрица конкурентности ТЗ §26 | параллельные клиенты против MySQL | **6 из 6 сценариев PASS** |
| Усиление инвариантов | 37 проб на нарушение | **все пробелы закрыты, легитимные сценарии не сломаны** |
| Контракт OpenAPI | `php tools/verify-openapi.php` | **11 из 11 проверок PASS (77 операций, 71 схема)** |

Матрица §26 в цифрах: 40 одновременных покупателей на одно место → ровно один hold;
60 покупателей на standing-зону 200 → 60 hold и остаток 140; 30 покупателей на
распроданное место → 0 hold; 5 дублей вебхука → одна обработанная доставка;
10 одновременных check-in одного билета → ровно один допуск.

### Что осталось непроверенным (честно)

- **`composer install` по-прежнему невозможен** — sandbox блокирует сеть. `vendor/`
  отсутствует, `php artisan migrate` не запускался. Проверялся DDL пакета, а не
  Laravel-миграции приложения.
- **PHP не может подключиться к MySQL** — sandbox блокирует исходящие сокеты, причём это
  не зависит от бинарника: у PHP 8.4.21 из VertexCMS есть `pdo_mysql` и `mysqli`, но
  соединение всё равно падает на `[2002] доступ к сокету запрещён`. Все проверки идут
  через `docker exec`, что для верификации DDL эквивалентно.
- **Eloquent-модели, observers и guard'ы** не проверены — их нет.
- **Нагрузочное тестирование** не проводилось: 40–60 параллельных клиентов доказывают
  корректность блокировок, но не пропускную способность.

### Границы, которые нужно уважать при работе со схемой

- Пакет несёт `organization_id` только у 12 из 56 таблиц — см. §6. Это не деталь, а
  главный риск изоляции арендаторов.
- MySQL считает NULL в UNIQUE-ключе различным. Два уникальных ключа `inventory_items`
  работают только потому, что ровно одно из `seat_id` / `standing_zone_id` заполнено;
  это теперь закреплено ограничением `ck_inventory_target`.
- Триггер неизменяемости — единственное поведенческое ограничение в схеме. Он создаётся
  через `DELIMITER` и потому требует CLI-клиента; при запуске через PDO оператор
  `CREATE TRIGGER` нужно отправлять целиком одним запросом, без `DELIMITER`.
