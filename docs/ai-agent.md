# ИИ-агент NABILET (MCP-сервер)

Внешний ИИ-агент (Claude Desktop, OpenCode, n8n и др.) подключается к системе
по протоколу MCP (Model Context Protocol) и работает на обычном web-маршруте —
без долгоживущих процессов, то есть на shared hosting.

## Два канала: человек и агент

| Канал | Адрес | Аутентификация | Кто пользуется |
|---|---|---|---|
| Управление доступом и одобрение действий | `POST /api/v1/admin/agent/…` | обычная сессия админки (`auth:api` + `admin`) | человек в браузере |
| Сам протокол MCP | `POST /mcp` | Bearer-токен Sanctum | ИИ-агент |

Токен **нельзя** получить через `/mcp` — только из админки (или с консоли
сервера, если она есть). Разделение намеренное: человек управляет доступом,
агент им пользуется.

## Выдача токена без терминала (шаред-хостинг)

Откройте админку → раздел **«ИИ-агент»** (раздел «Продажи») → **«Выпустить токен»**.

1. Введите название (например, «Дежурный агент Сургут-Концерт»).
2. Оставьте e-mail пустым — токен будет от вашего имени, и агент увидит только
   ваши организации. Чтобы выпустить от имени другого сотрудника, укажите его
   e-mail (он должен состоять в одной с вами организации).
3. Отметьте полномочия:

| Способность | Что разрешает |
|---|---|
| `agent:read` | чтение событий, заказов, продаж (добавляется **всегда**) |
| `agent:events:write` | подготовка черновиков мероприятий |
| `agent:schemas:publish` | подготовка публикации схем залов |
| `agent:refunds:write` | подготовка возвратов |
| `agent:actions:confirm` | исполнение действий, уже одобренных человеком |

4. **Скопируйте токен сразу**: plaintext показывается один раз, в списке — только
   имя, способности и даты. Не успели скопировать — отзовите и выпустите новый.

Токен = ключ к данным организации. Храните его в менеджере секретов или в
переменной окружения ИИ-клиента, но не в конфиге в репозитории.

### Управление токенами

В том же разделе: **«Обновить»** (отзыв старого + выпуск нового) и **«Отозвать»**.
При утечке отзыв действует немедленно; помните, что агент мог успеть скопировать
данные в свой контекст — отзыв не «отматывает» утечку.

Если есть SSH, доступны старые команды:
`php artisan nabilet:agent-token <email> [--list|--rotate|--revoke-all]`;
`--revoke-all` только отзывает (новый не выпускает).

## Инструменты

### Чтение (без подтверждения)

| Инструмент | Назначение |
|---|---|
| `sales_summary` | выручка по оплаченным заказам, статусы заказов, проданные билеты за N дней |
| `search_events` | поиск события → `public_id` |
| `get_event` | детали, сеансы, остатки; описание режется до 2000 знаков |
| `search_orders` | заказы с фильтрами по статусу/событию |
| `get_order` | позиции, контакты, билеты. **QR-пейлоад не выдаётся никогда** |

### Запись (двухфазная, с подтверждением человека)

| Инструмент | Что делает | Нужна способность |
|---|---|---|
| `create_event` | готовит **черновик** (афиша, описание, площадка, дата, схема). Не публикует и не открывает продажи | `agent:events:write` |
| `publish_schema` | готовит публикацию версии схемы (замораживает геометрию); поддерживает `base_revision` против параллельной правки | `agent:schemas:publish` |
| `refund` | готовит возврат по заказу (полный или частичный) | `agent:refunds:write` |
| `confirm_agent_action` | исполняет уже одобренное человеком действие; повтор возвращает сохранённый результат | `agent:actions:confirm` |

**Как это работает**

1. Агент вызывает `create_event` / `publish_schema` / `refund`. Ничего не меняется
   в бизнес-данных — создаётся запись в `agent_actions` со снимком payload.
   В ответе — `action_public_id` и `status: pending_approval`.
2. Агент **обязан сказать пользователю резюме** действия. Человек открывает
   раздел «ИИ-агент» → «Ожидают подтверждения», читает резюме и нажимает
   «Одобрить». Для возврата он дополнительно вводит `REFUND`.
3. Только после одобрения агент вызывает `confirm_agent_action(action_public_id)`.
   Сервер исполняет ровно сохранённый снимок, а не новые аргументы: подменить
   одобренное действие нельзя. Повторный confirm идемпотентен.
4. Срок действия подготовленного действия — 30 минут, затем его нужно создать
   заново. Все шаги пишутся в `audit_logs` (`agent_action_prepared/approved/
   executed/rejected`).

Публикацию самого **мероприятия** и открытие продаж агент не выполняет: это
отдельный переход `EventPublicationService` с проверками (наличие сеанса,
запрет отмены при продажах). Агент создаёт черновик, человек публикует его
штатной кнопкой в карточке мероприятия. Это сознательная граница доверия.

## Подключение клиента

```json
{
  "mcp": {
    "nabilet": {
      "type": "remote",
      "url": "https://ваш-домен/mcp",
      "headers": {
        "Authorization": "Bearer {env:NABILET_AGENT_TOKEN}"
      },
      "enabled": true
    }
  }
}
```

Любой MCP-клиент с remote-транспортом и заголовком `Authorization: Bearer <токен>`.
OAuth не используется. Лимит — 60 вызовов/мин на токен.

## Ограничения

- `sales_summary` не включает посетителей сайта: таблица аналитики глобальная,
  честно срезать её по организации нельзя.
- Инвентарь сеанса без `inventory_items` отдаётся как `inventory: null`.
- Данные всегда ограничены организациями владельца токена; чужие объекты
  неотличимы от несуществующих и при чтении, и при подготовке действий.
- Для возврата нужен успешный платёж по заказу и права провайдера на refund.
