### Рабочее название

**NABILET Core** — «ядро системы продажи билетов».

Это особенно хорошо ложится на вашу существующую идею `nabilet.ru`: публичная часть может называться **NaBilet**, а сама платформа — **NABILET Core**.

# ТЗ — NABILET Core

## 1. Назначение системы

**NABILET Core** — монолитная модульная веб-система для организации полного цикла продажи и контроля билетов:

> мероприятие → площадка → зал → схема → сеанс → места → цена → заказ → оплата → билет → QR → проверка входа → аналитика.

Система должна подходить для:

* концертов;
* театров;
* кино и презентаций;
* конференций;
* фестивалей;
* клубов;
* корпоративных мероприятий;
* спортивных мероприятий;
* выставок;
* лекций;
* танцполов и фан-зон;
* мероприятий со смешанной рассадкой.

Основной принцип:

> **Монолитная система, но модульная внутри.**

Пользователь получает один продукт и одну установку, а разработчик получает архитектуру, в которой функциональность можно заменять, расширять и отключать.

Установка должна быть максимально похожа на WordPress:

# 14. Версионирование схем залов

Критически важное правило.

Нельзя использовать одну изменяемую схему для уже проданных билетов.

Пример:

```text
HallSchema v1
     ↓
Session 1

HallSchema v2
     ↓
Session 2
```

После публикации версии схема становится immutable.

Это защищает исторические заказы от изменения мест.

### Защита от race condition

```text

FOR UPDATE
```

Именно это позволит потом использовать одно ядро не только для `nabilet.ru`, но и, например, отдавать партнерам полноценный **White Label Ticketing**.

### Рекомендуемая технологическая концепция

**NABILET Core = Laravel Modular Monolith + Vue 3/TypeScript + MySQL + Redis + REST API + PWA + Android Checker.**

При этом **Android Checker не нужно делать частью монолита**: он является отдельным клиентом, но использует API монолита.

А самое главное — **схема зала и Ticket Inventory должны быть спроектированы раньше каталога и красивого frontend**. Именно здесь будут самые сложные проблемы: конкурентное резервирование, версии схем, цены, возвраты, синхронизация и check-in.

Если это ТЗ пойдет в Cursor/Claude/Codex для разработки, следующим документом логично сделать уже не описание, а **техническую спецификацию разработки: структуру репозитория, ER-модель БД, все таблицы и индексы, state machines Order/Ticket/Payment, OpenAPI всех endpoint'ов и backlog по этапам**.
