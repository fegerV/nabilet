## 1. Что уже работает (и работает хорошо)

### 1.1 Форма мероприятия

`resources/js/pages/admin/AdminEventFormPage.vue` — заголовок, slug с автогенерацией из
заголовка (с флагом `slugTouched`, чтобы не перебивать ручную правку), краткое и полное
описание, статус, SEO-поля, возрастной лимит, длительность. Секции, живое превью,
`drag&drop`-загрузка.

### 1.2 Афиша — уже с загрузкой файла

Важная деталь: **афиша умеет не только URL, но и загрузку файла** — то, что обычно
добавляют «потом».

- Клиент: drag&drop, превью через `URL.createObjectURL`, лимит 5 МБ, типы `jpeg/png/webp`,
  понятные ошибки.
- Сервер: `StoreEventRequest` → `poster_file` сохраняется как
  `posters/<ULID>.<ext>` на `public`-диске, а URL пишется в `events.poster`.
- Расширение берётся из `hashName()` (**мим-тип, проверенный валидатором**), а не из имени
  файла клиента — правильное решение.
- Есть нормализация `image_url` → `poster`: раньше афиша **молча терялась**, потому что UI и
  API слали `image_url`, а колонка называется `poster`.

Отдельно отмечу `stripNonColumnFields()`: поля `start_date`, `timezone`, `currency`,
`is_featured`, `min_price`, `max_price`, `metadata` валидируются, но **вырезаются** из payload,
потому что колонок нет. Это защита от 500 на несуществующей колонке — и одновременно грабли
(см. §5).

### 1.3 Площадка и цены на рядах

- `AdminSessionsPage.vue`: выбирается зал, затем **только опубликованные схемы**
  (`/halls/{public_id}/schema-versions`, фильтр `status === 'published'`) — нельзя
  продавать билеты по неопубликованному залу. Сеанс берёт `schema_version_id` последней
  published-версии.
- `AdminSessionPricesPage.vue`: цены по рядам, `PATCH /inventory/sessions/{id}/prices`.
  Сидячие группируются по `seat.row_id`, стоячие — по `standing_zone_id`. Ответ содержит
  `rows_updated`, `items_updated` и **`cart_items_updated`** — то есть цены правятся и в уже
  собранных корзинах, а не только в инвентаре. Это правильная деталь, которую легко упустить.

### 1.4 Витрина

Каталог `GET /api/v1/events` + карточка `/events/by-slug/{slug}`; `EventPage.vue` рисует
`poster`, `cover`, описание, JSON-LD и SEO. Публичный статус фильтруется на сервере.

## 2. Дата и время: они не в событии, и это правильно

**По сценарию:** выбрали дату и время начала концерта в форме события.
**По факту:** в форме мероприятия даты нет — и это **осознанное решение**, а не пробел.

Причина в модели данных. Одно событие («Концерт группы Би-2») может иметь несколько сеансов
(гастроль, два вечера, перенос). Дата, зал и схема живут в `sessions`, где все четыре поля
обязательны:

```
sessions.event_id, venue_id, hall_id, schema_version_id, starts_at  — все NOT NULL
```

Поэтому «дата + время + площадка» — это **создание сеанса**, и `AdminEventFormPage` честно
ведёт по кнопке «К сеансам →».

**Что предлагаю (не ломая модель):** не переносить дату в событие (это разрушит
мультисеансность и сломает инвариант иммутабельности схемы зала), а **сделать шаг сеанса
частью одного визарда**. Администратор всё равно проходит: мероприятие → сеанс → цены → билет.
Разница только в том, видит он четыре экрана подряд или один. Это UI-работа, а не изменение
схемы.

**Отвергаю:** добавлять `events.starts_at` «для удобства». Два источника даты = расхождение,
и первый же перенос концерта его проявит. `StoreEventRequest` уже **вырезает** `start_date`
именно по этой причине — возвращать его нельзя.

## 3. Дополнительные фото и видео: отсутствует полностью

Это единственный пункт сценария, которого **нет вообще** — ни в форме, ни на витрине
(`grep video` = 0 в обоих файлах).

При этом схема **уже готова** и не используется:

```sql
media_assets (public_id, organization_id, filename, mime_type, size_bytes,
              width, height, checksum, title, alt_text, variants_json, uploaded_by)
media_links  (media_asset_id, entity_type, entity_id, role, position)
              UNIQUE (entity_type, entity_id, media_asset_id, role)
-- role DEFAULT 'gallery', position — порядок в галерее
```

`media_links` полиморфна **намеренно** — комментарий в DDL прямо говорит: «один asset может
обслуживать афишу мероприятия, фото площадки и страницу CMS». То есть галерея мероприятия
задумана как `media_links(entity_type='event', role='gallery')`. **Новых таблиц не нужно.**

Ключевой вывод по «слишком затратному»: галерея в NABILET **дешевле, чем кажется**, потому
что табличные решения приняты. Дорого здесь — не схема, а загрузка и сжатие изображений.

### 3.1 Видео: надо разделить надвое

«Загрузить видео» и «вставить видео» — принципиально разные вещи, и первое я **отвергаю**:

| Вариант | Что нужно | Вердикт |
|---|---|---|
| **Загрузка видеофайла** | транскодирование, огромный диск, лимиты PHP, CDN | 🔴 **отвергаю** |
| **Ссылка на видео** (Rutube / VK Видео / YouTube) | одна колонка или `media_links` с `role='video'` + embed допустимого домена | 🟢 рекомендуется |

Почему загрузка — тупик: видео на сервере требует транскодинга под браузеры, иначе файл не
проигрывается; это отдельный сервис (ffmpeg) и отдельная инфраструктура. Для анонса концерта
достаточно ссылки. При этом **хранить URL нужно не в HTML-описании**: произвольный HTML в
описании — это XSS, а проект уже держит правило «без `v-html` для пользовательского текста».

**Осторожно с embed:** белый список доменов обязателен. Вставлять `<iframe>` по ссылке из
поля — значит дать возможность поместить на витрину чужой произвольный фрейм.

### 3.2 Что делать (минимум)

1. Подключить `Media` как настоящий модуль (сейчас это скелет, см. §4).
2. Загрузка нескольких изображений → `media_assets` + `media_links(role='gallery', position)`.
3. Одно поле «Видео (ссылка)» → `media_links(role='video')` с белым списком доменов.
4. На витрине — галерея из `role='gallery'` по `position`, видео — `<iframe>` только для
   разрешённых доменов.

**Не нужно:** новая таблица галереи, поле `gallery_json` в `events`, загрузка видео.

## 4. Модуль `Media` — скелет, а не модуль

Это надо знать до планирования галереи:

- `app/Modules/Media/` содержит **только** `module.json` и `MediaServiceProvider.php`.
- `register()` пуст («Bind media services» — комментарий без кода).
- `boot()` вызывает `loadRoutesFrom(__DIR__ . '/../routes/api.php')`, но **каталога
  `Media/routes/` не существует** → провайдер упадёт при загрузке, если его подключить.
- В модуле упадёт и `module.json` (`enabled: true`) — то есть Media включён, но не грузится
  (по состоянию из `REVIEW-spec-bundle.md` §3.25.5 провайдеры модулей вообще не
  регистрируются — значит сейчас это скрыто).

Следствие: **нельзя «доработать модуль Media»** — его надо построить. Но объём известен и
ограничен: контроллер загрузки, сервис, роуты, два поля UI и галерея на витрине. Схема уже
есть.

## 5. «Готова к продаже страница»: кнопки нет, есть только поле в теле запроса

Здесь два дефекта, оба тихие.

**Первый: публикация не является действием.** `EventService::publish()` существует:

```php
public function publish(Event $event): Event
{
    return $this->eventRepository->update($event, ['status' => EventStatus::PUBLISHED]);
}
```

Но **ни один роут и ни один контроллер его не вызывает** — в `app/Modules/Events/routes/api.php`
нет ни `publish`, ни `status`. Единственный способ опубликовать — прислать
`status=published` в теле POST/PATCH, что валидатор разрешает (`in:draft,published,archived,
cancelled`). В админ-списке статус только фильтруется (`{ value: 'published', label: 'В продаже' }`).

**Второй: проверок готовности нет.** `EventService::canPublish()` и `isPubliclyVisible()`
написаны, но **не вызываются нигде**. То есть опубликовать можно событие без сеанса, без
афиши и без цен — и на витрине появится страница, которую нельзя купить.

**Что предлагаю:** эндпоинт публикации, который **отказывает**, если не выполнены условия,
и говорит, каких именно данных не хватает. Проверки — из существующих данных:

| Условие | Источник |
|---|---|
| Есть хотя бы один сеанс в будущем | `sessions` по `event_id` |
| У каждого сеанса есть инвентарь | `inventory_items` по `session_id` |
| У мест есть цены | `inventory_items.price_amount` или `inventory_row_prices` |
| Есть афиша | `events.poster` |

Это то, что превращает «страницу на витрине» в **готовую к продаже**, а не просто видимую.
Отказ должен быть 422 в конверте §66 с перечнем недостающих условий — тогда админ поймёт,
что доделать, а не увидит пустой каталог.

**Не нужно:** автоматическая публикация по расписанию, отдельный статус «ready». Достаточно
проверки в момент публикации.

## 6. Грабли, которые надо знать (иначе тихо потеряете поле)

`StoreEventRequest::NON_COLUMN_FIELDS` — список полей, которые **валидируются и молча
вырезаются** перед записью:

```php
private const NON_COLUMN_FIELDS = ['start_date', 'end_date', 'timezone', 'currency',
    'is_featured', 'min_price', 'max_price', 'metadata'];
```

Правило: добавляя колонку в `events`, **обязательно убрать её из этого списка** — иначе
значение будет приниматься, проходить валидацию и не сохраняться. Это уже случалось с
афишей (`image_url` → `poster`), и тогда баг нашёлся только потому, что кто-то проверил
сохранение глазами.

Отсюда практическое следствие для §3: если для галереи решите добавить поле в `events`
(чего я не рекомендую — есть `media_links`), его надо вычистить из этого списка.

## 7. Целевой сценарий после правок

```
1. Форма мероприятия:  заголовок, описание, афиша (файл), галерея, видео (ссылка), SEO
                      ↓
2. Визард добавляет шаг сеанса:  дата/время → площадка (из заготовок) → схема (published)
                      ↓
3. Цены по рядам  (PATCH /inventory/sessions/{id}/prices)
                      ↓
4. Макет билета под это мероприятие  (events.ticket_template_id + конструктор)
                      ↓
5. «Опубликовать»  → проверка готовности (сеанс, инвентарь, цены, афиша)
                      ↓
6. Страница на витрине, готовая к продаже
```

Шаги 2–4 сегодня существуют, но разрознены. Шаг 5 отсутствует как действие. Шаг 4 не связан
(см. `ticket-designer-delivery-plan.md`). Шаг 1 работает и уже умеет больше, чем ожидалось.

## 8. Приоритет и цена

| Этап | Содержание | Цена | Почему в этом порядке |
|---|---|---|---|
| **1** | Эндпоинт публикации + проверка готовности | мало | Без него «готовая страница» — иллюзия: публикуется что угодно |
| **2** | Визард: объединить событие → сеанс → цены → билет | средне | Сценарий из запроса становится одним проходом |
| **3** | `events.ticket_template_id` + подключение конструктора | мало-средне | См. отдельный план; этап 1 там — убрать внешний рендер QR |
| **4** | Медиа: построить модуль, галерея + ссылка на видео | средне | Схема готова, работы ограничены |
| **5** | (опц.) Массовая загрузка фото, сжатие вариантов | средне | `variants_json` уже предусмотрен |

Явно **вне** плана: загрузка видеофайлов, транскодирование, собственная видео-инфраструктура.
