# Виджет схемы зала Яндекс.Афиши: устройство и парсинг

> Результат полного исследования (октябрь 2026). Рабочие выводы подтверждены
> живыми запросами и разбором фронтенд-бандлов Яндекс.Афиши и её белого лейбла
> «Касса Югра» (surgut.kassa-ugra.ru). Файл-памятка для разработки: как
> устроен виджет, что можно парсить автоматически и как переносить схемы залов
> в конструктор NABILET.

## 1. Экосистема Яндекса: четыре уровня

| Уровень | Домен | Что это |
|---|---|---|
| Витрина афиши | `afisha.yandex.ru` | SSR-страницы событий/площадок на React; статика — `yastatic-net.ru/s3/afisha-frontend/static/{build}/` |
| Виджет билетов | `widget.afisha.yandex.ru` | Хост виджетов покупки (dealer, hallplan); есть `tickets.widget.kinopoisk.ru` для Кинопоиска |
| Сервис билетов | `tickets.yandex.ru` («Яндекс Билеты») | Кабинет организаторов; white-label платформа |
| Белые лейблы | `*.kassa-ugra.ru` и т.п. | Региональные кассы на движке Яндекс.Билетов: ассеты лежат на `tickets.s3.yandex.net`, JSON-LD и цены — те же |

Важно: **Касса Югра — не отдельный источник данных**, это тот же backend.
Её страницы отдают минимальный SSR (без карты мест), картинка «схема зала»
если и есть, то это постер-файл. Искать структуру зала там бесполезно —
проверено разбором их Nuxt-чанков.

## 2. Страница события: что открыто серверу (это мы уже парсим)

`GET https://afisha.yandex.ru/{city}/{rubric}/{slug}` (обычный HTML ответ,
trебуется маскировочный User-Agent) содержит:

1. **JSON-LD (schema.org)** — 2 блока: `MusicEvent`/`Event` и `BreadcrumbList`.
   Из MusicEvent достаются: название, описание, афиша, дата (`startDate`),
   цены (`offers.lowPrice/highPrice`, в рублях), площадь `location` (name,
   address, geo, telephones). Проверено — основа нашего парсера площадок.
2. **Apollo SSR-стейт** (`<script> /** GraphQL APQ payload */…`) — здесь
   вся расписочная часть, включая:

   ```json
   "session": {"date": "2026-11-13", "datetime": "2026-11-13T19:00:00",
               "ticket": {"__ref": "Ticket:NDIzMHw4NDMwMTd8MTYwMzY4fDE3OTQ1Nzg0MDAwMDA="},
               "hallName": ""}
   ```

   `'Ticket:NDIz…'` — base64 от `4230|843017|160368|1794578400000`, то есть
   `activityId|ticketId|placeId|startTimestampMs`. Это устойчивые числовые id:
   наш случай — **event 4230, session 843017, place 160368 (СурГУ)**.
3. **TicketPriceRange** — цены сеанса в **копейках**:

   ```json
   "ticket": {"id": "843017",
              "price": {"__typename": "TicketPriceRange",
                        "currency": "rub", "min": 230000, "max": 280000},
              "saleStatus": "available"}
   ```

Оба пункта 2–3 вырезаются одним регулярным выражением и добавлены к нашему
`POST /venues/import-afisha` (поля `ticket.id`, `ticket.price_min/max`,
рубли). Именно `ticket.id` дальше ищется в DevTools при переносе схемы.

## 3. Покупка и виджет: как кнопка превращается в карту мест

На партнёрских сайтах (в т.ч. белых лейблах) покупка — через **dealer.js**:
`https://widget.afisha.yandex.ru/dealer/dealer.js`. Установлено разбором
скрипта:

* Партнёр размечает ссылки: `<y:ticket data-event-id|data-venue-id|
  data-session-id|data-venue-tag|data-client-key|data-region-id|…>`.
* Сканер читает атрибуты (`data-url-query-params`, `data-date`,
  `data-ignore-sale-available`, ...) и запускает **JSONP-запрос** к
  `https://widget.afisha.yandex.ru/api/tickets/v1/{events|venues|sessions}/sale-available`
  c параметром `{events|venues|sessions}_ids=ID` + `clientKey` + `callback`.
  Ответ: `{"status":"success","result":{"sessions":[{id, key, saleAvailable}]}}`;
  для сеанса ответное `key` подменяет id в URL виджета.
* Кнопке назначается `class="js-yaticket-button"`, `href` — адрес окна
  покупки на widget-хосте, `target="_blank"`.
* Окно общения: iframe ↔ родитель через `postMessage`, источник
  `YandexTicketsMessenger` (события `render`, `close`, `resize` и т. д.).

Итог по правам доступа: у Widget API **есть публичные методы** (sale-available
проверен живьём; для нашего сеанса вернул пустой список без региона-ключа),
но **данные карты мест в этих методах не отдаются**.

## 4. Карта мест (hallplan): эндпоинт подтверждён, но защищён и часто пуст

Реальный запрос карты, снятый пользователем в DevTools (окно покупки Яндекса):

```
GET https://widget.afisha.yandex.ru/api/tickets/v4/sessions/<B64>/hallplan
    ?clientKey=<uuid партнёра>&req_number=<номер запроса>
Referer: https://widget.afisha.yandex.ru/w/sessions/<B64>?widgetName=w1
         &clientKey=<uuid>&embed=true&lang=ru
```

* `<B64>` — тот самый base64-композит из SSR-стейта
  (`Ticket:NDIzMHw4NDMwMTd8MTYwMzY4f…` = `activityId|ticketId|placeId|startTs`,
  декодируется свободно, пример в §2).
* Обязательные заголовки запроса:
  * `x-antibot-token` — JWT вердикта «green», время жизни ≈ 1 час
    (`exp` − `iat` = 3600);
  * `x-csrf-token` — `<hex>:<unixtime>`;
  * куки Яндекса (`Session_id`, `yandexuid`, …) — персональные, в логи/чат
    не выносить;
  * `clientKey` — ключ конкретного партнёра виджета (у каждого свой).
* Ответ: `application/json`; может быть почти пустым (~20 байт, нет плана)
  либо полноценным `with-seats`-планом. Реальный образец (СурГУ, сеанс 843017
  событие Марат Яруллина, kassa-ugra 356653) сохранён у владельца и разобран
  здесь.

## 4.1. Формат hallplan (по живому образцу)

```
result: {
  saleStatus: "available",
  hallplan: {
    totalSeatCount: 512, availableSeatCount: 163,   ← seats[] НЕПОЛНЫЙ: только продаваемые места
    maxTicketsCount: 6, allowCompositeOrders: false,
    hallplanDisplayType: "with-seats",
    categories: [ {id, name: "Партер", priceInfos: [{price, fee, total}]} ],
    levels: [
      {
        id: 1, name: "Партер",
        seats: [ { seat: {place, row, xCoord, yCoord},
                   sourceSeatId, categoryId, priceInfo: {price/fee/total, копейки},
                   extSessionId, sourceLevelId, levelId, admission: false,
                   sourceCategoryId: "Партер-RUB 3080.00" (цена + СБОР!), 
                   categories[], serviceId: "ticketsteam-5466",
                   gatewaySessionId: 356653 } ],
        rows: [ {row: "9", seatCount: 29, xCoord, yCoord} ],  ← ПОЛНАЯ геометрия рядов,
                                                               в т.ч. проданных целиком
        admission: false, availableSeatCount: 65,
        outline: "M13.0 211.0 L869.0 … (SVG-path контура сектора на фоне)",
        prices: [{value: 280000}, {value: 270000}]
      },
      { id: 2, name: "Балкон", … }
    ],
    prices: [280000, 270000, 240000, 230000, 250000],
    sessionServices: [ {serviceName: "ЯБилеты ARM", serviceDescription: "Касса Югра",
                        protocolName: "TICKETSTEAM", serviceId: 5466,
                        gatewaySessionId ↔ id события на белом лейбле,
                        serviceOrganizationInfo: ООО «Тикет Бэст», organizerInfo: ИП…} ]
  }
}
```

Ключевые факты формата:

1. **`levels[].seats[]` содержит ТОЛЬКО продаваемые места** (163 из 512).
   Полная геометрия — в `levels[].rows[]`: номер ряда, `seatCount` и
   координата первого места. Любой конвертер обязан восстанавливать
   полные ряды из `rows[]`, интерполируя позиции по якорям из `seats[]`.
2. **Цены в копейках** и ДВУХСЛОЙНЫЕ: `price` («цена места») и `total`
   (с сервисным сбором `fee`). В NABILET переносится `price`. Для проверки
   соответствия Яндексу при сравнении помните: на витрине Яндекса клиент
   видит **total с сбором** (2700 ₽ места = 2970 ₽ на кассе).
3. **Продавец может быть внешним** (`protocolName: TICKETSTEAM`,
   «ЯБилеты ARM» = касса Югра): тогда `gatewaySessionId` — id события у
   продавца (356653 — это и есть `/events/356653` на kassa-ugra),
   а сервисный блок несёт его реквизиты (юрганизация, оферта).
4. `sourceCategoryId` вида «Партер-RUB 3080.00» — дублирует total с сбором.
5. `outline` — контур сектора в SVG-path: можно рисовать фоном в конструкторе
   (инструмент «Фон»/подложка), если важно сохранить фигуру зоны.
6. `admission: false` у мест — стандартная посадка; `seatGroups: []` и
   `sections: []` в этом примере не используются (уровни вместо секций).
* Без кук/antibot-токена эндпоинт отвечает **400** (проверено). Сервер то же
  самое воспроизвести не может: нужны живые cookies + свежий antibot-JWT,
  то есть участие человека в окне виджета. Программный обход (headless,
  перебор clientKey) — вне правил платформы и нестабилен при релизах.

Отсюда правило: **NABILET не скрейпит hallplan**; политика — экспорт вручную
(§5.1) или подложка-скриншот (§5.2).

## 5. Правильные способы переносить схемы в NABILET

### 5.1 DevTools на живой карте (точная геометрия, используется разработкой)

1. Открыть событие на `afisha.yandex.ru`, кнопка «Купить билет» — окно карты
   мест (или решает как вкладка, или как iframe модалки).
2. F12 → вкладка **Network** → фильтр `Fetch/XHR`; в строке поиска фильтра
   вводить по очереди: `hallplan` (эндпоинт
   `/api/tickets/v4/sessions/<B64>/hallplan` — см. §4), `sections`, `seats`,
   `prices`. Если по `hallplan` тело почти пустое (~20 байт) — у площадки
   нет seat-плана даже в Яндексе, и наша размеченная схема уже полноценнее.
3. ПКМ по строке → Copy → **Copy response** — сохранить в файл
   (например `hallplan.json`).
4. Одна команда до published-версии зала:

   ```
   php tools/hallplan-to-schema.php hallplan.json \
       --hall <public_id зала> --publish
   ```

   Без `--hall` — только сборка schema.json; без `--publish` — черновик
   версии (проверка в конструкторе и кнопка «Опубликовать»). Ручной путь
   тот же: конструктор → «Импорт» → schema.json → сверить → опубликовать.
5. Правки никогда не пишут в опубликованную версию: каждая публикация —
   новая версия (см. `HallSchemaSeeder`/`HallService`).

> Совет для «точь в точь»: снимать hallplan как можно раньше после открытия
> продаж — `seats[]` содержит только ещё не проданные места, и чем их больше,
> тем точнее интерполяция продажных рядов. Вместе с тем `rows[]` всегда
> даёт точное количество мест в каждом ряду, поэтому «первое же снятие»
> обеспечивает корректные ряды и нумерацию даже при больших продажах.

> Подсказка нашему импордатчику: `ticket.id` с предпросмотра (`data.ticket.id`)
> в файле ответа встречается рядом с ценами/сектором — удобно для сверки, что
> взят правильный сеанс.

### 5.2 Скриншот как подложка (мастер-путь для админа, не требует DevTools)

1. Скриншот карты мест (Win+Shift+S), сохранить.
2. Конструктор схемы → инструмент **«Фон»** → загрузить скриншот.
3. Свойства фона → непрозрачность вниз (30–50 %).
4. Инструментами «Ряд» / «Место» / «Сектор» / «Стол» обвести поверх — ряд за
   рядом, координаты мест берутся прямо с подложки, дуги и балконы
   воспроизводятся без искажений.
5. Фон удалить → «Опубликовать». Виджет витрины (CoordSeatMap) рисует места
   по координатам — получится визуально 1:1 с картой Яндекса.

Так построены уже работающие залы: «Нефтяник» (parтер-дуги + бельэтаж +
балкон, 1073 мест) и «Вавилон» (62 банкетных стола, 359 мест).

### 5.3 Чего НЕ делать

* Не оборачивать антибот/CSRF программно (скраперы headless-браузера,
  перебор clientKey) — ломается при каждом релизе Яндекса и вне правил
  платформы. Официальный путь для автоматизации — договор с Яндекс
  Тикетами (у организатора появляется свой clientKey и легальный API).
* Не публиковать распарсенную схему сразу в боевой зал: всегда новая версия
  (immutable published версий — см. `HallService`).

## 6. Конвертер: hallplan → схема конструктора

`tools/hallplan-to-schema.php` — PHP-скрипт без внешних зависимостей:

```
php tools/hallplan-to-schema.py hallplan.json --out schema.json
```

Что делает:

1. Берёт полный ответ (`result.hallplan`) или сам `hallplan`.
2. Для каждого уровня (`levels[]`) собирает сектор: геометрию восстанавливает
   из `rows[]` (там seatCount и стартовые координаты), точные позиции — из
   якорей доступных мест (`seats[]`), промежуточные — кусочно-линейной
   интерполяцией по якорям, крайние — экстраполяцией крайним наклоном;
   ряды без якорей (проданы целиком) — прямой линией от `rows[].xCoord`
   медианным шагом уровня.
3. Разрешает перекрытия (валидатор §50 требует ≥16px по обеим осям) сдвигом
   по y на 1px вниз; id мест делаются уникальными во всей схеме.
4. Цены: точная у доступных мест, рядам без якорей — цена ближайшего
   известного ряда того же уровня («ценомерная лестница»); рыночная
   `rowPrices` + секторная медиана. Копейки Яндекса → копейки NABILET
   (сервисный сбор НЕ переносится — на витрине Яндекса клиент видит total
   со сбором, поэтому цена на кассе и на витрине Яндекса визуально разнится).
5. Проверяет: вывод проходит `HallService::validateSchemaPayload` (OK на
   образце СурГУ: 512 мест, Партер 2800×13/2700×3, Балкон 2500/2400/2300).
6. Результат — в «Импорт» конструктора и публикация новой версией.

Соответствие форматов:

| Яндекс (hallplan) | NABILET (schema_json) |
|---|---|
| `levels[]/{id,name}` | `sectors[]/{id,name,x,y}` |
| `levels[].rows[]/seatCount` | `sectors[].seats[]` (восстановленные ряды) |
| `levels[].seats[].seat.xCoord/yCoord` | `sectors[].seats[]/{x,y}` (px канваса) |
| `priceInfo.price.value` (копейки) | `rowPrices{row}` / `seat.priceMinor` (копейки) |
| `serviceInfo.fee` | не переносится (сбор продавца) |
| типы мест, admission | `seats[].kind: standard/vip/accessible` |
| `outline` (SVG path) | фон конструктора (вручную) |

## 7. Соответствие форматов (устаревшая сводная таблица §6 → см. выше)

| Яндекс (hallplan JSON) | Конструктор NABILET (schema_json) |
|---|---|
| `sections[]/{id,name}` | `sectors[]/{id,name,x,y}` (прямоугольник сектора) |
| `sections[].rows[]` (или seats в ряде) | `sectors[].seats[]/{id,row,number,x,y}` — координаты в px канваса |
| цены `sections[].price` / `rows[].price` / per-seat | `sectors[].priceMinor`, `sectors[].rowPrices{row}, seat.priceMinor` (в копейках) |
| канвас (размеры фона) | `canvas.width/height` |
| типы мест (VIP, маломобильные) | `seats[].kind: standard/vip/accessible` |
| танцпол/standing | сектора `type: standing` + `capacity` |

Ценовая цепочка при продаже: `seat.priceMinor ?? rowPrices[row] ?? sector.priceMinor`
— совпадает с логикой Яндекса (билет → ряд → тариф зоны).

## 7. Чек-лист «перенести зал с Яндекса в NABILET»

1. `POST /venues/import-afisha {url}` — площадка, адрес, координаты, цены,
   `ticket.id` (всё открытое уже в предпросмотре).
2. Создать площадку (если новой нет) → создать зал (название/вместимость —
   сравнить с данными страницы места).
3. Скриншот карты мест → подложка → разметка (§5.2) или DevTools-JSON →
   конвертер (§5.1).
4. Проверка: `eerove` цены по цепочке (место → ряд → сектор), «Выровнять все
   столы» при банкетных залах, сцена/вход/подписи секторов.
5. Новая версия → «Опубликовать» → первый сеанс автоматически получит
   опубликованную схему.

## 8. Хронология исследования (для будущих доработок)

* Проверено живьём: JSON-LD парсер (внедрён), SSR TicketPriceRange (внедрён),
  base64 Ticket composite (декодирован вручную пользователем —
  `activityId|ticketId|placeId|startTs`), `/api/tickets/v1/sessions/sale-available`
  (публичный, JSONP, работает), и — по снимку DevTools — настоящий эндпоинт
  карты `v4/sessions/<B64>/hallplan` (требует antibot-JWT × 1 час, csrf,
  куки и clientKey; для СурГУ ответ ~20 байт — schema-плана в Яндексе нет;
  без кук — 400).
* Разобраны скрипты: `dealer.js` (полный контракт партнёрского виджета),
  `EventPageDesktop.js`, `afisha50.js` (список публичных API-методов витрины).
* Проверены и отклонены: `afisha.yandex.ru/api/events/{uuid}` (400),
  `order/{uuid}` (404), Nuxt-чанки и builds-манифест Кассы Югры,
  изображения страниц (постеры, не схемы).
* Осталось закрытым: тело ответа `hallplan` для залов, где seat-план есть —
  при получении первого нетривиального примера добавить в этот документ
  расшифровку полей и расширить конвертер (§6).
