### Находка: `migrate:fresh` на тест-БД ломается от НАКОПЛЕННОГО состояния
Симптом посреди прогона: `SQLSTATE[42S02] Table 'nabilet_test_suite.migrations' doesn't exist`
на INSERT в `migrations` — таблица исчезает прямо во время `005_payments_tickets` (миграция 5
из 24, ДО нашей `2026_10_15`). Причина — `db:wipe` не вычищает БД с уже накопленными
таблицами+триггерами (`trg_schema_version_*`/`trg_hall_frozen_*`), `migrate:fresh` идёт по
недоочищенной БД. **Лечение: `DROP DATABASE nabilet_test_suite; CREATE DATABASE ...`** — после
этого `migrate:fresh` чистый (проверено: `revision` появляется, exit 0). Это УСИЛИВАЕТ прежнюю
находку про параллельный прогон: две причины «нет таблицы» — (1) чужая сессия, (2) недоочистка
`db:wipe`. Диагностика: `SELECT COUNT(*) FROM information_schema.tables WHERE
table_schema='nabilet_test_suite'` (норма 77) + `information_schema.triggers` (норма 3).

### Слой сервиса
- **`PageDocument` (Domain)** — чистый типизированный объект (slug/title/description/
  contentHtml/publishedAt/updatedAt/robots/organizationName). `canonical()` через
  `function_exists('route')` + fallback `/page/{slug}` — purity-гейт иначе красный,
  и `tests/Unit/...` без `vendor/` не загрузит класс. Докблок явно предупреждает:

  одно — `HoldGrace`).
- **`PageService::forSlug()`** — единственная точка сборки из БД. Фильтр:
  `status='published'` И `published_at <= now()`. `NULL published_at` при
  `published` трактуется как «ещё не опубликовано» (миграция не заставляет
  проставлять дату руками при первой вставке). Описание — `strip_tags()` +
  `preg_replace('/\s+/', ' ')` + `mb_substr(…, 0, 160) . '…'` — UTF-8-safe обрез.
  `organization_name` — ОТДЕЛЬНЫЙ запрос к `organizations` только при наличии
  `organization_id` (JOIN дороже для одной строки).

## «Личный кабинет пользователя» — что есть в текущем локальном дереве

Пользователь спросил «как посмотреть личный кабинет пользователя». Ответил, что в
текущей локальной базе (на `e2586910`) это **только `/#/tickets` («Мои билеты»)**
через гостевой токен `X-Cart-Token` — никакого логина. Полный «Кабинет /
Моя коллекция» (Клуб зрителей, баллы, медали, рефералка) живёт в 36 коммитах
на `origin/main`, не в текущем дереве.

Запустил `php artisan serve` на `127.0.0.1:8000` и попробовал проиграть сценарий
через curl — затык был не в коде, а в **дубликате dev-сервера** (см. ниже).
После починки прогнал полный цикл успешно: hold → checkout → payment →
demo-pay → `GET /my-tickets` вернул билет с QR.

### Главная находка сессии: ДВА `php artisan serve` на порту 8000

`Get-CimInstance Win32_Process` показал:
- PID 7136 `…\php.exe artisan serve` ← **МОЙ** сервер (cwd `C:\Project\nabilet`)
- PID 7692 `…\php.exe artisan serve` ← **СТАРЫЙ** из другой сессии (cwd
  `C:\Users\Professional\nabilet\…\…` — ДРУГОЙ путь проекта, со своим `.env`
  и своей БД)
- по child'у `-S 127.0.0.1:8000 …\server.php` — каждому `artisan serve`
  соответствует свой `server.php` из своего `vendor/`.

PHP встроенный сервер однопоточный: **порт занимает тот, кто первый**, второй
висит без `listen`. Какой из двух процессов реально обслуживает curl — лотерея.
У меня на этой машине это был **старый** (PID 7692), и он отвечал данными своей
БД: `/api/v1/venues` возвращал 1 площадку «СурГУ» из Сургутского сидера,
тогда как dev-БД `nabilet` имела 6 площадок (Дворец искусств «Нефтяник» и т.д.).
Все мои `cart`/`order`/`payment` создавались там — в БД, к которой я
физически не подключён.

**Симптомы, по которым ловится:**
- `/api/v1/venues` показывает 1 venue «СурГУ» (Сургут) — это запись из Surgut-
  VenuesSeeder, и она есть ТОЛЬКО в той чужой БД; в `nabilet` она с `id=5`, а
  не с `id=1`. В тест-БД `nabilet_test_suite` `surgu` count = 0.
- `/api/v1/cart?session_id=1` под свежим токеном → `{"data":null}`, хотя
  в `nabilet` корзина с этим `cart_token` есть.
- Демо-pay возвращает `UNKNOWN_PAYMENT` при наличии строки в `nabilet.payments`
  (видно из tinker) — потому что сервер читает свою БД, а не нашу.

**Лечение:** `Stop-Process -Id 7692 -Force` + `-Id 13032 -Force` (child
`-S 127.0.0.1:8000`). После этого мой сервер (PID 7136, PID 8792) занял порт.
Проверка: `/api/v1/venues` стал отдавать 6 площадок с правильными именами.

### Сценарий заполнения кабинета через curl

```bash
TOKEN=$(python -c 'import uuid;print(uuid.uuid4())')

# 1) Холд места. inventory_item_id — любой 'available' (status проверять через
#    GET /api/v1/inventory?session_id=N). Session 1 уже была вся «sold_out»/
#    «held» после чужих прогонов; перешёл на session 5, inventory_item_id=14.
curl -X POST http://127.0.0.1:8000/api/v1/cart/items \
  -H "X-Cart-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"session_id":5,"inventory_item_id":14,"quantity":1}'
# → 201 { data: { cart_id, id, unit_price, total_price }, cart: {...} }

# 2) Checkout — обязательны customer_email/name/phone (ТЗ §66).
curl -X POST http://127.0.0.1:8000/api/v1/cart/checkout \
  -H "X-Cart-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"session_id":5,"customer_name":"…","customer_email":"buyer@example.com","customer_phone":"+7…"}'
# → { data: { cart_id, order_id (ULID!), session_id, total_amount, currency, items } }

# 3) Инициировать платёж. order_id — ULID из шага 2, idempotency_key — любой.
curl -X POST http://127.0.0.1:8000/api/v1/payments \
  -H "X-Cart-Token: $TOKEN" -H "Content-Type: application/json" \
  -d "{\"order_id\":\"$ORDER\",\"idempotency_key\":\"pay_demo_$(date +%s%N)\"}"
# → { data: { payment: { provider_payment_id:"demo_…", public_id:"01M…",
#                       status:"pending", confirmation_url:"…/#/checkout/demo-pay?…" } } }

# 4) Подтвердить демо-оплату. ВАЖНО: payment_id здесь — это provider_payment_id
```

### Ловушки bash

- **`PPID` — readonly** (parent process ID в любом POSIX-шелле), присваивать
  `PPID=…` упадёт. Для `provider_payment_id` использую `PAY_ID` или `PROVIDER_PID`.
- **`head_limit`/grep под Windows-GitBash** — без NUL-разделителя ломаются на
  именах с пробелами/кириллицей, но для логов это OK.
- **Демо-pay в SPA** работает через `DemoPayPage.vue` (`resources/js/pages/storefront/DemoPayPage.vue:38`),
  который вызывает `confirmDemoPayment(route.query.payment_id)` — query-параметр
  уже приходит как `demo_…`, так что в UI ошибки `NOT_DEMO_PAYMENT` не возникает.
  Она появляется ТОЛЬКО в curl, если скопировать `public_id` вместо
  `provider_payment_id`.
