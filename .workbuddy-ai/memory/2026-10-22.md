## Исправление 500 на промокодах (коммит `d3d55e49`, запушен)

Пользователь: «Продолжай. Исправь ошибки». Прогнал полную батарею — гейты,
`vue-tsc`, unit, phpunit (989/0) были зелёные, поэтому искал ошибки в живых
ответах API, а не в сборке.

**Найдено:** `POST /api/v1/promo-codes/validate` → 500 `INTERNAL_ERROR`;
`GET`/`POST /api/v1/promo-codes` под админом → тоже 500. Причина не в
промокодах, а в резолвинге арендатора — ТРИ независимых дефекта:

1. `ResolveOrganizationContext` читал `users.organization_id` — такой колонки
   нет, членство в `user_organization` (установщик кладёт админа туда).
2. Middleware в ГЛОБАЛЬНОМ стеке, т.е. раньше `auth:api`; `$request->user()`
   смотрит в guard `web`, а API ходит bearer-токеном через guard `api` →
   пользователь не виден даже с валидным токеном.
3. `OrganizationContext` не singleton: `NabiletServiceProvider` объявляет его
   так, но не зарегистрирован (он бутит все модули и вернул бы маршруты вне
   /api/v1). Контейнер давал новый экземпляр каждому — middleware писал в
   свой, контроллер читал пустой.

**Что сделано:**
- `bootstrap/app.php`: `->withSingletons([OrganizationContext::class => …])`.
- `ResolveOrganizationContext::resolveFromUser()`: `apiGuardUser()` (только при
  наличии `bearerToken()`, чтобы не бить в `user_sessions` на публичных
  запросах) + членство из `user_organization` (`orderBy('organization_id')` —
  у таблицы НЕТ колонки `id`).
- `PromoCodeController`: организация для публичной валидации выводится из
  корзины (`carts.session_id → sessions.event_id → events.organization_id`);
  без корзины — 422 с полем `cart_id`, а не 500 и не «первая организация в БД»
  (это была бы утечка чужих скидок). `Session` ищется по `id` ИЛИ `public_id` —
  как в `Session::findOrFailBySessionId()`.
- Тесты: `tests/Feature/Pricing/PromoCodeValidateTest.php` (4),
  `tests/Feature/Core/OrganizationContextResolutionTest.php` (3). В последнем
  `roles` пуст под RefreshDatabase → роль создаётся в самом тесте.
- Обновлён устаревший комментарий в `RateLimitTest` (там было написано, что
  анонимный вызов 500-ит).

**Проверено:** админ 200/201, валидация с корзиной `valid:true` (31 000 коп. на
310 000), без корзины 422, чужой код `not_found`; обход 47 GET-путей API — ни

## vendor/ и node_modules/ в git — нужно решение владельца
- 19 861 файл в индексе, из них 18 627 (93.8 %) — `vendor/` (11 429) +
  `node_modules/` (7 198). Реального кода — 1 234 файла. `.git` = 130 МБ,
  pack = 77 МиБ. Рабочее дерево: vendor 101 МБ, node_modules 354 МБ.
- `node_modules/` есть в `.gitignore`, но отслеживается (git игнорирует правило
  для уже отслеживаемых файлов). Для `vendor/` правила нет вовсе.
- Добавлены 2026-10-05 (три коммита), с тех пор тронуты 7–8 раз, последний раз
  2026-10-11 — в тот же день, что и `composer.lock`. **Сейчас синхронны с lock**
  (127 пакетов, версии совпадают), то есть это не «устаревшая ловушка», а просто
  дубль.
- CI их не использует: `phpunit`-джоба делает `composer install` из lock,
  `frontend` — `npm ci`, Dockerfile предпочитает `composer install` при наличии
  lock. Документация (`README.md`) описывает `composer install`.
- Вариант: `git rm -r --cached vendor node_modules` + правило `vendor/` в
  `.gitignore`; история сохранится, .git не уменьшится без отдельной чистки.
  Риск: у всех, кто делает pull, файлы исчезнут из рабочего дерева — лечится
  `composer install` / `npm ci`. **Не выполнено: нужно решение владельца.**
