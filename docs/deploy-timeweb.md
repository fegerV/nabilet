# Деплой NABILET Core на шаред-хостинг TimeWeb

Целевой стек (заявлен TimeWeb на момент написания):

| Компонент | Ограничение | Влияние на проект |
|-----------|-------------|-------------------|
| PHP       | версия выбирается в панели; на разных серверах доступны разные (8.3 и новее) | Код целится в `^8.3`; проверьте версию именно своего аккаунта, а не по названию тарифа |
| ionCube   | присутствует на хосте | **Не нужен** — в репозитории нет ионкод-файлов |
| Python    | 3.4 (устаревший) | **Не используется** — приложение чисто PHP/Laravel |

> Вывод: «переработка под стек» сводится к **деплой-адаптации под шаред-хостинг**
> (фиксированный докумень `public_html/`, отсутствие composer/npm на сервере),
> а не к даунгрейду кода. Сам код PHP 8.3-совместим из коробки.

---

## 1. Модель размещения

Докумень (DocumentRoot) на TimeWeb жёстко зафиксирован как `public_html/` внутри
**каталога сайта** — у каждого домена он свой, например
`/home/c/ce99429/vertex-art.ru/`. Приложение кладётся **в каталог сайта**, т.е.
на уровень выше `public_html/` (это НЕ «корень аккаунта» `/home/c/ce99429/` и НЕ
сам `public_html/`):

```
/home/c/ce99429/vertex-art.ru/     ← каталог сайта = корень приложения
├── app/
├── bootstrap/
├── config/
├── database/
├── vendor/                        (ставится composer install на сервере)
├── dist/                          (SPA-витрина: dist/index.html + dist/assets)
├── .env                           (создаётся на сервере, НЕ в git)
├── storage/                       (симлинк из public_html/storage)
├── public/                        (канонический фронт-контроллер Laravel)
└── public_html/                   ← DocumentRoot (то, что видно по HTTP)
    ├── index.php                  ← НОВЫЙ тонкий вход (требует ../public/index.php)
    ├── .htaccess                  ← НОВЫЙ rewrite на index.php
    ├── .user.ini                  ← лимиты PHP (обязан лежать ВНУТРИ DocumentRoot)
    └── build/                     (скомпилированный фронтенд, отслеживается в git)
```

Если в аккаунте несколько сайтов — у каждого свой каталог-домен, и приложение
каждого лежит рядом со своим `public_html/`. В `public_html/` допустимы только
статика и тонкий `index.php`; `.env`, `vendor/`, `storage/`, `app/` там оказаться
не должны.

Чувствительные каталоги (`app/`, `config/`, `.env`, `vendor/`, `storage/`) лежат
**вне** DocumentRoot → недоступны по HTTP. Это правильная изоляция; менять её не надо.

В репозитории `public_html/build/` **намеренно отслеживается** (см. `.gitignore`):
на шаред-хостинге часто нет npm, поэтому собранные ассеты приезжают вместе с кодом
через `git pull`.

## 2. Что добавлено в репозиторий

| Файл | Назначение |
|------|------------|
| `public_html/index.php` | Тонкий вход: `require ../public/index.php`. Единый источник правды — канонический `public/index.php` Laravel. |
| `public_html/.htaccess` | Стандартный rewrite Laravel на `index.php` + блокировка dot-файлов (`Require all denied`, Apache 2.4). |
| `public_html/.user.ini` | PHP 8.3-настройки (выкл. `display_errors`, `expose_php=Off`, лимиты загрузки, secure session cookies). Лежит **внутри** DocumentRoot — иначе PHP его не прочитает (скан останавливается на DOCUMENT_ROOT). |

`.user.ini` применяется к web-запросам из `public_html/` и ниже — поэтому он и
лежит в `public_html/` (копия выше DocumentRoot не читается PHP вовсе; web-доступ
к файлу закрыт правилом `<FilesMatch "^\.">` в `.htaccess`). На CLI (`artisan`)
он **не** действует — при необходимости продублируйте лимиты в окружении cron/ssh.

## 3. Проверка PHP 8.3-совместимости (pre-flight)

Код объявляет `"php": "^8.3"` в `composer.json`. Дополнительно проверено отсутствие
PHP 8.4-специфичного синтаксиса:

- property hooks (`private(set)`, `public/get`) — **0** вхождений в `app/`;
- asymmetric visibility — **0** вхождений.

На сервере финально подтвердите после `composer install`:

```bash
composer check-platform-reqs
php -v            # ожидаем 8.3.x
```

## 4. Установка через мастер (рекомендуемый путь)

После выкладки кода открываем в браузере `https://ваш-домен/install` — пошаговый
мастер сам напишет `.env`, прогонит миграции, создаст администратора и его
организацию, слинкует `storage`. Это основной сценарий деплоя на шаред-хостинг.

> **Региональный каталог — под конкретного заказчика.** Система общая, поэтому
> стартовый каталог площадок Сургута (39 площадок) и схемы «Нефтяника»/«Вавилона»
> по умолчанию **не** загружаются. Для развёртывания «Сургут-Концерт» поставьте
> галочку «Загрузить каталог площадок Сургута» на шаге 2 мастера — она запишет
> `NABILET_SEED_SURGUT=true` в `.env` и подключит каталог при сидировании. Для
> другого города оставьте галочку снятой и заполняйте площадки в админке или
> своим сидером. Мастер перезаписывает `.env` из шаблона, поэтому правка файла
> «до установки» не сработает — только галочка.

```bash
# 0. В панели TimeWeb выбрать доступную версию PHP 8.3+, затем по SSH:
php -v

# 1. Выложить код в каталог сайта — тот, что СОДЕРЖИТ public_html
#    (напр. /home/c/ce99429/vertex-art.ru/), не в public_html и не в /home/c/ce99429:
git -C /home/c/ce99429/vertex-art.ru pull origin main

# 2. Зависимости (vendor/ в git НЕ входит — ставим на сервере; мастер его не ставит):
cd /home/c/ce99429/vertex-art.ru
composer install --no-dev --optimize-autoloader

# 3. Права (мастер проверит сам, но заранее лучше открыть):
chmod -R ug+w storage bootstrap/cache

# 4. Открыть в браузере:  https://ваш-домен/install
```

Шаги мастера:

1. **Требования** — PHP ≥ 8.3 (мастер требует именно 8.3: `composer.json` объявляет
   `"php": "^8.3"` — на 8.1/8.2 Composer не поставит зависимости, а мастер
   свалился бы позже на первом же классе с новым синтаксисом; проверено
   smoke-прогоном 2026-11-04), расширения (pdo/mbstring/openssl/json/xml/curl/zip),
   права на запись, отсутствие `.env`. Если что-то красное — поправить на сервере.
2. **База данных** — хост/порт/имя/пользователь/пароль. **На TimeWeb хост БД — НЕ
   `localhost`** (берётся в панели управления, напр. `mysql.timeweb.ru`), порт обычно
   `3306`. Там же — необязательные ЮKassa Shop ID и секретный ключ.
3. **Администратор** — email и пароль (мин. 8 символов).
4. **Прогресс** — миграции → админ → storage → финализация → «Установка завершена».

Мастер выполняет под капотом именно то, что раньше делалось вручную, и закрывает
ряд ловушек шаред-хостинга (все — проверены e2e-прогоном на чистой копии без
`.env`, 2026-11-04):

- пишет `.env` со сгенерированным `APP_KEY`; в шаблон также входят
  `DB_CHARSET=utf8mb4` / `DB_COLLATION=utf8mb4_unicode_ci` (без них MySQL 8 падал
  `Unknown collation: ''` на первом шаге `migrate`), `CACHE_STORE=database` с
  флагом `NABILET_ALLOW_DATABASE_CACHE=true` (разрешение сторожа прод-конфига);
- **гарантирует рабочий `APP_KEY` до записи `.env`** (`PreinstallAppKey`): ключ
  генерируется на буте и персистится в `storage/`, иначе `GET /install` отвечал
  500 `MissingAppKeyException` — форма, которая этот ключ и создаёт, была
  недостижима;
- **включает файловые драйверы сессий/кеша до записи `.env`**
  (`PreinstallDrivers`): дефолты Laravel — `database`, а хост БД на этом шаге ещё
  неизвестен, каждый запрос падал `SQLSTATE[HY000] [2002]`; каталоги
  `storage/framework/{sessions,cache/data}` создаются явно;
- **подменяет in-memory-конфиг БД перед `migrate`** (включая charset/collation) —
  иначе миграции уходили на boot-значения (`127.0.0.1`/`forge`) и падали;
- снимает лимит `max_execution_time` на время установки (`set_time_limit(0)`):
  bcrypt-сидеры на шаред-хостинге не влезают в дефолтные 30 секунд HTTP-запроса;
- создаёт пользователя-админа **и его организацию** (приложение multi-tenant: без
  организации tenant-scoped запросы падают с `TenantContextMissingError`);
- `storage:link` и `db:seed` запускаются в fail-soft режиме;
- таблицы `cache`/`cache_locks` создаёт миграция `2026_09_19_000000_000_cache` —
  throttle на `POST /install` и кеш работают на дефолтном `CACHE_STORE=database`
  сразу после установки.

После успеха создаётся `storage/install.lock`, и мастер **перестаёт существовать
как маршрут**: `routes/web.php` не регистрирует `/install`, поэтому повторный
заход даёт брендированную 404, а `POST` — 405 (маршрута для этого метода нет).
Одновременно сбрасывается кеш маршрутов (`route:clear`) — правило действует и
если маршруты были закешированы до установки.

Также после установки автоматически удаляются диагностические файлы, которые
могли оказаться в docroot **вне архива**: `info.php`, `phpinfo.php`,
`install.php` и legacy-каталог `install/` (только с точкой входа внутри).
Список удалённых путей возвращается в JSON ответа `POST /install` в поле
`removed_setup_files`. Для уже установленного сайта, куда просто залили новый
zip (мастер не запускается), та же зачистка выполняется один раз на версию
приложения при первом запросе — `InstallerServiceProvider` пишет метку
`storage/framework/setup-purged-<версия>.marker`. Удаление идёт по белому
списку имён в двух корнях (корень проекта и `public/`), символические ссылки
не трогаются.

### Ограничения и нюансы (важно)

- **MySQL 5.7 — рабочий, но degraded режим.** CHECK-ограничения исполняются
  только с **MySQL 8.0.16+ / MariaDB 10.2.1+**. На 5.7 сервер принимает
  `ALTER TABLE ... ADD CONSTRAINT ... CHECK`, но молча его игнорирует, а
  `migrate:status` показывает миграцию как «Ran». Это не ломает установку и не
  мешает ручному тестированию: уникальные индексы, транзакции и бизнес-правила
  PHP продолжают работать. Но БД перестаёт быть вторым барьером для сумм,
  статусов и несовместимых состояний билета. Мастер теперь показывает
  предупреждение при «Проверить подключение» и пишет его в `/install/log`.
  **Для реальных продаж переведите аккаунт на MySQL 8.0+** (у TimeWeb это
  новый сервер/тариф; версия зависит от конкретного аккаунта, а не от названия
  тарифа). Триггеры (`trg_schema_version_*`) на шаред-хостинге часто не
  создаются по той же причине — это уже учтено как defense-in-depth.
   Узнать фактическое состояние конкретного аккаунта можно без догадок:
   `GET /api/v1/admin/system/status` → `checks.database_invariants` показывает
   причину: версию сервера, найденные CHECK и наличие триггера. Публичный `/api/v1/health`
   намеренно остаётся в контракте и не становится «degraded» из-за этого
   известного ограничения хостинга.
- **Триггеры БД могут не создаться на шаред-хостинге.** Миграции
  `2026_09_20_001100_*` и `2026_10_06_000100_*` создают MySQL-триггеры через
  `CREATE TRIGGER`; на шаред-хостинге это часто падает с `ERROR 1419` (binary
  logging + нет прав SUPER). Мастер **не прерывается** — триггеры опциональны
  (defense-in-depth), те же правила защищены на уровне приложения.
- **`composer install` обязателен при git-выкладке** — `vendor/` не коммитится.
  Альтернатива — готовый архив установки (собирается скриптом
  `scripts/build-hosting-zip.ps1`): в нём `vendor/` и собранная витрина
  `dist/` уже внутри, `composer install` и `npm run build` на хостинге
  не нужны; каталоги `tests/`, `tools/`, `docs/`, `.git` в архив не входят.
  **Архив распаковывается в КАТАЛОГ САЙТА — тот, что содержит `public_html/`,
  а НЕ в сам `public_html/`.** В архиве `public_html/` содержит только публичные
  файлы (`index.php`, `.htaccess`, `.user.ini`, `robots.txt`, `favicon.svg`,
  `installer-tailwind.js`, `images/`, `assets/`); приложение (`app/`, `config/`,
  `vendor/`, `storage/`, `dist/`, …) лежит на уровень выше — вне DocumentRoot.
  Хранилище новой установки пустое (только `.gitignore`), рабочих файлов и
  резервных копий в архиве нет. Пример для `/home/c/ce99429/vertex-art.ru/`:

  ```bash
  cd /home/c/ce99429/vertex-art.ru                 # НЕ public_html!
  unzip -q ~/nabilet-hosting-v1.16.0-20261125-034321.zip  # создаст/перезапишет public_html/ и соседние каталоги
  rm -f public_html/index.html                     # заглушка хостинга, если есть
  # проверка: ./app/, ./vendor/, ./storage/ лежат ЗДЕСЬ; ./public_html/index.php — внутри docroot; .env нет
  chmod -R ug+w storage bootstrap/cache
  ```
- **Проверьте обработчик PHP после распаковки.** В зависимости от выбранной
  версии PHP TimeWeb подключает CGI/FPM-строки в `.htaccess` через панель;
  архив приезжает с generic-конфигом, поэтому если панель не дописала строки
  автоматически, сайт может отдать исходник `index.php` вместо страницы.
  В таком случае зайдите в панель → PHP → «применить» (панель перепишет
  `.htaccess`) или сверьте конфиг с бэкапом.
  **Проверка — не «страница открылась», а ответ API:**
  `curl -s https://домен/api/v1/health` должен вернуть JSON с
  `"version":"1.16.0"`; исходник PHP в ответе означает, что обработчик не
  подключён.
- **ЮKassa опциональна** — поля можно оставить пустыми; платежи заработают после
  заполнения в настройках.
- **CSRF на `/install` отключён** (`bootstrap/app.php` →
  `validateCsrfTokens(except: ['install','install/*'])`): это одноразовый pre-auth
  эндпоинт, доступный только до `install.lock`.
- **Кеши.** Мастер их не прогревает. Для прод-режима после установки:
  ```bash
  cd /home/c/ce99429/vertex-art.ru
  php artisan config:cache
  php artisan route:cache
  php artisan view:cache
  ```

### Ручной fallback (если мастер недоступен)

```bash
cd /home/c/ce99429/vertex-art.ru
```

## 5. Фронтенд (активная сборка)

- `vite.config.ts` — активная конфигурация приложения: `npm run build` создаёт
  `dist/index.html` и `dist/assets/*`. Laravel отдаёт этот SPA-файл из `routes/web.php`
  и SEO-роутов; после изменения Vue-кода именно `dist/` должен попасть в релиз.
- `vite.config.js` — legacy-конфигурация для отдельного набора ассетов в
  `public_html/build/`; она не является источником активной страницы SPA. Не
  запускайте её вместо `vite.config.ts` для production-сборки.
- Демо-страницы `ticket-builder.html` и `hall-editor.html` вместе с их копиями и
  ассетами удалены; отдельно публиковать их больше не нужно.

```bash
npm ci
npm run build
```

## 6. Очередь и расписание (обязательно для писем и вебхуков)

Транзакционные письма и исходящие вебхуки ставятся в database queue. После
развёртывания примените миграции, включая `jobs` и `failed_jobs`:

```bash
php artisan migrate --force
```

Настройте `.env` — значения ниже взять у вашего SMTP-провайдера; реальные
пароли не хранить в git:

```dotenv
QUEUE_CONNECTION=database
MAIL_MAILER=smtp
MAIL_HOST=<SMTP-хост>
MAIL_PORT=587
MAIL_USERNAME=<SMTP-пользователь>
MAIL_PASSWORD=<SMTP-пароль>
MAIL_ENCRYPTION=tls
MAIL_FROM_ADDRESS=<подтверждённый адрес отправителя>
MAIL_FROM_NAME="${APP_NAME}"
```

Планировщик запускает worker очереди порциями (50 секунд каждую минуту) и
поднимает отложенные повторы вебхуков. Установите cron в панели TimeWeb:

```cron
* * * * * cd /home/c/ce99429/vertex-art.ru && php artisan schedule:run >> /dev/null 2>&1
```

При первом развёртывании (и после добавления новых шаблонов) создайте системные
шаблоны писем; существующие тексты сидер не перезаписывает:

```bash
php artisan db:seed --class='Database\\Seeders\\NotificationTemplateSeeder' --force
```

После изменения `.env` очистите/пересоберите config cache, затем проверьте
`php artisan schedule:list` и выполните тест-покупку на реальный SMTP-ящик.

### Каталог площадок Сургута

Мастер установки запускает `db:seed --force`, а `DatabaseSeeder` первым делом
вызывает `SurgutVenuesSeeder` — 39 площадок Сургута (филармония, ДИ «Нефтяник»,
СурГУ, клубы и залы) уже заведены, отдельная команда не нужна.

Это только строка `venues`: ни залов, ни схем, ни событий. Публичные страницы
`/venue/{slug}` и `/sitemap-venues.xml` появляются позже — когда в площадке
заведено хотя бы одно опубликованное событие (пустая страница отвечает 404, и
адрес в карте сайта, ведущий на 404, — ошибка для поисковика).

Повторный запуск безопасен и ничего не затирает: ключ — `slug`, а уже
существующие площадки пропускаются, поэтому правки описаний и адресов,
сделанные в админке, сохраняются. Запустить вручную (например, чтобы вернуть
удалённую по ошибке площадку):

```bash
php artisan db:seed --class='Database\\Seeders\\SurgutVenuesSeeder' --force
```

Площадки ложатся в организацию администратора; если в базе их несколько и нужна
конкретная — задайте `NABILET_SEED_VENUES_ORGANIZATION_ID=<id организации>`.

## 7. Резервное копирование и восстановление

### Подключение Яндекс.Диска без терминала

Откройте «Бэкапы» в админке. Там есть Redirect URI, который надо зарегистрировать
в приложении Яндекс OAuth, и пошаговая инструкция:

1. Создайте приложение на <https://oauth.yandex.ru/client/new> (тип — веб-сервис).
2. Вставьте Redirect URI со страницы бэкапов в поле **Callback URI** приложения —
   точь-в-точь, без завершающего слэша. Для локальной проверки это
   `http://127.0.0.1:8000/admin/backups/oauth`, на боевом сайте —
   `https://ваш-домен/admin/backups/oauth`.
3. Включите право доступа к Яндекс.Диску (чтение и запись), сохраните приложение.
4. Скопируйте ClientID в форму на странице бэкапов и нажмите «Подключить Диск».
5. Разрешите доступ на странице Яндекса — токен придёт во фрагменте URL на
   `/admin/backups/oauth`, страница сохранит его в базу зашифрованным (Crypt +
   `APP_KEY`) и вернёт вас обратно. Токен никогда не показывается целиком и не
   пишется в логи.
6. Кнопка «Проверить соединение» делает дешёвый запрос к API Диска.

Старый способ через `.env` (`YANDEX_DISK_OAUTH_TOKEN`) оставлен как фолбэк:
существующие установки продолжают работать без миграции. Значение из админки
перекрывает `.env`.

### Три режима

| Режим | Что содержит | Когда |
|---|---|---|
| `db` | дамп `db_<база>_YYYY-MM-DD_HH-MM-SS.sql[.enc]` | ежедневно, RPO ≈ сутки |
| `files` | `storage/app/public` + `.env` (только при `NABILET_BACKUP_ENCRYPTION_KEY`) + ZIP | по мере изменения афиш |
| `full` | БД + файлы + конфигурация в одном архиве | еженедельно, для полного восстановления |

Кнопка админки ставит задачу в очередь (`RunBackupJob`) и возвращает 202:
`mysqldump` и загрузка не выполняются внутри HTTP-запроса. Результат виден в
блоке «Последний запуск». На шаред-хостинге очередь разбирается кроном
(см. раздел про cron), поэтому убедитесь, что `schedule:run` настроен.

### Расписание и политика

`backup:run` стоит в расписании (`routes/console.php`: ежедневно 03:00,
`withoutOverlapping`). Ротация — только после успешной выгрузки, только что
созданная копия защищена от удаления. Очереди `db` / `files` / `full`
считаются отдельно (по 7–30 последних копий, `NABILET_BACKUP_KEEP`).

Практика 3-2-1: три копии, два носителя, одна вне сервера. Шифруйте архивы
(`NABILET_BACKUP_ENCRYPTION_KEY`), ключ храните отдельно от бэкапов. Бэкап старше
26 часов поднимает алерт `system:selfcheck`.

Разовые команды по SSH (если он есть):

```bash
php artisan backup:run --mode=db
php artisan backup:run --mode=files
php artisan backup:run --mode=full --keep-local
php artisan backup:rotate --local-only --keep=7
```

### Восстановление

Скачайте архив на Яндекс.Диске (веб-интерфейс, WebDAV или REST API с токеном).
Для дампа БД:

```bash
mysql -h<host> -u<user> -p <dbname> < db_<база>_YYYY-MM-DD_HH-MM-SS.sql
```

Для `files` / `full` распакуйте ZIP: `database.sql`, `storage_public/`, `env.txt`
(если шифрование было включено). Скопируйте `storage_public` обратно в
`storage/app/public`, при необходимости восстановите `.env`. Если архив `.enc`,
сначала расшифруйте его тем же ключом `NABILET_BACKUP_ENCRYPTION_KEY`.

Сверка после восстановления:

```sql
SELECT COUNT(*) FROM orders;
SELECT COUNT(*) FROM order_items;
SELECT status, COUNT(*) FROM payments GROUP BY status;
```

**Проверенное восстановление — единственное доказательство работоспособности
бэкапа.** Делайте пробное восстановление на отдельную БД регулярно, фиксируйте
RTO/RPO письменно до первого инцидента.
## 8. Проверка после деплоя

- `https://домен/` открывается (не 500, не листинг каталога).
- `https://домен/build/assets/*.js` отдаётся как статикa (200).
- `https://домен/robots.txt`, `/favicon.svg` отдаются физически из docroot (200).
- `https://домен/storage/<файл>` отдаёт медиа (маппинг `.htaccess` в
  `storage/app/public/`), приватное `storage/app/private` недоступно (404).
- `https://домен/app`, `/vendor`, `/config` → **403** (системные каталоги
  закрыты `.htaccess`); `https://домен/.env` → **403** (dot-файлы).
- `php artisan --version` на сервере показывает Laravel 13.x на PHP 8.3.x.
- `POST https://домен/mcp` без токена → **401** (MCP-эндпоинт ИИ-агента,
  v1.3.0; эндпоинт доступен, но закрыт Bearer-токеном).

### Выпуск токена ИИ-агента (v1.3.0)

После обновления токен агенту выпускается по SSH на сервере (см.
`docs/ai-agent.md` — границы полномочий, подключение клиентов):

```bash
cd /home/c/ce99429/DarAgent/public_html
php artisan nabilet:agent-token <email-admin-или-manager>
# Открытый текст токена печатается один раз — скопировать в менеджер
# секретов. Отзыв: php artisan nabilet:agent-token <email> --revoke-all
```

Затем в конфиге клиента (например, OpenCode) указывается
`https://домен/mcp` с заголовком `Authorization: Bearer <токен>`.

### Smoke-прогон релиза на локальном стенде

Перед выкладкой zip на хостинг установка и витрина проверяются на чистом
стенде. Мастер-копии скриптов живут в `scripts/smoke/` (коммитятся): сборщик
zip стирает `.tmp-release-stage` целиком, поэтому после каждой сборки стенд
пересобирается копированием:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build-hosting-zip.ps1 -Version X.Y.Z
php .tmp-release-stage\db-setup-smoke.php              # чистая БД install_smoke + юзер installer
Copy-Item scripts\smoke\smoke-install.php .tmp-release-stage\
Copy-Item scripts\smoke\router-smoke.php .tmp-release-stage\site\
# в .tmp-release-stage\site не должно быть .env и storage/install.lock
# в отдельном окне, из каталога .tmp-release-stage\site:
php -S 127.0.0.1:8088 router-smoke.php
php .tmp-release-stage\smoke-install.php
```

`router-smoke.php` имитирует правила поставляемого `.htaccess` (dot-файлы и
системные каталоги → 403, `/storage/…` → медиатека, остальное →
фронт-контроллер). `smoke-install.php` проходит визард установки как браузер
(с паузой 61 с перед POST-фазами — на `/install` стоит `throttle:5,1`) и после
установки проверяет версию в `/api/v1/health`, оболочку витрины на белом
списке путей (`/admin`, `/tickets`, `/checkout`, `/reset-password?token=…` —
history-роутинг, v1.2.0), брендированную 404 на неизвестном пути, статику и
403 на системные каталоги.

### Процесс релиза

1. bump версии (`config/nabilet.php`, `package.json`);
2. `CHANGELOG.md` += новый релизный блок;
3. commit (`fix:`/`feat:`/`docs(release):`) → тег `vX.Y.Z` → push (`git push origin main vX.Y.Z`);
4. пересборка архива: `npm run build` (если менялся Vue-код) + скрипт
   `scripts/build-hosting-zip.ps1 -Version X.Y.Z` → `releases/nabilet-hosting-vX.Y.Z-YYYYMMDD.zip`
   (скрипт сам собирает staging, чистит runtime-мусор и верифицирует записи);
5. e2e на архиве → удаление старого zip → обновление имени в этом документе.

### Обновление установленной системы

- Через архив (рекомендуется): распаковка **в каталог сайта — на уровень выше
  `public_html/`** (файлы ложатся поверх с перезаписью; внутри `public_html/`
  обновляются только публичные файлы), затем
  `chmod -R ug+w storage bootstrap/cache`. Мастер при `storage/install.lock` —
  откажет `403 ALREADY_INSTALLED` — это норма.
- **Если терминала нет:** после распаковки зайдите в админку → «Центр помощи»
  и примените ожидающие миграции через `POST /api/v1/admin/system/migrate`
  (фраза подтверждения `MIGRATE`). Эндпоинт под `auth:api` + `admin`, пишется в
  security-журнал. Для больших баз это не замена SSH — миграция идёт внутри
  HTTP-запроса и может упереться в таймаут хостинга; в таком случае
  `php artisan migrate --force` по SSH остаётся надёжным путём.
- **Первая установка:** мастер сам выполняет `migrate` и `db:seed`, поэтому
  таблица `agent_actions` (нужна для write-инструментов агента) появится сразу.
- Через git: `git pull origin main` + `composer install --no-dev --optimize-autoloader`
  (здесь `public_html/` остаётся docroot, а код — на уровень выше: git-раскладка
  не менялась).
- После обновления: `php artisan migrate --force`; при изменении `.env` —
  `php artisan config:cache && php artisan route:cache && php artisan view:cache`;
  cron `schedule:run`; проверка `/api/v1/health` → 200, `/` → 200, повторный `/install`
  → 403 `ALREADY_INSTALLED`.
