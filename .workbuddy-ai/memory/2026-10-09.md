### Главная находка: проверка здоровья врала

`GET /api/v1/health` **объявлен в спеке** (`openapi.yaml:1292`, схема
`HealthResponse`, ответы 200 и 503), но не был подключён ни одним маршрутом.
Монитор, повешенный на `/api/v1/ping` или `/up`, получал 200 всегда: оба ничего
не проверяют. То есть зелёный свет при мёртвой базе. `/up` (`withRouting(health:)`)
тоже вечно 200 — ничего не слушает `DiagnosingHealth`.

Сделано: `HealthProbe` (единственный источник вердикта) + `HealthController`
(ровно схема контракта) + `app/Modules/System/routes/api.php`. Проверено живьём:
DB поднята → 200 `{"status":"ok",...}`; `docker stop nabilet-mysql` → **503**
`{"status":"down","database":"error"}`; `/ping` при этом остался 200 (liveness).

Критичность: `database` → 503; `redis`/`queue` → 200 + `degraded`
(`.env.example`: Redis опционален; `docs/PLAN.md` 6.5: «деградация Redis не
роняет систему»). Правило приоритета вынесено в чистую `statusFor()`, иначе
«down перекрывает degraded» проверялось бы только отключением MySQL.

Попутно: прежний `status()` отдавал `healthy` — такого значения нет в enum
`[ok, degraded, down]`, то есть контракт нарушался и по значению.

### Логи: проводка дважды не работала молча

Это главный урок сессии. Маскирование ПД было написано, **тест на содержимое
конфига проходил**, а в `storage/logs/laravel-*.log` лежали адрес и пароль
покупателя. Нашлось только живой проверкой. Две независимые причины:

1. **Драйвер `daily` ключ `processors` НЕ ЧИТАЕТ ВООБЩЕ.**
   `LogManager::createRotatingDriver()` собирает Monolog с жёстким списком
   `[new PsrLogMessageProcessor()]`. Только `createMonologDriver()` (драйвер
   `monolog`) прокидывает процессоры. Поэтому `daily`/`security` переведены на
   `'driver' => 'monolog'` + `RotatingFileHandler` в `handler_with`.
2. **Процессор обязан реализовать `Monolog\Processor\ProcessorInterface`** —
   `createMonologDriver()` проверяет через `is_a()` и бросает
   `InvalidArgumentException`. Без интерфейса канал не создаётся, Laravel уходит
   в emergency logger и пишет в `laravel.log` БЕЗ фильтра. То есть попытка
   включить защиту оставляла логи и без защиты, и без канала.

Вывод на будущее: **проверять проводку на разрешённом объекте, а не на конфиге.**
`Log::channel('daily')->getProcessors()` — вот настоящий оракул. Ложность старой
проверки подтвердил возвратом сломанного конфига: 2 теста упали, как должны.

### Каналы утечки ПД (все четыре закрыты)

1. `$context` по ключу; 2. по значению; 3. **исключение в `$context`**;
4. **строковое представление исключения** в `message` (`Log::error($e)`).

3 и 4 — неочевидные: Laravel включает трассировку
(`new LineFormatter(..., includeStacktraces: true)`), а `getTraceAsString()` в
PHP печатает **аргументы вызовов**. Проверено на рантайме:
`#0 ...: login('user@example.co...', 'hunter2')`. Поэтому `Throwable` разбирается
вручную в структуру `class/message/code/file/trace` (форма как у
`NormalizerFormatter::normalizeException`), а трасса строится из `getTrace()`
как `файл:строка` — без аргументов.

Границы фильтра выбраны так, чтобы его не отключили: Unix-время и id заказов НЕ
маскируются; карта — только по Луна; `8XXXXXXXXXX` без разделителей — нет.

`Monolog\LogRecord` — **readonly**! `$record->message = ...` даёт фатал
«Cannot modify readonly property». Только `$record->with(...)`.

## Этап 6: локальный QR в письме (свой кодировщик на PHP)

### `app/Modules/Tickets/Domain/Qr/` — три файла
- `QrEncoder` — байтовый режим, уровень M, версии 1..10, чистая статика. В `vendor/`
  нет библиотеки QR, Composer без сети, а payload отдавать сервису картинок нельзя
  (это ровно та утечка, из-за которой убрали `api.qrserver.com`). Поэтому кодировщик свой.
- `QrPngRenderer` — матрица → PNG (оттенки серого, 1 бит/пиксель) вручную: сигнатура,
  `IHDR`, `IDAT` через `gzcompress`, `IEND`, CRC32. **Без GD/Imagick** — расширения может
  не быть, а `imagepng()` ещё и требует дескриптор. `dataUri()` → `data:image/png;base64,…`.
- `QrCapacityException` — отдельный тип: вызывающий обязан отличить «QR не построить»
  (лечится текстом) от «в коде ошибка».

### ГЛАВНОЕ: эталонная матрица, а не «выглядит как QR»
Своя ошибка в таблицах RS / раскладке / масках даёт картинку, которая ВЫГЛЯДИТ как QR, но
не читается — ни один структурный тест этого не поймает. Поэтому:
`tools/gen-qr-golden.mjs` (npm `qrcode@1.5.4`) → `tests/Fixtures/qr_golden.json` (25 кейсов,
**все 10 версий**) → `tests/Unit/QrEncoderGoldenMasterTest` требует **побитового** совпадения.
Фикстура коммитится, чтобы PHP-тест остался чистым (без Node и без vendor).

**Ловушка №1 — режим кодирования.** `qrcode` подбирает режим САМ: для строки из заглавных
букв берёт алфавитно-цифровой (плотнее байтового → другая версия). Первый прогон дал
«v1: 1..20 байт», хотя байтовая ёмкость v1-M = 14. Сравнение байтового кодировщика с
авторежимом не проверяет ничего — нужен явный `[{ data, mode: 'byte' }]`.

**Ловушка №2 — порядок битов формата.** В `(8,0)` лежит СТАРШИЙ бит (14), в `(0,8)` —
младший. Я положил наоборот. Симптом: расходились ровно 8-12 модулей, всегда начиная с
колонки 8, а данные совпадали. Хуже — штраф маски считается по матрице с УЖЕ записанным
форматом, поэтому неверный порядок иногда менял и выбор маски (кейсы с 186 и 420
расхождениями). Один корень, два симптома.

**Ловушка №3 — N4 в штрафе маски.** Эталон считает `k = |ceil(доля% / 5) − 10|`, а не
`floor(|доля% − 50| / 5)`. Расходятся на 51-54 % (53 % → 0 против 1). Выбор маски на
читаемость не влияет (любая из восьми даёт корректный код), но расхождение ломает
побитовое сравнение, а именно оно и проверяет всю цепочку. Формула взята у эталона.

**Ловушка №4 — фильтр строки PNG.** Первый байт каждой строки — фильтр (0), пиксели идут
ПОСЛЕ него. Я писал биты в байт 0, затирая фильтр → картинка разъезжалась на байт.
Поймал обратный разбор PNG (распаковка `IDAT` и сверка пикселей с матрицей).

### `verify-purity` НЕ РЕКУРСИРОВАЛ — дыра в страже
`glob($dir . '/*.php')` видел только файлы непосредственно в `Domain/`, поэтому

### Проводка
`TicketGeneratorService::generateTicketData()` отдаёт `qr_data_uri` (одно поле для ОБОИХ
писем — расхождение каналов уже было источником бага). `OrderNotificationData::ticketBlock`

### Решения, которые стоит помнить
- **Диск = `nabilet.media.disk` (default `public`), НЕ `filesystems.default`.** `local` в этом
  проекте → `storage/app/private`, который веб-сервер НЕ отдаёт: запись есть, картинки нет.

- **`MediaLink`: `const UPDATED_AT = null`.** У `media_links` есть только `created_at`;
  `public $timestamps = false` был бы неверен — отключил бы и `created_at` → NOT NULL-фейл.
- **Удаление файла мягкое, связи снимаются ЯВНО.** `fk_media_links_asset ON DELETE CASCADE`
  на мягком удалении не срабатывает НИКОГДА (DELETE на уровне SQL не выполняется), поэтому
  без явного снятия `media_links` копил бы строки на удалённый файл. Сам файл на диске остаётся.
- **Варианты изображений СОЗНАТЕЛЬНО не генерируются** (GD есть, но конвейер = EXIF-ориентация,
  альфа, лимиты памяти, инвалидация). `variants_json` принимает произвольный JSON.

  может быть и афишей, и элементом галереи. Снять все роли = оставить мероприятие без афиши.

## Шаблоны писем по событиям + SMTP-страница (закрывает запрос «SMTP и шаблоны»)

Запрос: «В админке должны быть поля настройки SMTP для настройки отправки писем,
и должны быть редактируемые шаблоны писем, которые отправляются по событиям».
SMTP-страница (`AdminMailSettingsPage`) уже была закрыта ранее — host/port/
username/password(show-hide, шифруется в покое, на сервер не возвращается)/
encryption/from_address/from_name + тестовое письмо + «эффективный мейлер».
Доделка касалась шаблонов: и данных, и вида.

### Скрытый дефект: 3 шаблона из 10 были не засеяны
В БД лежало 7 шаблонов (только `order.*` статусы), а сидер определяет 10 —
включая `order.reminder` и два `account.*`. `TransactionalMailService::findTemplate()`
ищет `active=true` и при промахе просто `Log::warning` + молча НЕ шлёт письмо.
То есть письмо «напоминание за сутки», «подтверждение email» и «смена пароля»
не доходили до покупателя без видимой ошибки. Худший класс дефекта.

Запустил `php artisan db:seed --class=NotificationTemplateSeeder --force`
(идемпотентный: `firstOrCreate` по `code`, не перетирает правки админа). В БД
теперь 10 строк (ids 1–10), API `GET /api/v1/notification-templates` отдаёт все
десять — проверено `curl` с настоящим Bearer-токеном.

### Страница шаблонов переведена на дизайн-систему
`AdminNotificationTemplatesPage.vue` была собрана вручную: `text-xl` заголовок,
`<textarea>` без рамок, переменные статичным `<code>`. Переписана на
`NPageHeader` + `NCard`, добавлено то, чего реально не хватало администратору:

- **Группировка по семейству** (`Заказы` / `Доступ к аккаунту` / `Прочее`) — список
  из 10 писем читается как каталог, а не плоский перечень. Заголовки групп —
  uppercase 2xs muted.
- **Человекочитаемые имена** (`LABELS`: `order.paid` → «Заказ оплачен»), код
  оставлен мелкой моноширинной подписью для сверки с логами.
- **Индикатор состояния** — мятная точка (`active`) / серая (`!active`) + `NBadge`
  «отправляется / выключен» в шапке редактора.
- **Курсорная вставка переменных.** Чипы `{{customer_name}}` и т.д. вставляются в
  позицию курсора в активном поле (отслеживаем `lastField` через `@focus`),
  а не в конец текста. Для subject — конкатенация (там нет позиции курсора в API
  инпута). Метка «Есть несохранённые изменения» появляется по `isDirty`
  (сравнение `JSON.stringify(form)` со снапшотом), кнопка «Сохранить»
  дизейблится при чистом состоянии.
- **Предпросмотр в sandboxed iframe** (`sandbox=""` + `:srcdoc`), а не через
  `v-html` — шаблон это HTML, и скрипты из него НЕ должны выполняться.

`code`, `channel`, `locale` НЕ редактируются: это идентичность шаблона, по
коду его находит обсервер заказа; правка кода молча отключила бы рассылку.
