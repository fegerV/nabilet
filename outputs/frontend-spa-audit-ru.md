## 2. Что произошло с веткой (важно для понимания)

Когда я начал исправления, ветка `main` в удалённом репозитории **ушла на 71 коммит вперёд**
относительно той точки, где делался аудит: `cca4dfe5` → `e2586910`.
Часть находок аудита была **уже исправлена другими людьми** в этих коммитах
(PR #107/#108: «Reconcile the three schema bundles and unblock CI», «Close the SEO page surface,
harden payments/webhooks», «Make the PHP suite hermetic…», «Make the event page suite independent
of the Vite build»).

Поэтому я:
1. Нашёл опасную ловушку в git-конфиге: у `origin` **не настроен fetch-refspec**, из-за чего
   `git fetch origin main` обновлял только `FETCH_HEAD`, а `origin/main` оставался старым —
   сравнение показывало ложное «0 behind». Реальное состояние берётся через `git ls-remote`.
2. Сделал резервную ветку `backup-audit-fixes-e3361258`.
3. Пересобрал исправления **поверх нового `main`**, оставив только реально открытые пункты
   и отбросив дубликаты (то, что уже починено в main).
4. Запушил fast-forward `e2586910..966eaa52`.

Удалённый `main` сейчас = `966eaa52b0248273d2d9a0dfedfa617b4c643786` (совпадает с локальным, проверено `git ls-remote`).

## 4. Расхождения UI ↔ API (перевод)

### Что уже согласовано (подтверждено исходником)

- Оформление вызывает `POST /cart/checkout` с `customer_name`, `customer_email`, `customer_phone`,
  затем `POST /payments`, используя серверный `order_id`, и показывает серверный итог.
  Это опровергает старое описание с пустым email и имитацией оплаты.
- Оформление возвращает `order_id` как публичный ID заказа; контроллер оплаты понимает и публичные,
  и числовые внутренние ID.
- Общий API-клиент добавляет `X-Cart-Token` к запросам `/cart*` и прокидывает существующий токен
  в запросы оплаты. Контроллер оплаты сверяет гостевой токен с корзиной заказа. В исходнике
  контракт согласован; реальный платёжный запрос не отправлялся.
- Удаление из корзины ограничено и токеном корзины, и владельцем корзины на бэкенде.
  `releaseSeat()` отправляет строку с числовым session ID — совместимо с целочисленной валидацией Laravel.

### Подтверждённые расхождения

1. **ID восстановленной корзины.** `CartItemResource.id` — это ID строки корзины в БД;
   `inventory_item.id` — публичный ID позиции склада. `SeatSelectionPage.applyServerCart()`
   находил строку склада и сохранял её внутренний inventory-id в `cart.meta`, а затем передавал
   это значение как cart-item id в `DELETE /cart/items/{id}`. `CheckoutPage.restoreCart()` восстанавливал
   места, но не восстанавливал `cart.meta`. Это могло оставить серверный холд висеть после снятия
   восстановленного места.
2. **Количество стоячих билетов.** `CoordSeatMap` предлагал 1–5. `onToggleCoord()` отправлял `qty`
   в `holdSeat()`, но у `CartSeat` не было поля количества, `count` был мощностью множества выбранных
   ID, а `subtotalMinor` добавлял одну цену на каждый выбранный ID. Бэкенд `CartService` при этом
   инкрементирует и суммирует запрошенное количество. Итог UI мог быть ниже итога заказа.
3. **Конверт ошибок валидации.** Бэкенд отвечает как `error.message` и `error.details.fields`;
   `lib/api.ts` читал верхнеуровневые `message` и `error.errors`. В результате ошибки полей оформления
   могли исчезать и показывался общий текст «HTTP 422» вместо конкретных ошибок по полям.
4. **Видимость билетов.** Экран билетов питался фикстурами, тогда как актуальный API чтения билетов
   требует bearer-авторизации и привязывает обычных пользователей к `order.user_id`. Гостевые покупки
   при такой реализации на этой странице появиться не могли.
5. **Доверие к результату оплаты.** Вид результата выбирался только по параметру маршрута, а
   неизвестные значения по умолчанию считались успехом. Перед показом сообщения об успехе
   запроса статуса к серверу не было.

## 7. Прочие замечания и ограничения (перевод)

- В корневом HTML есть запрос `/favicon.ico` (404) в Network браузера; низкая критичность.
- `dist/` и его вывод локальны/игнорируются; закоммиченного `dist` для сравнения со свежей сборкой нет.
- Сток в отдельном `hall-editor.html` — вне маршрутизируемого Vue SPA. Шаблон установщика тоже
  использует `innerHTML`, но проверенные поля ответа строятся из серверных проверок окружения;
  поток данных, контролируемый атакующим, не установлен.
- Изменений исходного кода в рамках аудита не делалось. Рабочее дерево содержало сгенерированные
  изменения в `node_modules/.package-lock.json`, `node_modules/.vite/vitest/.../results.json`,
  `node_modules/.vue-global-types/vue_3.5_0_0_0.d.ts` и `vendor/autoload.php`; два последних были
  локально изменены ещё до аудита. Они не откатывались.
- Остаётся проверка, требующая контролируемых тестовых данных: добавить/снять холд и сверить
  состояние БД, восстановление корзины после F5, итоги количества стоячих зон, транзакция
  оформления/оплаты, получение гостевых билетов, потоки отказа по роли/истечения токена в админке
  и рантайм-проверка отсутствующего `dist`. Аудит намеренно не создавал эти записи.

### Важная оговорка про окружение (`APP_KEY`)

В репозитории **нет `.env`**. Без `APP_KEY` 152 Feature-теста падают с ошибкой
«No application encryption key has been specified» — это особенность окружения, а **не регрессия**.
Запуск с сгенерированным ключом даёт 584/584 OK:

```bash
APP_KEY="base64:$(head -c 32 /dev/urandom | base64)" php vendor/bin/phpunit
```

`phpunit.xml` уже форсирует тестовую БД `nabilet_test_suite` (`force="true"`), host `127.0.0.1`, port `3307` —
поэтому прогон Feature-тестов не затрагивает `nabilet_testing`.

## 11. Технические заметки по инфраструктуре (на будущее)

- **Ловушка git:** у `origin` нет fetch-refspec → `git fetch origin main` обновляет только `FETCH_HEAD`,

  `https_proxy` и передавать явно через `GIT_SSH_COMMAND` с `http_connect_tunnel.py`.
