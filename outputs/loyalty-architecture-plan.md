# NABILET: структура под лояльность, анонимные билеты, соц-авторизация

**Дата:** 2026-10-08 · **Режим:** активная разработка, MVP
**Роль:** Backend Architect
**Задача:** предложить изменения в структуре под лояльность покупателей, минимизировать риски,
отвергнуть слишком затратное, задокументировать. Билет с QR обязан доходить до анонима.
Добавить вход через ВК / Яндекс / MAX.

**Принцип этого документа:** мы в разработке, а не после запуска. Значит ценно только то, что
**нельзя изменить потом без миграции данных**. Всё остальное — преждевременно.

---

## 0. Главный вывод

**Уточнение по бизнес-модели (см. §2.5):** «Сургут-Концерт» — это **сам организатор**, а не
бренд-площадка над чужими организаторами. Проект делается **для этого организатора**.
Поэтому подсистема мультитенантности в ядре остаётся как есть (переписывать её затратно и
опасно), но реально в базе будет **одна организация** — и это снимает целый класс вопросов
про распределение денег между организаторами.

Хорошая новость: **доставка билета анониму уже почти работает** — `orders` хранит
`customer_email`, и письмо уходит на него независимо от `user_id`. Здесь нужен не рефакторинг,
а закрытие одной дыры (QR отдаётся текстом, а не картинкой) и одного бага с молчаливым
пропуском билетов.

Плохая новость: под лояльность **в спецификации нет ни одной сущности**. И почти всё, что
описано в прошлом обсуждении (бонусы, уровни, рефералы, избранное, подписки) — это новый
подсистемный объём.

Мой вывод по приоритету — **один новый модуль, три таблицы, ноль изменений в существующих
сущностях**. Всё, что требует больше — отвергаю как преждевременное.

## 0.1 Что изменилось после уточнения «Сургут-Концерт = организатор»

| Было (предположение) | Стало (факт) |
|---|---|
| Бренд-площадка над несколькими организаторами | **Один организатор**, одна строка в `organizations` |
| Вопрос «кто эмитент бонусов» — открыт | Эмитент — **сам организатор**. Вопрос закрыт |
| Риск «организатор А субсидирует Б» | **Отсутствует** — организатор один |
| Мультитенантность — бизнес-требование | **Переиспользуемый шаблон продукта** (можно продать второй раз), не текущая потребность |
| `organization_id` в проводках — страховка от спора | Остаётся как недорогое будущее-доказательство, но уже не обязательство |

Практические следствия:

1. **Кошелёк один** — `bonus_balances(user_id PRIMARY KEY)`, без `organization_id` в ключе.
   Разбивка по организациям не нужна вообще.
2. **Промокоды, ранний доступ, квоты — «наши».** Их можно делать смелее: риска, что они
   субсидируют чужой бизнес, нет. Эксклюзивные квоты NABILET — это просто ваши собственные
   квоты, а не переговоры с третьей стороной.
3. **Мультитенантность не трогаем, но и не приоритезируем.** Переписывать её — затратно и
   ломает ядро; оставить как есть — бесплатно и даёт возможность продать продукт второму
   организатору позже. Это ровно тот случай, когда «отложить» — правильное решение.
4. **Настройки лояльности (`+5 %`, лимит 30 %, уровни) уже есть куда положить:**
   `organizations.settings_json` (JSON, nullable) и таблица `settings` (scope + setting_key +
   `value_json`, `encrypted`) — тем же способом, каким сделан `MailSettings`. **Это значит:
   ставки и проценты настраиваются без единой миграции.** Отдельная таблица для «настроек
   лояльности» не нужна.

## 1. Что уже работает для анонимного покупателя (проверено по коду)

### 1.1 Билет анониму уходит уже сейчас

```
cart/checkout (customer_email обязателен)
      ↓
Order::create([ 'user_id' => null, 'customer_email' => … ])   CartCheckoutService:172
      ↓
payment → order.paid → OrderObserver::updated()
      ↓
SendOrderNotificationJob → recipient: $order->customer_email   SendOrderNotificationJob:66
```

Ключевое: `order.user_id = null` **не мешает** — получатель берётся из `orders.customer_email`.
Колонка объявлена `NOT NULL` в спеке, а `customer_name` / `customer_phone` добавлены
проектной миграцией D5/B2 (зеркалирована в спеке, строка 1412). Для регистрации этого
достаточно — гость получает письмо с билетом.

### 1.2 Гость может восстановить билеты без письма

`GET /api/v1/my-tickets` — единственный маршрут **вне** `auth:api`:

```
X-Cart-Token (UUID, ≥32 символа) → carts.cart_token → orders.cart_id → tickets
```

Это правильное решение: гостевая витрина не имеет аккаунта, и fail-closed (нет токена →
пустой список, а не 401) выбран осознанно, чтобы гость видел пустой экран, а не ошибку.
Ограничение: **потеря вкладки = потеря доступа**. Остаётся только письмо.

### 1.3 QR сейчас — не картинка

`tickets.qr_payload` содержит подписанную строку `NB1.<publicId>.<token>.<signature>`
(`QrSigner`, ТЗ §30). Письмо печатает её **текстом** (`OrderNotificationData::ticketBlock`,
`email/ticket.blade.php`). Ни QR-пакета, ни PDF-пакета в `composer.json` нет.

Android-checker принимает `qr_payload` строкой (`CheckinController`), поэтому **вход
технически работает и без картинки** — код можно ввести руками. Но покупатель, увидевший
«QR-код», ожидает квадрат, который сканируют. Это UX-разрыв, а не поломка контура.

Внешний сервис рендера (типа api.qrserver.com) **запрещён**: подписанный токен входа
нельзя отправлять третьей стороне — получивший его получает доступ на вход.

### 1.4 Баг, который тихо съест билеты из письма

`TicketGeneratorService::generateTicketData()` бросает `LogicException`, если `qr_payload`
пуст. Оба потребителя — `OrderNotificationData::ticketsHtml()` и `ticketsText()` — **глотают
`Throwable` и делают `continue`**. Последствие: при любой проблеме с выпуском письмо
отправляется **без блока билетов** и никто об этом не узнает.

Хуже: положительный случай (письмо с реальным payload) нигде не проверяется — а урок проекта
уже записан в `docs/REVIEW-spec-bundle.md` §3.25.2: *«набор проверок, состоящий только из
отказов, не отличает рабочий guard от сломанного»*.

**Требование:** регрессионный тест, который **сам вызывает** `generateTicketData()` на реальном
билете с `qr_payload` и утверждает, что payload присутствует в письме. Молчаливый `continue`
оставить нельзя, но и падать на весь заказ — тоже; правильно логировать с уровнем error и
**не считать письмо доставленным**.

## 2. Бизнес-модель: один организатор

Зафиксировано заказчиком: **«Сургут-Концерт» — организатор концертов**, проект делается для
него. В базе будет одна строка в `organizations`.

Что это меняет по сравнению с изначальным предположением о бренде-площадке:

| Аспект | Влияние |
|---|---|
| Эмитент бонусов | **Сам организатор.** Никакой третьей стороны |
| Спор «чья скидка» | Невозможен: организатор один |
| Мультитенантность | Не трогаем и не приоритезируем. Остаётся в ядре как шаблон продукта, который можно поставить второму организатору |
| `organization_id` в новых таблицах | Баланс — не по организации. В проводках оставляем как источник начисления (стоит ноль) |
| Настройки лояльности | `organizations.settings_json` + `settings`. **Новых таблиц не нужно** |
| Промокоды, квоты, ранний доступ | Это «наши» акции, а не переговоры с третьей стороной — делать смелее |

**Отвергаю** переписывание мультитенантности под «одного организатора»: это затратно, ломает
ядро и лишает продукт возможности быть проданным дважды. Правильно — оставить как есть и
просто не нагружать её вопросами, которых у одного организатора не возникает.

## 3. Что менять в структуре (минимально и только необратимое)

### 3.1 Идентификация покупателя — до всякой лояльности

Бонусы, история, избранное — всё это свойства человека. Пока заказ анонимен, у большей части
покупателей не будет истории. Но **заставлять регистрироваться нельзя** — это прямо
противоречит требованию (билет обязан уходить анониму) и убивает конверсию.

Правильное решение — **identity-first, без обязательной регистрации**:

| Что делаем | Зачем | Цена |
|---|---|---|
| Гость, оставивший email, — это **известный контакт**, не серая запись | бонусы можно привязать к email | 0 (данные уже есть) |
| При регистрации/соц-входе по тому же email — **привязка истории** (не дубль) | «я уже покупал, мои билеты здесь» | 0 (запрос по `customer_email`) |
| Телефон — необязателен | не блокирует покупку | 0 |

Это даёт лояльности фундамент **без единой новой таблицы**. Всё, что нужно — при
регистрации (и при OAuth) искать прошлые заказы по нормализованному email и поставить
им `user_id`. Операция идемпотентная и обратимая.

**Отвергаю:** автосоздание `users` на каждой гостевой покупке (ТЗ §83 в текущей трактовке).
Минусы: почта-мусор, конфликт при регистрации («адрес занят»), риск `isReachable()`-нарушений.
История по email даёт тот же результат дешевле.

**С учётом «Сургут-Концерт = организатор» это стало ещё проще.** Единственная причина, по
которой автосоздание аккаунтов было хоть как-то оправдано («нужно привязать покупателя к
организатору») — исчезла: организатор один, и привязка к нему всех заказов очевидна. История
по email — правильное решение, и оно не требует новых сущностей.

### 3.2 Один новый модуль: `Loyalty`

Не трогаем `Pricing` (чистый домен, охраняется `verify-purity.php`) и `Orders`
(единственный владелец жизненного цикла). Лояльность — **наблюдатель**, а не участник
транзакции.

```
app/Modules/Loyalty/
├── module.json          requires: ["orders","tickets","users"]   enabled: false
├── Providers/LoyaltyServiceProvider.php
├── Domain/
│   ├── BonusLedgerEntry.php       чистая запись книги
│   ├── BonusPolicy.php            правила начисления (таблица «за что»)
│   └── SpendLimit.php             «не больше 30 % заказа»
├── Models/
│   ├── BonusTransaction.php       append-only
│   └── BonusBalance.php           материализованный баланс
├── Services/
│   ├── BonusService.php           начислить / списать / сторнировать
│   └── CustomerHistoryLinker.php  привязка гостевых заказов по email
└── Listeners/OrderLoyaltyListener.php
```

`enabled: false` — намеренно. Модуль включается, когда готов; до этого он не участвует в
графе загрузки, но структура уже зафиксирована (правило проекта: отложенная функция не должна
требовать правки ядра, когда её добавят).

### 3.3 Три таблицы, ни одной правки существующих

```sql
-- 1. Книга проводок: append-only, никогда не обновляется
bonus_transactions (
  id, user_id, organization_id NULL, order_id NULL,
  delta BIGINT NOT NULL,          -- может быть отрицательным (списание/сторно)
  reason VARCHAR(32) NOT NULL,    -- registration|purchase|visit|referral|refund_reversal
  idempotency_key VARCHAR(64) NOT NULL,
  created_at,
  UNIQUE uq_bonus_tx_idempotency (idempotency_key)   -- ← защита от двойного начисления
)

-- 2. Материализованный баланс: то, что показываем в кабинете
bonus_balances (
  user_id PK, organization_id, balance BIGINT NOT NULL DEFAULT 0,
  CHECK (balance >= 0)
)

-- 3. Привязки соц-входов (для OAuth, см. §4)
user_identities (
  id, user_id, provider VARCHAR(32), provider_user_id VARCHAR(191),
  created_at,
  UNIQUE uq_user_identities_provider (provider, provider_user_id)
)
```

**Почему ledger + отдельный баланс, а не одна колонка.** Баланс-колонка не отвечает на вопрос
«откуда взялось» и расходится с историей на первом же возврате. Ledger даёт аудит и позволяет
проверять утверждением: **баланс == SUM(delta)**. Это проверяется тестом, а не уговорами.

**Почему `idempotency_key` — не деталь.** `PaymentService` уже дедуплицирует вебхуки, но
начисление бонусов должно быть защищено **собственным** ключом: `order:<id>:purchase`.
Повторный вебхук не начислит дважды — и это гарантия уровня БД, а не кода.

**Ни одной правки в `orders`/`carts`/`users`.** Всё нужное там уже есть.

### 3.4 Порядок подписки на события

Вешать на `OrderObserver` (он ловит все переходы), **не на `add_action`** — в этом проекте
`HookRegistry` это реестр фильтров, а не lifecycle.

| Событие | Действие | Обратимость |
|---|---|---|
| `order.paid` | `+5 %` бонусами, `+300` за первую покупку | идемпотентно по ключу |
| `ticket.used` | «посещение» (`+100`) | раз в билет |
| `order.refunded` / `partially_refunded` | **сторно** начислений по заказу | обязательно |
| `order.cancelled` / `expired` | сторно, если успели начислить | обязательно |

Сторно — **не доработка на потом**, а часть определения готовности. Без него: покупка →
начислено 5 % → возврат → бонусы за отменённую покупку остаются. Это прямая утечка денег.

## 4. Что отвергаю как слишком затратное

| Пункт | Почему отвергаю сейчас |
|---|---|
| **Персональные рекомендации** | Требуют признаков интереса и истории посещений; сегодня истории нет (заказы анонимны). Вернуться после идентификации и накопления данных |
| **Розыгрыши, «счастливый билет»** | Стимулирующая лотерея → отдельное юридическое оформление. Не MVP. Заменить на «подарок за посещение» (не лотерея) |
| **PDF-билет** | Новый пакет (`dompdf`/`tcpdf`) + CJK/шрифты + вес. Письмо и веб-страница решают задачу; PDF нужен только для корпоративного, и это запрос, а не базовое требование |
| **Генерация QR на сервере через внешний сервис** | **Запрещено по безопасности:** `qr_payload` — токен входа, его нельзя отдавать третьей стороне |
| **Уровни клуба (`Start/Friend/VIP`) как колонка в `users`** | Расходится с историей на первом возврате. Если делать — **производная функция**, пересчитывается из `orders`, не хранится |
| **Избранное, подписки на артистов, «не пропусти»** | Отдельная подсистема с уведомлениями. Стоит делать после того, как заработают билеты и бонусы |
| **Второй кошелёк на организатора** | Мультитенантная схема бонусов = миграция данных всех клиентов позже. **Снято с повестки:** «Сургут-Концерт» — сам организатор, распределять между организаторами нечего |
| **Автосоздание `users` на гостевую покупку** | См. §3.1: история по email дешевле и без мусора. С единственным организатором стало ещё проще |

## 5. Соц-авторизация: ВК, Яндекс, MAX

### 5.1 Что уже заявлено, но не реализовано

- `Auth/module.json`: *«Email/пароль, OAuth (Яндекс, VK, Telegram), 2FA…»* (ТЗ §8) — заявлено.
- `docs/openapi.yaml:149–171`: объявлены `/auth/yandex/callback` и `/auth/vk/callback`
  (GET, `code` + `state`, ответ `302`) — **обработчиков нет**.
- **Расхождение в контракте:** эти два пути объявлены **без префикса `/api/v1`**, тогда как
  все остальные auth-пути имеют его. Причины не задокументированы. Решить до реализации.
- `UserIdentity::isReachable()` требует email ИЛИ телефон, и докблок прямо фиксирует:
  *«the bundle has no OAuth/social table»* — то есть новая таблица обоснована существующей
  архитектурной заметкой, а не нашим желанием.
- **MAX** в спецификации отсутствует. Это новое требование — принимается как расширение.

### 5.2 Архитектура: OAuth выдаёт ту же сессию

```
GET /auth/{provider}/redirect   → 302 на провайдера (state в подписанной куке/кэше)
GET /auth/{provider}/callback   → обмен code → профиль → user_identities
                                → SessionIssuer::issue(...)   ← существующий механизм
```

Критично: OAuth **не заводит второй механизм аутентификации**. Он выдаёт тот же bearer-токен
из `user_sessions` через существующий `SessionIssuer`, поэтому все protected-маршруты
(`auth:api`) продолжают работать без изменений. Иначе получим две параллельные системы входа —
классический источник дыр.

### 5.3 Привязка и риск дублей (главный)

Правила, которые надо зафиксировать **до** кода:

1. Провайдер подтвердил **верифицированный email**, и такой `users.email` уже есть →
   **привязываем к существующему аккаунту**. Это то, что нужно: человек, купивший анонимно,
   входит через Яндекс и видит свои билеты.
2. Email не совпал → **новый аккаунт** + запись в `user_identities`.
3. Провайдер email не отдал → аккаунт всё равно должен быть `isReachable()`; иначе
   `UserIdentityPolicy::registerDecision()` откажет (и правильно сделает).
4. **Отвязка последнего способа входа запрещена** — иначе аккаунт становится недостижимым.
   Это правило уровня домена, не контроллера.

### 5.4 Что нужно от заказчика (внешние данные, не код)

| Провайдер | Что нужно | Замечание |
|---|---|---|
| **Яндекс** | `client_id` + `client_secret`, согласованный redirect URI | Путь уже в контракте |
| **VK** | Приложение VK ID, `client_id` + `client_secret` | Путь уже в контракте; VK ID ≠ старый VK OAuth — уточнить, что именно |
| **MAX** | Наличие OAuth/OIDC-эндпоинтов, регистрация приложения | **Не проверено.** Если OIDC стандартный — ложится в ту же абстракцию; если нет — отдельный адаптер |

Провайдеры делать **адаптерами** (интерфейс + реализация на каждый), а не ветвлением в
контроллере: MAX с неизвестным протоколом не должен менять существующий код.

### 5.5 Билеты и соц-вход — независимы

Требование «билет обязан уйти анониму» и соц-вход решают **разные** задачи и не пересекаются:
email нужен для билета, соц-вход — для кабинета и истории. Соц-вход **не может** быть условием
получения билета. Если это правило нарушить, гость без соцсети не купит — то есть потеряем
основной поток.

## 6. QR-код в письме: дешёвое решение

Задача формулируется как «билет с QR-кодом». Сегодня в письме — текстовая строка.

**Отвергнуто:** серверная генерация через внешний сервис (утечка токена).

**Отвергнуто сейчас:** серверный пакет + новая зависимость в MVP.

**Предлагаю (дешевле и безопаснее):** страница билета в SPA рисует QR **на клиенте** из
`qr_payload` (клиентская JS-библиотека, payload не покидает браузер). Письмо содержит кнопку
«Открыть билет» → страница, где QR уже картинкой плюс текстовая строка как fallback.
Доступ к странице — тем же `X-Cart-Token` или по одноразовой подписанной ссылке из письма.

Это закрывает UX-разрыв без нового пакета на сервере, без PDF и без утечки токена.
Ограничение честное: QR **генерируется в браузере** — если нужен именно вложенный в письмо
готовый PNG, потребуется серверный пакет, и это уже отдельное решение с ценой.

## 8. Порядок работ

Порядок задан риском, а не привлекательностью. Этапы 1–2 — то, что нельзя отложить;
этапы 3–4 можно ставить на паузу без потери.

| Этап | Содержание | Почему сейчас |
|---|---|---|
| **1** | QR-страница билета + регресс-тест на письмо с реальным `qr_payload`; логирование вместо тихого `continue` | Билет — ядро продукта; баг тихо съедает билеты. Детали — `outputs/ticket-designer-delivery-plan.md` |
| **2** | Модуль `Loyalty` (скелет, `enabled:false`) + `bonus_transactions` / `bonus_balances` + начисление на `order.paid` + **сторно на возвратах** | Фундамент; сторно нельзя добавлять «потом». Ставки — в `organizations.settings_json`, без новых таблиц |
| **3** | OAuth: Яндекс → VK → MAX (адаптеры), `user_identities`, привязка по email | Требование заказчика; ложится на существующий `SessionIssuer` |
| **4** | Привязка гостевой истории по email; кабинет (билеты, баланс, история) | Даёт эффект лояльности без новых механик. Для одного организатора работает без оговорок |

Явно **вне** этого плана: рекомендации, розыгрыши, уровни, избранное, подписки, PDF.
Причина одна — они требуют данных, которых ещё нет.

**Замечание по приоритету после уточнения.** Поскольку «Сургут-Концерт» — единственный
организатор, подсистема мультитенантности ни одного из этих этапов не касается. Это
существенно: раньше любая работа с заказами и бонусами тянула за собой вопрос
«к какой организации это относится», а `organization_id` есть лишь у 16 из 64 таблиц и не
подставляется автоматически. Теперь этот риск — **вне пути** этапов 1–4.
