# NABILET — ротация секретов (runbook, 2026-11-04)

> **Зачем файл.** В PRODUCTION-READINESS §4 (строка 8) «ротация секретов» до сих пор
> значилась пунктом-намерением: секреты перечислены в `.env.example`, но нигде не
> сказано, **чем себе дороже** ротация каждого из них. «Сменить ключ» — операция,
> у которой самые дорогие последствия наступают не в момент утечки, а через
> несколько часов после плановой замены (билеты перестали проверяться, бэкап
> уже не дешифруется, вебхук-приёмник молча отбрасывает подпись, платежи воют
> тревогу). Этот runbook — инвентаризация с ценой каждой операции и порядком
> действий на среде Timeweb.

---

## 1. Принципы

1. **Секреты живут в `.env` на сервере, не в репозитории.** `.env.example` — только
   перечень и указания, как генерировать. Дампа конфига «на всякий случай» быть
   не должно: дамп базы его не содержит именно потому, что секретов там нет
   (`deploy-timeweb.md`, раздел бэкапов).
2. **Плановая ≠ аварийная.** Плановая ротация происходит в спокойное окно и
   допускает деградацию, описанную заранее. Аварийная (подозрение компрометации)
   допускает деградацию **любую**, кроме «компрометированный ключ остаётся
   действительным» — порядок в §4.
3. **Ротация = правка `.env` + сброс конфигурации + проверка.** Среда Timeweb —
   shared-хостинг: nginx+php-FPM читают окружение на каждый запрос, планировщик
   и воркер очереди просыпаются раз в минуту (cron `schedule:run`), systemd не
   существует. Полный цикл:

   ```bash
   nano .env                  # заменить значение
   php artisan config:clear   # снять кеш конфига, если он строился
   curl -fsS https://<домен>/api/v1/health   # зависимости живы
   ```

   Крон-процессам (`schedule:run`, воркер очереди) новые значения видны со
   следующей минуты — ждать минуту перед smoke-проверкой.
4. **Журнал обязателен.** Ротация без записи о том, когда и что заменяли, не
   закрывает инцидент: невозможно ответить, «какой ключ шифровал бэкап от
   12 октября». Журнал — §5, заполнять всегда.
5. **Случайное — генерирует машина.** `php -r "echo bin2hex(random_bytes(32));"`
   и `php artisan key:generate` (только для `APP_KEY`). Значения, выдаваемые
   чужими панелями (OAuth-токены, ключи провайдеров), копируются оттуда и
   собственной фантазией не сочиняются.

### Таблица приоритетов

| Приоритет | Секреты | Почему |
|---|---|---|
| 1 | `TICKET_QR_SECRET` | компрометация = неограниченный вход на любой сеанс подделанным билетом |
| 2 | `APP_KEY` | компрометация = подмена cookie-сессий и расшифровка шифрованных полей БД |
| 3 | `YOOKASSA_SECRET_KEY`, платёжные вебхуки | деньги: ложные/пропущенные вебхуки искажали бы «оплачено» |

| 5 | OAuth/SMTP/бэкап-токен | каналы наружу; ущерб меньше, ротация тривиальна |

## 2. Инвентаризация

| Секрет (`.env`) | Что защищает | Цена утечки | Цена ротации |
|---|---|---|---|
| `APP_KEY` | cookie-сессии (`web`-guard — инсталлер, админ-SPA), `Crypt::`-поля в БД | подмена сессий от имени любого; расшифровка шифрованных значений (см. §3.1) | обнуление cookie (все перелогинятся); старые шифрованные значения перестают расшифровываться — план в §3.1 |
| `TICKET_QR_SECRET` (арх. имя: `NABILET_QR_SECRET`) | HMAC-подпись QR билетов (`QrSigner`, версия `NB1`, `keyId` `k1`) | подделка билета, неотличимая для Checker'а | невалидация всех выданных QR — только в окно без сеансов (§3.2) |
| `NABILET_BACKUP_ENCRYPTION_KEY` | шифрование архивов `backup:run` | чтение бэкапов укравшим файл | старые архивы не расшифровать новым ключом — старый ключ хранить в журнале до истечения retention (§3.3) |
| `DB_PASSWORD` | MySQL | полный дамп базы | требует согласования с MySQL (§3.4) |
| `REDIS_PASSWORD` | Redis (кеш, дедуп алертов) | кеш и дедуп; заказов там нет | простая (§3.4) |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | приём платежей | закрепление платежей за чужим магазином | кабинет ЮKassa + пересохранение в админке (значения шифруются в `settings`, §3.5) |
| `YOOKASSA_WEBHOOK_SECRET` | необязателен: основной барьер — IP-allowlist (без него в проде уведомления отклоняются) | значим только если уведомления идут через ваш прокси | кабинет ЮKassa + `.env`/админка |
| `STRIPE_WEBHOOK_SECRET`, `KASPI_WEBHOOK_SECRET` | обязательны (HMAC-подпись, иначе уведомления отклоняются `WEBHOOK_NOT_AUTHENTICATED`) | ложные подписанные вебхуки = «оплачено» без оплаты | кабинет провайдера + `.env`/админка (§3.5) |
| `NABILET_WEBHOOK_SECRET` | **не используется кодом** — читателей env не существует; подписи исходящих вебхуков живут в подписках (`webhooks.secret_encrypted`, показывается один раз) | нет — строка мёртва | ротация не нужна; секрет подписки перегенерируется пересозданием подписки (§3.6) |
| `YANDEX_DISK_OAUTH_TOKEN` | загрузка бэкапов на Диск | доступ к нашим архивам | кабинет Яндекс.OAuth; после ротации прогнать `backup:run` и проверить (§3.7) |
| `MAIL_PASSWORD` | SMTP (письма: билеты, reset) | рассылки спама через ваш SMTP | панель SMTP-провайдера; smoke-письмо (§3.8) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | соц-вход Telegram | вход на сайт от чужого Telegram-аккаунта | BotFather `/revoke` (§3.9) |
| `YANDEX_CLIENT_SECRET`, `VK_CLIENT_SECRET` | OAuth-вход | вход под чужим аккаунтом (соц-вход по умолчанию выключен, см. PRODUCTION-READINESS §1) | кабинет провайдера, замена в `.env` (§3.9) |
| `NABILET_MATRIX_ACCESS_TOKEN` | подключение админ-уведомлений к Matrix | спам/порча в комнате — инцидент вы не узнаете | Synapse: logout устройств, перелогин, перезадать в админке (значение шифруется в `settings`) (§3.10) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | S3-совместимое хранилище медиа — только если `FILESYSTEM_DISK=s3` | чтение/перезапись объектов | кабинет S3-провайдера + `.env` |

Дополнение: часть секретов живёт НЕ в `.env` (для полноты журнал §5 ведёт и по
ним): `checkin_devices.device_token_hash` — bearer-доступ Checker-устройств
(выпускает админка: отзыв + выдача нового); `user_sessions.session_token_hash`
— bearer-сессии покупателей (sha256; аутентификация по хешу, поэтому ротация
`APP_KEY` их не задевает).

## 3. Сложные процедуры

### 3.1 `APP_KEY` — единственный, где ротируют не только строку

`Crypt::encryptString()` использует `APP_KEY`. Что шифруется им и лежит в БД
(инвентаризация перед ротацией обязательна):

| Место | Что лежит | Что теряется при ротации | Как лечить |
|---|---|---|---|
| `webhooks.secret_encrypted` | секреты подписок исходящих вебхуков | приёмники перестают принимать (подпись невалидна) | пересоздать каждую подписку, новый секрет передать приёмнику |
| `settings` (с `encrypted=1`) — `SettingsStore` | ключи ЮKassa, токен Matrix | админка не прочтёт старое значение (она его и раньше не показывала) | пересохранить ключи через админку (экран платежей шифрует заново при сохранении), перезадать токен Matrix (§3.10) |
| `AccountTokenService` (reset/verify-письма) | одноразовые токены в письмах | уже выданные письма перестают работать | ничего: TTL ≤ 30 мин — переотправить письмо нуждающемуся |
| cookie `web`-guard | админ-инсталлятор и SPA | перелогин всех участников | принять; именно это и нужно при подозрении на кражу cookie |

**Не страдает:** `user_sessions` (bearer `auth:api`) — токены хранятся хешем,
`sha256` не зависит от `APP_KEY`; очередь и корзина этим ключом не шифруются.

Порядок:

```bash
# 1. новый ключ
php artisan key:generate --show
nano .env                                   # APP_KEY=base64:…
php artisan config:clear
# 2. перелогин в админке обязателен (cookie невалидна)
# 3. пересохранить ключи ЮKassa в админке — шифрование уже новым ключом
# 4. Matrix-токен — §3.10
# 5. пересоздать подписки вебхуков, передать приёмникам новые секреты
# 6. smoke: логин, тестовая покупка, входящий вебхук payment.succeeded
```

Миграции и фронт при ротации `APP_KEY` не нужны — фронтенд об этом ключе не
знает.

### 3.2 `TICKET_QR_SECRET` — ротация в окно

Билеты подписываются HMAC (`NB1.<ticketId>.<token>.<hmac>`); проверка проходит
офлайн на Checker-устройствах, значит **все выпущенные билеты, подписанные
старым ключом, новым ключом отвергаются**: устройству нельзя заступать на смену
с бандлом старого «отпечатка ключа» (материал проверки несёт бандл — §43 схемы),
если сервер уже принял новый.

Правила обязательны:

1. Выбрать окно без активных сеансов и продаж (ночной интервал); продажи
   заморозить распоряжением — билеты, выпущенные до ротации, проверяться не
   будут.
2. Заменить секрет, `config:clear`, выдать свежий офлайн-бандл и
   пересинхронизировать каждое устройство (в админке — «отзыв + выдача»).
   Валидность бандлов ≤ 24 ч, так что плановая синхронизация вытянула бы
   значения сама — но после ротации проверить явно, до первого сеанса.
3. Уже погашенные билеты трогать не нужно: их проверка прошла. Непогашенные
   старые билеты становятся невалидны — это известная цена; сценарий
   компенсации (перевыпуск/возврат) не автоматизирован и живёт на уровне
   операционного процесса.

`QrSignerFactory` отказывается стартовать со слабым (< 32 байт) секретом или
невалидным `base64:`-префиксом — если после правки `.env` выпуск QR упал, это
ошибка в значении самого секрета, а не признак успешной ротации.

### 3.3 `NABILET_BACKUP_ENCRYPTION_KEY` — ключ «в склеп»

- Новый ключ применяется к СЛЕДУЮЩИМ бэкапам. Архивы, уже лежащие локально
  и на Диске, остаются зашифрованы старым.
- До истечения retention (`NABILET_BACKUP_KEEP=7` копий в очереди — примерно
  семь дней при ежедневном бэкапе) старый ключ держать **в журнале ротации**
  (§5), не в `.env` и не в репо.
- Проверка после ротации: забрать свежий архив, расшифровать новым ключом,
  убедиться, что дамп читается (`deploy-timeweb.md`, раздел бэкапов).
- Если утёк канальный доступ (Диск), это уже инцидент, а не плановое окно:
  ключи меняются немедленно, старые архивы считать прочитанными и принять это
  в оценке ущерба.

### 3.4 `DB_PASSWORD` / `REDIS_PASSWORD`

MySQL — создать нового пользователя, не трогая пока старого:

```sql
CREATE USER 'nabilet_next'@'localhost' IDENTIFIED BY '<новый>';
GRANT ALL PRIVILEGES ON nabilet.* TO 'nabilet_next'@'localhost';
FLUSH PRIVILEGES;
-- после успешного перелогина и smoke:
DROP USER 'nabilet_old'@'localhost';
```

Тестовая база (`nabilet_test_suite`) живёт по тем же переменным окружения
на CI/локали: если `DB_PASSWORD` сменился, обновите окружение тестов, иначе
CI-гейт `phpunit` упадёт по причине, не связанной с кодом.

Redis: `redis-cli CONFIG SET requirepass "<новый>"` и сразу же в `.env`.
На Redis только кеш и дедуп — минуты расхождения не фатальны, но
`config:clear` делать сразу.

### 3.5 Платёжные ключи (ЮKassa и провайдеры)

- `YOOKASSA_SECRET_KEY` живёт в двух местах: `.env` (bootstrap) и шифрованном
  значении `settings` (экран платежей). Экран шифрует по-новому при сохранении —
  меняются вместе с `APP_KEY` (§3.1).
- `YOOKASSA_WEBHOOK_SECRET` не обязателен: основной барьер для уведомлений —
  IP-allowlist `YOOKASSA_WEBHOOK_IP_ALLOWLIST` (официальные CIDR ЮKassa;
  `*` запрещён `ProductionSafetyProvider`). Подмена нужна только при
  проксировании уведомлений.
- `STRIPE_WEBHOOK_SECRET`/`KASPI_WEBHOOK_SECRET` — подпись обязательна; ротация
  идёт по кабинету провайдера: сначала выпустить новый секрет у них, затем
  внести у нас; на время рассинхронизации подписанные уведомления будут
  отвергаться — окно держать коротким.
- Smoke после любой платёжной ротации — тестовой суммой на проде (10 ₽) и
  проверка, что живой вебхук `payment.succeeded` попал в заказ и закрыл его
  (проверять в админке по заказу, не глазами на письма).

### 3.6 Исходящие вебхуки

Секреты подписок (`X-Nabilet-Signature`, HMAC-SHA256) не лежат в `.env`:
генерируются при создании подписки (`Str::random(48)`), хранятся шифрованно и
показываются приёмнику один раз. Ротация — пересоздать подписку (URL тот же),
передать новый секрет приёмнику; старый перестаёт работать.

### 3.7 `YANDEX_DISK_OAUTH_TOKEN`

Кабинет OAuth Яндекса → новый токен → `.env` → `php artisan backup:run` и
вручную проверить, что архив на Диске появился. За протухший бэкап скажет
`system:selfcheck` (алерт при `BACKUP_STALE_HOURS=26`) — но это не замена
ручной проверки сразу после ротации: алерту нужно пролежать до 26 часов,
чтобы сработать.

### 3.8 `MAIL_PASSWORD`

Панель SMTP → новый пароль → `.env` → `config:clear` → тест-письмо на реальный
ящик (не array-транспорт тестов). Убедиться, что `MAIL_MAILER=smtp`; ошибки
SMTP старого пароля будут видны в `storage/logs` до `config:clear`.

### 3.9 OAuth-провайдеры и Telegram

- `TELEGRAM_BOT_TOKEN`: BotFather `/revoke` — старый токен живёт ровно до
  отзыва; новый — в `.env`. `TELEGRAM_WEBHOOK_SECRET` отдельная величина
  (secret_token у `setWebhook`) — менять только если скомпрометирован и он.
- `YANDEX_CLIENT_SECRET`/`VK_CLIENT_SECRET`: кабинет приложения провайдера →
  новый секрет → `.env`; redirect_uri менять не нужно (совпадает с
  зарегистрированным). Соц-вход по умолчанию выключен (пустые креды —
  провайдер отвечает отказом, не 500), так что ошибка в этом блоке не валит
  витрину.

### 3.10 `NABILET_MATRIX_ACCESS_TOKEN`

Токен даёт полный доступ к аккаунту бота и не отзывается вместе с утратой
членства в комнате (см. `MATRIX.md`). Порядок: аккаунт бота в Synapse —
logout всех устройств, следующим логином получить новый токен, внести в
админке Matrix (значение шифруется в `settings`). Поле админки «пусто» не
означает «не задан» и не стирает значение: форма никогда не возвращает токен
назад — замена проходит сохранением нового значения, а не очисткой (правило
обратное другим настройкам, см. `MATRIX.md`).

## 4. Аварийная ротация (подозрение компрометации)

Если есть основания считать `.env` прочитанным (дамп/shell/устаревший архив
конфига), порядок — «самое опасное первым», каждый шаг со своим
`config:clear` и отметкой в журнале:

1. `TICKET_QR_SECRET` — по §3.2, но без вопроса «когда удобней»: продажи
   останавливаются до перевыпуска QR; потеря оборота — приемлемая цена
   против фальшивых билетов.
2. `APP_KEY` — по §3.1 (включая пересохранение всех шифрованных настроек).
3. `NABILET_BACKUP_ENCRYPTION_KEY`, `DB_PASSWORD`, `REDIS_PASSWORD`.
4. Платёжные ключи + пересоздать подписки исходящих вебхуков.
5. OAuth, SMTP, Matrix, S3 — партиями, не дожидаясь окончания шагов 1–4.

После: smoke-набор (health, логин, покупка, входящий платёжный вебхук, скан
чекина), отметка в журнале §5, короткий разбор «как могла случиться утечка».

## 5. Журнал ротации

Заполняется при каждой ротации; временные старые ключи — сюда, не в `.env`:

| Дата | Секрет | Причина | Исполнитель | Согласовано | Старый ключ (если нужен для склепа) | Проверка |
|---|---|---|---|---|---|---|
| — | — | плановая / авария | | | | smoke |

Пример заполненной строки: `2026-11-04 · NABILET_BACKUP_ENCRYPTION_KEY ·
плановая · ops · да · hex:abc…def (истёк 2026-11-11) · расшифровка дампа
читается`.
