# ⚠ Эти миграции не являются базовой схемой

**Источник истины — пакет `nabilet_core_spec/`:**

```
nabilet_core_spec/migrations.sql              консолидированный DDL (64 таблицы)
nabilet_core_spec/migrations/001..010         сплит-миграции в порядке исполнения
```

Файлы в этом каталоге написаны **до** появления пакета и описывают **другую** схему:
66 таблиц вместо 64, с другими именами (`event_sessions`, `rows`, `tables`, `ab_tests`,
`privacy_consents`, `data_requests`, `outbox_messages`) и другой моделью inventory
(enum состояния вместо `capacity` + `available_quantity`).

> **Обновлено 2026-09-20.** Пакет вырос с 56 до 64 таблиц: миграция
> `010_tz_gaps.sql` вернула в него шесть возможностей ТЗ, которых в пакете не было
> (промокоды, переводы площадок и страниц, медиатеку, офлайн-бандлы, `user_roles`,
> статус билета `revoked`). Поэтому раздел 1 ниже — уже история: эти возможности в
> пакете теперь есть, хотя и под другими именами. Различия в именах и в модели
> inventory никуда не делись, поэтому **запускать эти миграции по-прежнему нельзя**.

Они сохранены по двум причинам.

## 1. Они покрывают возможности, которых в пакете нет

Пакет потерял часть требований исходного ТЗ `Мысли.md`. Проверено поиском по файлам:

| Возможность | Требование ТЗ | В пакете |
|---|---|---|
| **Промокоды** | `Мысли.md` §86 — сущность `PromoCode` с условиями fixed / percent / first_purchase / event / category / date / quantity | **отсутствует**; в `Техническая спецификация разработки.md` слово «промокод» не встречается ни разу |
| **Переводы площадок и страниц** | §73 — явно перечислены `event_translations`, `venue_translations`, `page_translations` | есть только `event_translations` |
| **Медиатека** | §73 базовый `locale / translation_key / translation_value`; `Media/` как модуль | нет таблицы; только URL-колонки `logo` / `poster` / `cover` |
| **Офлайн-бандлы Checker** | §43 — устройство загружает event, session, valid/revoked tickets, public key | нет таблицы для учёта выданных бандлов |
| **Много-ко-многим роли** | `user_roles` | в пакете одна роль на пару (пользователь, организация) |

Здесь эти таблицы есть: `promo_codes`, `promo_code_usages`, `venue_translations`
(через `translations`), `event_media`, `media`, `offline_bundles`, `user_roles`,
`backups`, `api_logs`, `ai_providers`, `ai_requests`.

Подробнее: `docs/REVIEW-spec-bundle.md`, раздел «Функциональные пробелы пакета».

## 2. Их больше никто не проверяет

Раньше эти миграции исполнял `tools/verify-schema.php` — через стабы Laravel Schema и
20 проверок инвариантов на SQLite. **Файл удалён 2026-09-20:** `database/migrations/`
теперь содержит актуальные миграции под 64 таблицы пакета, и тот инструмент начал бы
проверять не то, на что рассчитан.

Ему на смену пришёл `tools/verify-migrations.php`: он исполняет актуальные миграции и
сверяет результат с `nabilet_core_spec/migrations.sql` — таблицы, колонки, именованные
индексы, внешние ключи с `ON DELETE`, CHECK-ограничения и триггер. Расхождение — это
падение, а не предупреждение.

Настоящая проверка схемы пакета идёт **на реальном MySQL 8.4.11**
(`docs/ARCHITECTURE.md` §13).

## Что нужно сделать

Laravel-миграции для боевой схемы **ещё не написаны**. Их нужно сгенерировать из
пакета — с учётом `organization_id` (см. `docs/ARCHITECTURE.md` §6) и решением по
промокодам, переводам и медиатеке.

Пока это не сделано, **не запускайте** `php artisan migrate` на этих файлах: получите
схему, несовместимую с пакетом и с `docs/openapi.yaml`.
