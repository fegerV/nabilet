# Контракт с backend

Приложение использует четыре эндпоинта. Все запросы идут с
`Authorization: Bearer nbck_…` (токен устройства проверяющего), `Accept:
application/json`, `User-Agent: NabiletChecker/<версия> (Android)`. Тело —
`application/json; charset=utf-8`.

Источник правды — `docs/openapi.yaml` в корне репозитория и код модуля
`App\Modules\Checkin`. Ниже — то, на что реально опирается приложение.

## 1. `POST /api/v1/checkin/validate`

Проверка, что сервер и токен друг другу подходят. Отдельного «кто я» эндпоинта
нет, поэтому используется пробный QR: сервер проверяет токен **до** подписи QR.

```json
{
  "qr_payload": "NB1.probe.probe.probe",
  "session_id": "0"
}
```

| Ответ | Что означает для приложения |
| --- | --- |
| `200` (тело с `result: invalid_signature`) | токен принят |
| `401` / `403` | токен отклонён — сканирование блокируется |
| `429`, `5xx`, сеть | состояние токена не меняется, показывается ошибка связи |

Пробный QR заведомо не проходит HMAC, поэтому других вердиктов тут не будет.
`session_id: "0"` валиден по правилам запроса (только `required`), а до
разрешения сеанса дело не доходит: подпись проверяется раньше.

## 2. `POST /api/v1/checkin/use`

Авторитетная онлайн-проверка.

```json
{
  "qr_payload": "NB1.<ticketId>.<token>.<signature>",
  "session_id": "1001",
  "client_scan_id": "0f4b6f0e-6a7a-4b0e-9f0e-2f3c1a9d8c11",
  "scanned_at": "2026-11-04T18:30:12Z",
  "mode": "online"
}
```

`session_id` — внутренний числовой id сеанса (сервер принимает и `public_id`,
но приложение берёт `session` из бандла и хранит его как строку с числом).
`client_scan_id` — UUID, сгенерированный до запроса: он же ключ идемпотентности
на сервере (`uq_ticket_scans_client(device_id, client_scan_id)`).

Ответ `200`:

```json
{
  "data": {
    "result": "valid",
    "ticket": { "ticket_number": "A-001", "...": "..." },
    "message": "Билет действителен."
  }
}
```

Ответ `409` — **не ошибка транспорта**, а вердикт (`already_used`,
`conflict`): тело имеет тот же вид, `data.result` заполнен. Приложение
разбирает его как обычный результат.

Возможные `data.result`: `valid`, `already_used`, `cancelled`, `refunded`,
`expired`, `invalid_signature`, `wrong_session`, `wrong_event`,
`unknown_ticket`, `conflict`.

Обработка в приложении:

| Ответ | Действие |
| --- | --- |
| `200` / `409` с `data.result` | вердикт показывается и пишется в журнал как `online`, в очередь не ставится |
| `401` / `403` | «токен не принят», сканирование блокируется |
| `429`, `5xx`, таймаут, обрыв | офлайн-фолбэк по бандлу |
| `422` | показывается ошибка сервера, скан не записывается |
| ответ без `data.result` | `ParseError`, скан не записывается |

## 3. `POST /api/v1/checkin/sync`

Отправка очереди офлайн-сканов. Один запрос — один сеанс, поэтому очередь
группируется по `session_id`; внутри сеанса батчи по 200.

```json
{
  "device_id": "01JDEVICE0000000000000000",
  "session_id": "1001",
  "scans": [
    {
      "client_scan_id": "0f4b6f0e-6a7a-4b0e-9f0e-2f3c1a9d8c11",
      "ticket_id": "01JTICKET0000000000000001",
      "scanned_at": "2026-11-04T18:30:12Z",
      "result": "valid",
      "mode": "offline"
    }
  ]
}
```

`device_id` — публичный id устройства из бандла. Сервер сверяет его с
аутентифицированным устройством и на несовпадение отвечает `403
DEVICE_MISMATCH`; приложение проверяет то же самое локально до отправки.

`result` — то, что устройство решило офлайн. Сервер не обязан с ним
согласиться: он пересчитывает вердикт и возвращает свой. Для скана с
невалидной подписью сервер вернёт `unknown_ticket`, и локальная запись будет
перезаписана — журнал обязан показывать правду, а не оптимистичную догадку.

Ответ:

```json
{
  "data": {
    "accepted": 10,
    "duplicates": 1,
    "conflicts": 2,
    "rejected": 0,
    "results": [
      { "client_scan_id": "…", "result": "valid", "message": null }
    ]
  }
}
```

`results` применяется к локальным строкам по `client_scan_id`: `synced = 1`,
`result` и `server_message` заменяются серверными.

## 4. `GET /api/v1/offline-bundles/{id}`

Скачивание бандла по публичному id.

```json
{
  "data": {
    "id": "01JBUNDLE0000000000000000",
    "checkin_device_id": "01JDEVICE0000000000000000",
    "event_id": "01JEVENT0000000000000000",
    "session_id": "01JSESSION000000000000000",
    "bundle_hash": "7c198be9c28bef7620750c556007ad2151891af67049dba8ab2a1d68ea861bfe",
    "schema_version": 1,
    "public_key_fingerprint": "sha256:8f14e45fceea167a5a36dedd4bea2543",
    "ticket_count": 2,
    "revoked_count": 1,
    "payload_json": { "version": 1, "device": "…", "org": 7, "event": 42, "session": 1001, "key": "…", "valid": [], "revoked": [] },
    "status": "generated",
    "generated_at": "2026-11-04T17:00:00+00:00",
    "downloaded_at": null,
    "expires_at": "2026-11-05T01:00:00+00:00"
  }
}
```

`payload_json` приходит объектом; приложение принимает и строку, если транспорт
когда-нибудь изменится. Хеш считается не по принятому тексту, а по
каноническим байтам, пересобранным из полей (`BundleCanonical`), поэтому
различия в сериализации не ломают сверку.

Канонический порядок ключей — часть контракта:
`version, device, org, event, session, key, valid, revoked`; в билете —
`id, n, s`. Байты должны совпадать с
`json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE)`.
Это закреплено тестом `BundleCanonicalTest` с хешами, посчитанными реальным
PHP 8.4, включая кириллицу, кавычки, обратный слэш, перевод строки, табуляцию,
эмодзи и U+2028.

`expires_at` в OpenAPI nullable, но сборщик бандла всегда его выводит.
Приложение относится к отсутствию `expires_at` как к ошибке: бандл без срока
жизни — это вечный пропуск.

## 5. Ограничение backend: список бандлов недоступен устройству

```
GET /api/v1/checkin-devices/{device}/bundles   → 403 для nbck_-токена (только админ)
```

Устройство не может само узнать, какой бандл ему выдан, поэтому оператор
вводит публичный id вручную. Приложение не пытается обойти авторизацию и не
хранит админский токен.

### Предлагаемые доработки backend

1. **`GET /api/v1/checkin/bundles`** — скоуп проверяющего токена, возвращает
   бандлы только для аутентифицированного устройства, отсортированные по
   `generated_at`. Тогда экран настройки сможет показать «доступен новый бандл»
   вместо ручного ввода id.
2. **Подписанный бандл** — добавить в ответ `signature` (Ed25519 или HMAC
   ключом, которого нет на устройствах) и `signing_key`/`key_id`, чтобы
   приложение проверяло авторство, а не только целостность. Сейчас
   `public_key_fingerprint` — отпечаток ключа QR, а не ключ проверки.
3. **`session_id` в `/checkin/use`** — сделать необязательным, выводя сеанс из
   билета. Сейчас приложение обязано знать сеанс заранее, поэтому event-wide
   бандл (без сеанса) для офлайн-режима бесполезен: синхронизация требует
   `session_id`.

Пока этих изменений нет, приложение работает в описанных границах и честно
об этом сообщает в интерфейсе и документации.
