## 3. Дефекты, доказанные исполнением

### 3.1 Нет CHECK-ограничений — инвариант остатка не защищён

```sql
UPDATE inventory_items SET available_quantity = -1;          -- ВЫПОЛНЕНО
UPDATE inventory_items SET available_quantity = capacity+50;  -- ВЫПОЛНЕНО
UPDATE inventory_items SET capacity = 0;                      -- ВЫПОЛНЕНО
UPDATE inventory_items SET type = 'bogus';                    -- ВЫПОЛНЕНО
UPDATE tickets SET status = 'nonsense';                       -- ВЫПОЛНЕНО
```

MySQL 8.4 поддерживает настоящие `CHECK`-ограничения. Сам `migrations.sql` признаёт пробел
комментарием в конце файла («Recommended application-level CHECKS»). Но пока проверка живёт
только в приложении, **любая ошибка в коде даёт отрицательный остаток молча**, без сигнала.

Дешёвое усиление:

```sql
ALTER TABLE inventory_items
  ADD CONSTRAINT ck_inventory_qty   CHECK (available_quantity BETWEEN 0 AND capacity),
  ADD CONSTRAINT ck_inventory_type  CHECK (type IN ('seat','standing'));
ALTER TABLE tickets
  ADD CONSTRAINT ck_ticket_status   CHECK (status IN ('issued','used','cancelled','refunded','expired'));
ALTER TABLE sectors
  ADD CONSTRAINT ck_sector_type     CHECK (type IN ('seated','standing','mixed'));
```

### 3.2 Hold не защищён на уровне БД

| Попытка | Результат |
|---|---|
| Второй hold на то же место | **принят** |
| `quantity = 999` на место ёмкостью 1 | **принят** |
| `expires_at` в прошлом | **принят** |

У `seat_holds` нет ни UNIQUE, ни CHECK. Это осознанный компромисс (holds аддитивны по
количеству для standing-зон), но означает, что **единственная защита — сервисный слой**.
Для мест (`type='seat'`) имеет смысл частичный уникальный индекс активного hold.

### 3.3 Неизменяемость опубликованной схемы не обеспечена

```sql
UPDATE hall_schema_versions SET schema_json = '{"v":999}' WHERE status = 'published';  -- ВЫПОЛНЕНО
UPDATE hall_schema_versions SET version = 99              WHERE status = 'published';  -- ВЫПОЛНЕНО
```

§20 и §98 объявляют опубликованную версию неизменяемой, комментарий в DDL это повторяет,
но **ничто не мешает изменению**. Удаление при этом блокируется (FK `sessions` RESTRICT).

Это **самый опасный из app-level пробелов**: один случайный `save()` в Eloquent молча
переписывает геометрию зала, на которую ссылаются уже проданные сеансы. Историческая
целостность теряется без единой ошибки. Нужен либо `BEFORE UPDATE`-триггер, либо guard
в модели + запрет массового обновления.

### 3.4 NULL-distinctness

Строка `inventory_items` с обоими NULL (`seat_id` и `standing_zone_id`) **допускается и
дублируется без ограничений**: в MySQL NULL-значения в UNIQUE-ключе считаются различными.
Оба уникальных ключа работают лишь потому, что ровно одно из пары полей заполнено.
То же в `ab_assignments` (`uq_ab_assignment_user` / `uq_ab_assignment_anon`): пользователь
может получить назначение дважды — как аноним и как авторизованный.

### 3.5 Мультитенантность тонкая

`organization_id` присутствует только у **12 из 56** таблиц:
`ab_experiments, api_keys, audit_logs, checkin_devices, embed_domains, events, orders,
pages, ticket_templates, user_organization, venues, webhooks`.

**Отсутствует** у: `tickets`, `payments`, `refunds`, `carts`, `cart_items`, `order_items`,
`inventory_items`, `seat_holds`, `ticket_scans`, `sessions`, `analytics_events`,
`payment_transactions`, `notifications`, `privacy_requests` и др.

Следствие: тенант-скоуп для билетов, платежей и check-in требует JOIN в 2–3 шага
(`tickets → orders → organization_id` либо `tickets → events → organization_id`).
**Любой запрос, забывший JOIN, — это утечка между тенантами** (BOLA/IDOR), причём именно
на самых чувствительных сущностях. Это архитектурное расхождение с fail-closed подходом,
принятым в сессии 1, и его стоит обсудить отдельно.

### 3.6 OpenAPI

- **33 из 77** операций не описывают ни одной 4xx-ошибки — включая `GET /api/v1/admin/orders`,
  `/admin/tickets`, `/admin/webhooks`, `/admin/checkin/devices`, `GET /api/v1/me`, `/me/orders`,
  `GET /tickets/{ticket}/qr` и `/pdf`. Для админских ручек отсутствие 401/403 затрудняет
  и кодогенерацию, и security-ревью.
- **76 из 77** операций не описывают 5xx; при этом 503 задокументирован лишь у одной,
  хотя режим обслуживания в спеке есть.
- `POST /api/v1/admin/analytics/events` находится под `/admin/`, но намеренно без
  аутентификации — неудачное пространство имён, приглашающее будущую ошибку.
- Объявлены и не используются: схема `Organization`; параметры `CartItemIdPath`,
  `PublicIdPath`, `UserSessionIdPath`. При этом `DELETE /me/sessions/{session}` переиспользует
  `SessionIdPath` вместо специально созданного `UserSessionIdPath`.
- Схема безопасности в целом продумана: 3 схемы (`bearerAuth`, `checkerAuth`, `checkoutAuth`),
  54 операции с явным `security`, 23 публичные — все обоснованно (auth, каталог, гостевая
  корзина, health, вебхук). Единственное замечание: для `POST /webhooks/yookassa` требование
  проверки подписи нигде не задокументировано.

### 3.7 Прочие расхождения спеки и миграции

| Пункт | Спека | Миграция |
|---|---|---|
| §22 | таблица `rows` | `hall_rows` |
| §91 | `ip`, `type` | `ip_address`, `rule_type` |
| §69 | `docs/openapi.yaml`, Swagger `/api/docs`, Redoc `/api/redoc` | файл в корне, маршрутов нет |

`provider_event_id` надёжнее, чем заголовок), фактическое покрытие идемпотентности —
11 операций против 5 требуемых.

### 3.10 Функциональные пробелы пакета относительно исходного ТЗ

Это самое серьёзное из найденного. Пакет не просто переименовал таблицы — он **потерял
требования исходного `Мысли.md`**, и потеря произошла на уровне производной спеки, а не
только DDL.

**Промокоды.** `Мысли.md` §86 посвящён целиком этой сущности:

```
# 86. Промокоды
Сущность: PromoCode
Условия: fixed / percent / first_purchase / event / category / date / quantity
Например: WELCOME10 → -10%
```

В `Техническая спецификация разработки.md` слово «промокод» **не встречается ни разу**
(0 совпадений на 4603 строки). В `migrations.sql` и всех 8 сплит-файлах нет ни одной
таблицы промокодов. При этом `orders.discount_amount` и `order_items.discount_amount`
существуют — то есть скидка предусмотрена, но взять её неоткуда: нет ни справочника
кодов, ни счётчика использований, ни связи заказа с кодом.

**Переводы площадок и страниц.** §73 явно перечисляет три таблицы:

```
event_translations
venue_translations
page_translations
```

В пакете есть только `event_translations`. `venue_translations` и `page_translations`
отсутствуют — при том, что §73 объявляет локализацию URL (`/ru/events/…`, `/en/events/…`)
сквозной.

**Медиатека.** §73 определяет базовую модель `locale / translation_key /
translation_value`; в структуре проекта присутствует модуль `Media/`. В пакете нет
таблицы медиа — только URL-колонки `logo`, `poster`, `cover`. Следствие: нет учёта
загрузок, alt-текста, вариантов размера, порядка в галерее. Отметим честно: §2336
`Мысли.md` помечает медиа как «опционально», поэтому это пробел мягче двух предыдущих.

**Офлайн-бандлы Checker.** §43 требует, чтобы Android-устройство перед мероприятием
загрузило event, session, список действительных и отозванных билетов и публичный ключ.
Таблицы для учёта выданных бандлов (что именно и когда получило устройство) нет —
есть только `checkin_devices`.

**Роли много-ко-многим.** В пакете роль одна на пару (пользователь, организация) —
`user_organization.role_id`. Разделяемая таблица `user_roles` отсутствует.

**Состояние `revoked` у билета.** §43 требует, чтобы Android Checker перед мероприятием
загружал список **отозванных** билетов, а §44 описывает конфликты офлайн-сканирования,
которые разрешаются именно отзывом. Но `tickets.status` перечисляет только
`issued / used / cancelled / refunded / expired` — состояния `revoked` нет.

Свести `cancelled` и `revoked` в одно нельзя без потери смысла: `cancelled` — отмена с
возвратом или по инициативе покупателя; `revoked` — мошенничество, чарджбэк, разбор
дубля, часто **без** возврата. Различие существует ровно ради аудит-следа и отчётности.

Отдельно отметим: добавленное ограничение `ck_tickets_status` построено на перечислении
из самого пакета, поэтому оно **закрепляет** отсутствие `revoked` — теперь состояние
отклоняется базой. Если `revoked` решено вернуть, ограничение нужно расширить
одновременно с изменением схемы.

**Итого.** Шесть возможностей исходного ТЗ не имеют отражения в схеме пакета. Их
нельзя «дописать по ходу»: промокоды, переводы и отзыв билетов задевают `orders`,
`order_items`, публичный каталог и контур допуска на входе.

Рекомендация: до начала реализации решить по каждой — восстанавливать из `Мысли.md`
или сознательно выносить за скоуп v1. Молчаливая потеря требования — это ровно тот
класс дефекта, который обнаруживается на приёмке, а не в ревью.

## 4. Конфликт с артефактами сессии 1 — требуется решение

| Тема | Сессия 1 | Новый пакет (спека) |
|---|---|---|
| Формат ошибок | RFC 7807 `application/problem+json` | §66: `{"error":{"code","message","details"}}` |
| Таблиц | 66 | 56 |
| Сеансы | `event_sessions` | `sessions` |
| Залы | `rows`, `tables` | `hall_rows`, `hall_tables` |
| Инвентарь | `status`-enum | `capacity` + `available_quantity` |
| A/B | `ab_tests` | `ab_experiments` |
| Приватность | `privacy_consents`, `data_requests` | `consents`, `privacy_requests` |
| Вебхуки | `outbox_messages` | `webhook_events` |
| API | 24 пути / 26 операций | 68 путей / 77 операций |

**Конфликт по формату ошибок — прямой и материальный.** §66 задаёт вложенный конверт
`{"error":{"code","message","details"}}`; `docs/openapi.yaml` сессии 1 описывает RFC 7807
(`application/problem+json`, схема `Problem`). Одновременно жить не могут.

Дополнительно: в репозитории **три копии `openapi.yaml`** — в корне, в `nabilet_core_spec/`
и в `docs/`. Их нужно свести к одной.

### Рекомендация

1. **Источник истины — пакет.** Он выведен из ТЗ, проверяем и прошёл матрицу
   конкурентности. Документацию сессии 1 (`docs/DATABASE.md`, `docs/openapi.yaml`,
   `docs/ARCHITECTURE.md`) привести к пакету.
2. **`app/Core` сессии 1 сохранить как реализацию** — ядро не зависит от Laravel и проходит
   152 теста; модель `inventory_items` в нём нужно перевести с `status`-enum на
   `capacity` + `available_quantity`.
3. **Модель количества из пакета принять** — она строго выразительнее: standing-зона продаёт
   N единиц с одной строки, что `status`-enum не выражает.
4. **Три копии `openapi.yaml` свести к одной** (`docs/openapi.yaml`), остальные удалить.
5. **Внести в спеку §28/§39** поля `converted_at`, `ticket_index`, `refunded_at`, `expired_at`.
6. **Добавить CHECK-ограничения** (§3.1) и guard неизменяемости (§3.3).
7. **Обсудить отдельно** тонкую мультитенантность (§3.5) — это единственное расхождение,
   где пакет объективно слабее, и оно лежит в зоне безопасности.

## 5. Приложение: как воспроизвести

```bash
# MySQL 8.4 в Docker (обязателен seccomp=unconfined для Docker 18.09.2)
docker run -d --name nabilet-mysql --security-opt seccomp=unconfined \
  -e MYSQL_ROOT_PASSWORD=rootpass -e MYSQL_DATABASE=nabilet \
  -p 3307:3306 mysql:8

# Проверка DDL
docker exec nabilet-mysql mysql -uroot -prootpass \
  -e "CREATE DATABASE nabilet_verify CHARACTER SET utf8mb4;"
docker exec -i nabilet-mysql mysql -uroot -prootpass -D nabilet_verify < migrations.sql

# Структурные метрики
docker exec nabilet-mysql mysql -uroot -prootpass -N -B -e "
SELECT COUNT(*) FROM information_schema.tables
 WHERE table_schema='nabilet_verify' AND table_type='BASE TABLE';"
```

PHP не может подключиться к MySQL напрямую — sandbox блокирует сокеты. Все проверки
выполнены через `docker exec`, что для DDL-верификации эквивалентно.

### О PHP-бинарнике VertexCMS

Проверен `C:\Users\Professional\AppData\Local\VertexCMS\tools\php\php.exe`:
PHP 8.4.21 (ZTS, VC++ 2022 x64), есть `pdo_mysql`, `mysqli`, `curl`, `openssl`, `mbstring`,
`gd`, `zip`, `bcmath`. **Расширения на месте, но соединение всё равно не проходит:**

```
SQLSTATE[HY000] [2002] Сделана попытка доступа к сокету методом, запрещенным правами доступа
```

То есть блокирует не PHP, а sandbox-политика на исходящие сокеты — смена бинарника
проблему не решает. `docker exec` остаётся рабочим путём. Запустить `php artisan migrate`
против этого MySQL из песочницы по-прежнему нельзя; для проверки DDL это не требуется.

## 6. Финальная верификация после сверки: что нашлось и что исправлено

Проход выполнялся уже **после** приведения документации к пакету. Цель — проверить, что
правки не сломали то, что работало, и что инструменты репозитория не врут. Найдено семь
дефектов, шесть из них — регрессии, внесённые самой сверкой.

### 6.1 Сломанный HTTP-обработчик ошибок (критично)

`app/Core/Errors/AppError::toProblem()` был переименован в `toResponse()` (переход на
конверт §66), но `bootstrap/app.php` продолжал вызывать **старое имя**:

```php
return response()->json($e->toProblem($requestId), $e->status, [
    'Content-Type' => 'application/problem+json',
]);
```

Последствия, если бы ушло в прод: любой операционный `AppError` падал бы с
`Call to undefined method`, а клиент вместо конверта §66 получал бы `problem+json`.
**Почему не поймали тесты:** `ErrorModelTest` проверяет `AppError` напрямую, а обработчик
живёт в `bootstrap/app.php` и требует установленного Laravel, которого в песочнице нет
(нет доступа к Composer/Packagist). Это была слепая зона.

Исправлено: `toResponse()`, `application/json`, тело фоновой 500-й — тоже конверт §66
(`{"error":{"code":"INTERNAL_ERROR","message":…,"request_id":…}}`) вместо полей RFC 7807.
Добавлен `tests/Unit/ErrorEnvelopeWiringTest.php` — статические проверки бутстрапа плюс
контроль, что все ссылки на классы `Nabilet\Core\*` в нём разрешаются в существующие файлы.
**Проверено, что guard не пустой:** при возврате `toProblem()` тест падает с двумя
ошибками, при откате — снова зелёный.

### 6.2 Консолидированный DDL пакета не содержал усиления

`nabilet_core_spec/migrations.sql` (оригинальный файл пакета) **не содержал** 009-усиления,
хотя сплит-набор `nabilet_core_spec/migrations/001..009` его содержит. То есть применение
консолидированного файла давало незащищённую схему, а применение сплита — защищённую.
Расхождение — ровно один блок (проверено `diff`: единственный хунк).

Исправлено: файл приведён к корневому `migrations.sql`. **Проверено исполнением:**
`nabilet_core_spec/migrations.sql` на чистой БД даёт 56 таблиц / 24 CHECK / 1 триггер.

### 6.4 `tools/verify-openapi.php` проверял контракт сессии 1

Инструмент был написан под OpenAPI сессии 1 и на пакете давал **6 passed / 5 failed**.
Три «падения» были ложными, два — настоящими:

| Проверка | Диагноз |
|---|---|
| path-параметры | **ложное**: пакет объявляет их через `$ref: '#/components/parameters/…'`, а также inline в развёрнутой форме `- in: path` / `name: X`; регулярка инструмента видела только однострочную форму |
| неиспользуемые компоненты | **ложное**: `securitySchemes` ссылаются по имени в `security:`, а не через `$ref` |
| идемпотентность | **ложное**: инструмент искал `/sessions/{sessionId}/holds`, тогда как в пакете hold — это `POST /api/v1/carts/{cart}/items` |
| деньги в минорных единицах | **настоящее**: схема `MoneyTotals` содержала голый `{ type: integer }` без пояснения, что это копейки (§9 ТЗ) |
| QR без персональных данных | **настоящее**: свойство не было задокументировано, хотя ТЗ требует его дважды (стр. 1370 и 4285) |

Исправлено с обеих сторон:
- **Контракт:** `MoneyTotals` получила описание «integer minor units (kopecks)» и описания
  полей; эндпоинт `/tickets/{ticket}/qr` — явное «payload MUST NOT contain personal data».
- **Инструмент:** разрешает `$ref`-параметры, учитывает `security:`, проверяет реальные пути
  hold/order и реальные формулировки. Принимает путь к файлу аргументом, поэтому проверяет
  обе копии контракта. Итог — **11 из 11 PASS** на обеих.

Попутно устранена гигиеническая проблема: компоненты `CartItemIdPath` и `UserSessionIdPath`
были объявлены, но не использовались — соответствующие пути объявляли параметр inline, а
`/me/sessions/{session}` ссылался на `SessionIdPath` (путь сеанса события, а не сессии
пользователя — смысловая ошибка). Компоненты подключены по назначению.

### 6.5 `tools/verify-schema.php` падал с фатальной ошибкой

Инструмент разбирает Laravel-миграции **сессии 1** (66 таблиц, другая схема) и в конце
исполняет DDL через SQLite. В этой сборке PHP `pdo_sqlite` отсутствует (есть только
`mysql`), поэтому инструмент завершался необработанным `PDOException: could not find driver`
— выглядело как сломанный репозиторий.

Исправлено: добавлено явное предупреждение `SUPERSEDED TOOL` со ссылкой на актуальный путь
проверки, и корректный пропуск секций 3–4 при отсутствии драйвера. Фатала больше нет.

### 6.6 Проба неизменяемости `hall_id` ничего не проверяла

Проба «move schema_json to a different hall» использовала
`UPDATE … SET hall_id=1 WHERE id=1 AND hall_id<>1` — условие не совпадало ни с одной строкой,
поэтому проверялось отсутствие изменений, а не запрет. Исправлено: проба создаёт второй зал
и переносит на него **опубликованную** версию (BLOCKED триггером) и **черновик** (ALLOWED).
