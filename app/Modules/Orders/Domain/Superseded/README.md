# Superseded: домен оформления заказа

**Эти классы не участвуют в боевом пути.** Каталог — надгробие, не библиотека.

## Что здесь

`OrderPlacement::assess(CartCheckout): CheckoutVerdict` — цепочка проверок
«корзина → заказ»: активность корзины, непустота, правила количества, наличие
единиц, покрытие холдами, дрейф цены. Плюс её типы-спутники: `CartCheckout`
(вход), `CheckoutLine` (строка), `CheckoutVerdict` (вердикт), `CartState`
(состояния корзины для проверки).

## Почему здесь

`grep -rn "new OrderPlacement" app/` пуст. Единственный потребитель —
`tests/Unit/OrderPlacementTest.php`. Классы ссылаются друг на друга и больше
ни на что: `CheckoutVerdict` берёт константы причин из `OrderPlacement`, и это
всё внешнее использование.

## Где на самом деле живёт оформление

`Nabilet\Modules\Cart\Services\CartService::checkout()` — валидация inline:
токен покупателя, `carts.expires_at`, непустота, окно продаж
(`Session::isSellableAt()`), неотрицательный остаток, отказ по промокоду.
Затем напрямую создаются `Order` и `OrderItem`.

## Чего в боевом пути НЕТ, а здесь есть

Двух проверок, которые эта цепочка добавляла:

- **покрытие холдами** — что единицы удержаны именно этой корзиной и холд ещё
  конвертируем (`OrderPlacement::REASON_HOLD_MISSING` / `REASON_HOLD_EXPIRED`);
- **дрейф цены** — организатор поменял цену, пока корзина была открыта
  (`REASON_PRICE_INCREASED` блокирует, `WARNING_PRICE_REDUCED` предупреждает).

И контракт `REASON_PRECEDENCE`: какую причину отказа показать первой, когда
проблем несколько.

## Как включить (продуктовое решение, не рефакторинг)

1. Собрать `CartCheckout` из `Cart` + активных `SeatHold` + `InventoryStock`
   внутри `CartService::checkout()`.
2. Вызвать `assess()` и отобразить `CheckoutVerdict::refused()` в §66-ошибку.
3. Проверить, что новые отказы не ломают существующие сценарии оплаты —
   это ужесточение валидации в денежном пути.

До этого шага **правка любого файла здесь не меняет поведение системы**.
