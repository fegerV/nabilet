# Контракт JSON-схемы зала (версия 1.0)

Документ фиксирует формат, который теперь проверяется сервером (`HallService::validateSchemaPayload`) и используется редактором/импортёрами.

## 1. Версия

```json
{ "version": "1.0", "canvas": { "width": 900, "height": 620 }, ... }
```

- Поддерживаются `"1.0"`, `"1"` и числовое `1` (legacy-экспорт).
- Отсутствующее поле трактуется как legacy-схема до версионирования и принимается.
- Любое другое значение → 422 `SCHEMA_VALIDATION_FAILED`, поле `version`.

## 2. Пространства координат

| Пространство | Кто использует | Правило |
|---|---|---|
| Холст (px) | Konva-редактор, `staticObjects[].x/y`, `sectors[].x/y` | целые/дробные числа,>|1e4| отвергается |
| Локальные координаты сектора | `sectors[].seats[].x/y` | складываются со смещением сектора при проверке пересечений и конвертации |
| Нормализованная сетка | `InventoryService`, витрина | `unit = 60 / canvas.width`, единый масштаб для X и Y, округление до 3 знаков |
| Экранные координаты | `CoordSeatMap` | `projectPoint()` из `lib/seatViewport`, без инверсии Y |

Публичный рендерер **не перекомпоновывает** объекты: стоячие зоны с геометрией рисуются в своей точке; легаси-зоны без геометрии по-прежнему получают нижнюю полосу.

## 3. Объекты

### Sector

```json
{ "id": "s-1", "name": "Партер", "code": "A", "type": "seated|standing|mixed",
  "shape": "grid|arc|table", "x": 0, "y": 0, "priceMinor": 500000,
  "rowPrices": { "1": 600000 }, "seats": [] }
```

- Идентификатор — `id`, а не `name`.
- Номер места уникален внутри ряда; id места уникален в схеме.
- Действующая цена: место → ряд → сектор, всегда целые копейки ≥ 1.

### Standing zone

Хранится как `staticObjects[]` с `kind: "standing"`:

```json
{ "id": "zone-left", "kind": "standing", "text": "Танцпол", "capacity": 100,
  "priceMinor": 120000, "x": 40, "y": 60, "width": 200, "height": 120,
  "rotation": 0, "opacity": 1, "locked": false }
```

- `id` обязателен для новых схем и используется для дедупликации; две зоны с одинаковым `text` и разными `id` — две независимые зоны.
- Вместимость — число 1..10000; **не** массив виртуальных мест.
- В инвентарь попадает одна позиция `type=standing` с `capacity`/`available_quantity`; геометрия едет в `inventory_items.metadata_json.standing_zone` в нормализованных координатах.

### Остальные статические объекты

Допустимые `kind`: `stage`, `entrance`, `label`, `table`, `standing`, `text`. Проверяются id (уникальность непустой строки), конечность и границы `x/y/width/height/rotation/opacity`.

## 4. Подложки

`background` (объект/строка/null) и `backgrounds` (массив) проверяются:
- строка — data URI `data:image/...` или `http(s)://`;
- data URI ограничен 1.5 МБ;
- объект обязан иметь непустой `src` того же ограничения.

Рекомендуемый путь — ссылка на файл через медиатеку; Base64-подложки поддерживаются только для совместимости.

## 5. Ограничения

| Что | Лимит |
|---|---|
| Размер сериализованного JSON | `nabilet.hall_schema.max_payload_bytes`, по умолчанию 2 000 000 |
| Секторов | 200 |
| Мест | 20 000 |
| Статических объектов | 500 |
| Вместимость standing-зоны | 10 000 |
| Сторона холста | 20 000 |

## 6. Ошибки

```json
{"error": {"code": "SCHEMA_VALIDATION_FAILED", "message": "Hall schema validation failed",
  "details": {"fields": {"staticObjects.0.capacity": ["..."]},
              "objects": [{"id": "zone-1", "field": "staticObjects.0.capacity"}]}}}
```

- Код стабилен; frontend ищет проблемный объект по `details.objects[].id`.
- `SCHEMA_EMPTY_PAYLOAD` (422) — публикация без продаваемых мест.
- `SCHEMA_DRAFT_CONFLICT` (409) — несовпадение `base_revision`.
- Черновик допускает пустой `sectors`; опубликованная версия обязана содержать места/зоны и проходит проверку размера.

## 7. Round-trip

Ожидаемая цепочка: создание → экспорт → импорт → сохранение → перезагрузка → экспорт. Покрыта Vitest (`schemaSerialization.test.ts`) для редакторского формата; импорт Афиши (`rows`-формат) покрыт `YandexHallplanConversionTest.php` и PHP-тестами конвертации. Полный HTTP round-trip на реальных фикстурах пока не автоматизирован.
