## 0. Главный вывод из ТЗ

Раздел 97 ТЗ формулирует приоритет, который определяет весь план:

> «схема зала и Ticket Inventory должны быть спроектированы **раньше** каталога и красивого frontend»

Это не пожелание, а техническое ограничение. Причины:

1. **Inventory — это материализация.** `InventoryItem` создаётся один раз при публикации сеанса из immutable-версии схемы зала. Если модель схемы зала спроектирована неверно, `inventory_items` придётся перестраивать, а это означает потерю истории продаж, сломанные билеты и невозможность корректных возвратов.
2. **Конкурентное резервирование** (ТЗ §24) — единственное место в системе, где ошибка приводит к двойной продаже одного места. Это неисправимо постфактум: два валидных билета на одно место.
3. **Версионирование схем** (ТЗ §14) — правило «после публикации версия схемы становится immutable» нельзя «добавить потом», потому что к моменту добавления уже будут заказы, ссылающиеся на мутабельные данные.

**Следствие:** План построен так, что Этапы 1–3 (ядро + схема зала + inventory + hold) закрываются **до** того, как появится первый красивый экран каталога.

## 1. Целевая архитектура (кратко)

```
NABILET Core = Laravel 13 / PHP 8.3+ (Modular Monolith) + Vue 3/TS + MySQL 8.4 + Redis (опционально) + REST API + PWA + Android Checker
```

Полное обоснование — в [`ARCHITECTURE.md`](ARCHITECTURE.md). Три ключевых решения, влияющих на план:

| Решение | Следствие для плана |
|---|---|
| **Kernel без зависимостей от Laravel** (`app/Core`) | Хуки, модули, state machines, Money, подпись QR тестируются без БД и без фреймворка → быстрый TDD на критичной логике |
| **`InventoryItem` — единственная продаваемая сущность** | Всё коммерческое (цены, промокоды, возвраты, check-in) цепляется к inventory, а не к схеме зала |
| **Публичный каталог — SSR (Blade), админка — SPA (Vue)** | SEO (ТЗ §35–38) не требует отдельного рендер-сервиса; админка остаётся быстрой SPA |

### Этап 1. Ядро схемы зала и версионирование (P0 — критический путь)

Это самый рискованный этап. Ошибки здесь необратимы.

| # | Задача | Артефакт | DoD |
|---|---|---|---|
| 1.1 | Модель данных по пакету: `venues → halls → hall_schema_versions → sectors → hall_rows → seats / hall_tables / standing_zones` | Laravel-миграции, сгенерированные из `nabilet_core_spec/migrations.sql` + `DATABASE.md` | Схема исполняется на **MySQL 8.4**, все FK разрешаются, `migrations/009` применён |
| 1.2 | **Иммутабельность версии**: публикация версии → запрет любых мутаций | `HallSchemaVersion` + guard | Попытка UPDATE опубликованной версии → исключение |
| 1.3 | Геометрия: `x, y, width, height, rotation` для каждого объекта | миграции | Круглые сцены/веера рядов представимы без хаков |
| 1.4 | Standing-зоны: `capacity` без физических мест | миграции | Смешанное мероприятие (ТЗ §21) описывается одной схемой |
| 1.5 | Импорт/экспорт схемы: JSON + CSV с валидацией и превью (ТЗ §60–62) | сервис + API | Импорт 734 мест: превью показывает «Мест: 734, Рядов: 41, Секторов: 6, Ошибки: 3» |
| 1.6 | Редактор схемы (Konva, Canvas, 60 FPS на 500+ местах, ТЗ §15–17, §63–64) | Vue-модуль | 500 мест: drag/zoom без просадки ниже 60 FPS; автосохранение < 1 c |

**Ключевое правило (ТЗ §14), зашитое в код:**

```
HallSchema v1 ──→ Session 1   (использует v1, навсегда)
HallSchema v2 ──→ Session 2   (использует v2, навсегда)
```

Сеанс ссылается на `hall_schema_version_id`, а не на «текущую схему зала». Редактирование зала создаёт **новую версию**, никогда не меняет существующую.

## 4. Приоритизация: что НЕ входит в MVP

Осознанно откладывается, чтобы MVP дошёл до продакшена (ТЗ §92–95):

| Отложено | Причина |
|---|---|
| A/B testing, Heatmaps, session recording | Не влияют на способность продать билет; требуют consent-инфраструктуры |
| AI-модуль, умный поиск | Надстройка; подключается через хуки без правки ядра |
| Multi-organization, White Label | Сущность `Organization` закладывается сразу, но UI арендаторов — позже |
| Офлайн-checker с несколькими устройствами | Требует reconciliation-протокола; в MVP одно устройство онлайн |
| Marketplace, affiliate, loyalty | Продуктовое расширение, не ядро |

**Правило:** ни одна отложенная функция не должна требовать изменения ядра, когда её будут добавлять. Если требует — это архитектурный дефект, а не вопрос приоритета.

## 5. Определение готовности (DoD)

Общее для всех задач:

- [ ] Логика в сервисном слое; контроллер не содержит бизнес-правил и не обращается к БД
- [ ] Валидация на границе (FormRequest / DTO); ничего от клиента не принимается на веру
- [ ] Ошибки — типизированные, с кодом и корректным HTTP-статусом
- [ ] Мультитенантность: любой запрос ограничен `organization_id`, fail-closed
- [ ] Деньги — только целые minor units, никогда float
- [ ] Побочные эффекты (email, PDF, webhook) — через очередь, идемпотентно
- [ ] Структурный лог с `request_id`
- [ ] Тест на happy path + на отказ + на повторный вызов (идемпотентность)

Дополнительно для денег и мест:

- [ ] Конкурентный тест: параллельные запросы не приводят к двойной продаже
- [ ] Повторный вебхук не меняет состояние
- [ ] Откат транзакции не оставляет «зависших» hold'ов

## 6. Риски

| # | Риск | Влияние | Митигация |
|---|---|---|---|
| R1 | **Двойная продажа места** из-за гонки | Критично, необратимо | Транзакция + `FOR UPDATE` + уникальный индекс `(session_id, seat_id)` в `seat_holds`; конкурентный тест в CI |
| R2 | **Мутация опубликованной схемы зала** ломает исторические заказы | Критично | Иммутабельность версии на уровне модели + guard + тест |
| R3 | Повторная выдача билетов при повторном вебхуке | Финансово критично | `idempotency_keys` + дедупликация по `provider_event_id` |
| R4 | Производительность редактора схемы на 1000+ мест | Средне | Canvas + разделение static/dynamic слоёв + spatial index; замер FPS в DoD |
| R5 | Отсутствие Redis на хостинге клиента | Средне | Кэш/очередь/сессии с fallback на database/file; система деградирует, но работает |
| R6 | Утечка данных между организациями | Критично | Fail-closed global scope; тест «запрос без контекста → исключение» |
| R7 | Расхождение документации и кода при быстром росте | Средне | `tools/verify-schema.php` сверяет миграции с `DATABASE.md` в CI |
| R8 | Импорт «грязных» схем залов от клиентов | Низко | Импорт всегда в draft-версию + превью с ошибками до применения |
